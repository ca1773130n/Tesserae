Released **2026-09-11** · [PyPI](https://pypi.org/project/tesserae/0.40.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.40.0) · `pip install --upgrade tesserae==0.40.0`

Since v0.5.0 the incremental compiler has shipped behind a flag that was off,
labelled experimental, with a byte-parity gate that said it was proven for
seven edit shapes. This release turns the flag on. Before it could, the gate
had to be made honest.

## What happened

The parity gate compared an incremental compile against a full one and found
them byte-identical. It was comparing a full compile against a full compile.
Edge provenance was recorded against ids from before canonicalization, so on a
4-paper fixture 8 correct edges had 4 provenance rows, the readiness check
answered no, and every incremental arm silently degraded to a full recompile.
The gate now asserts `mode == "incremental"` from the build ledger. With the
remap fixed and incremental actually running, seven tests failed. All seven are
closed: multi-owner payloads re-extract the owner union, producer-owned layers
are stripped and regenerated, renamed files keep the aliases a full compile
folds in, and three subtractive leaks that kept what a full compile drops.

Measured on the real 1,422-file corpus, a correct owner union touches a median
24 files per edit. That is what "incremental" costs now.

## What changed

- **`incremental_compile` defaults to on.** A changed-only compile on a
  default project runs incrementally, and the ledger row says so.
  `incremental_compile: false` opts back out to the full recompile.
- **The build ledger records what a compile cost.** Each `.build-history.jsonl`
  row carries the mode, the duration, how many sources were extracted, and the
  reason for any downgrade to a full compile.
- **Sidecars are pruned.** `node_memory` and `fact_observed` were never
  reconciled; on one 1.19 GB store 95% of `node_memory` rows belonged to nodes
  that no longer existed. Full compiles now prune them, and `doctor` reports
  the bloat. Measured: 0.42 GB after, 65% reclaimed.
- **`tesserae engine --serve` serves the site from the daemon.** Same handler
  as `tesserae serve`, including `/api/ask`, on its own thread, stopped by an
  explicit closer at shutdown. A bind failure logs and the engine keeps
  compiling. Fleet mode never serves; `--serve` refuses `--once`,
  `--harvest-only` and `--all`.
- **The site build is an atomic swap.** The compile used to delete
  `.tesserae/site` and rewrite it, so a served page 404'd for the length of a
  compile. The build now lands in a staging directory and is exchanged with the
  live site in one syscall. A reader hammering the served index during three
  rebuilds sees zero misses; against the old path it saw 33,202.
- **`tesserae serve` is threaded.** One LLM `/api/ask` no longer blocks every
  static asset behind it.
- **A failed Pages push no longer wedges the repo.** `deploy.py` removes the
  worktree it created on every exit path and prunes stale registrations first.
- **`tesserae/frontend.py` is deleted.** 648 lines of dead code behind a
  one-line rebind; a test keeps it gone.

## Upgrade

The first changed-only compile after upgrading runs incrementally. If a graph
looks wrong afterwards, `tesserae compile` is still a full compile and
`incremental_compile: false` in `.tesserae/config.json` restores the old
default. Publishing stays manual on purpose: `deploy` needs a clean tree and
`gh-pages` is world-readable, so nothing in the daemon pushes.
