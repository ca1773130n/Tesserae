# Tesserae v0.42.0 — an open vocabulary that old readers can still load

Released **2026-10-06** · [PyPI](https://pypi.org/project/tesserae/0.42.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.42.0) · `pip install --upgrade tesserae==0.42.0`

The node and edge vocabulary was closed: a new relation type meant a new
release, and a graph that used one could not be read by an older install. A host
that grows its own ontology every week cannot work that way. This release lets
a host register types at runtime, each under a core parent, and keeps every
file it writes loadable by 0.41.

## What changed

- **Type registry.** `tesserae.type_registry` holds `TypeSpec` rows registered
  from code, from a JSON file, or from `TESSERAE_TYPE_REGISTRY`. Every type
  names a `core_parent`. Nodes keep their core type and carry the finer kind in
  `metadata.subtype`. An active registry edge type is accepted in memory.
- **Lenient load.** `TESSERAE_TYPE_MODE=lenient` maps a type the reader does not
  know onto its registry parent, else `Concept` or `references`. It keeps the
  original in `metadata.raw_type` and counts it in `load_stats`. The default is
  still `strict`, which raises exactly as before.
- **Views from the registry.** A registry type joins its declared view, else its
  parent's view. A new `crossdomain` view holds bridge relations such as
  `transfers_to` and `inspired_by`. It is empty until a host registers them.
- **Edge confidence and status.** Edges take optional `confidence`, `status`,
  `asserted_by`, `valid_from`, `invalid_at` and `provenance`. PPR multiplies the
  type weight by `confidence` and skips `candidate`, `refuted` and `retracted`
  edges unless asked. A refuted `supersedes` edge no longer hides its target.
- **Content resolver.** `compile_context(content_resolver=...)` asks the host
  for a node's content first, cheapest view first, then falls back to the wiki
  page and the description. Citations list the refs that were used.
- **Concept identity.** Federation merges nodes that share
  `metadata.concept_id`, a Wikidata QID or an MSC2020 class.
  `federate_graphs(identity_resolver=...)` lets a host supply identities from
  its own tables without editing any `graph.json`.
- **Schema drift.** `analyze_schema_drift(kind="edge")` proposes
  sub-relations, an `embedder` replaces name-token Jaccard, ledger records carry
  gate metrics, and `apply_ledger_to_registry` writes approved proposals into a
  registry file. It never retypes a node.
- **Capped neighbours.** `store_neighbors` and `store_iterate_edges` use a
  store's own `neighbors` / `iterate_edges` when it has them and fall back
  otherwise. `GraphStore` itself is unchanged.
- **Producer-only edges.** `transfers_to`, `candidate_transfer`, `analogous_to`
  and `merged_into` can never be extracted by an LLM or written as a type by an
  agent.
- **Agent writes.** `graph_write` maps a registry type onto its core parent
  before recording it, with `metadata.subtype` or `metadata.relation`. Edges may
  carry `metadata`.

## Compatibility

A 0.41 `graph.json` loads in strict mode with the same node, edge and type
counts. A graph without the new fields serializes byte for byte as before.
Nothing this release writes into `graph.json` or `agent-writes.jsonl` uses a
registry type, so going back to 0.41 stays safe.

## Upgrade

Nothing to migrate. Without a registry, every default is the 0.41 behaviour.
