Released **2026-08-04** · [PyPI](https://pypi.org/project/tesserae/0.28.6/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.6) · `pip install --upgrade tesserae==0.28.6`

**Upgrade if anything writes sessions into Tesserae from outside the local
harness convention.** Through 0.28.5, `tesserae sessions discover --import`
deleted those records, silently, and the plugin's `SessionEnd` hook runs a
discovery at every session close.

## The store shrank in a line that only reported growth

[#104](https://github.com/ca1773130n/Tesserae/issues/104), reported against
0.28.2 and still live in 0.28.5. A project had one session imported by an
external producer — an app that normalises its own agent sessions to
`HarnessSession` JSON and calls `tesserae sessions import <file>`. Running
`sessions discover --import` to add local Claude Code and Codex history took the
manifest from 1 to 377 sessions, and the pre-existing record was gone. Not just
from the manifest: pruned from the store. The only line printed was
`Imported harness sessions: 377`.

The empty-scan guard was already right — a scan that finds nothing merges rather
than wipes. What was wrong was how far "authoritative" reached. A discovery scans
local Claude Code and Codex transcripts; a record from any other producer is
structurally invisible to it. Not stale. Out of scope. It was pruned anyway.

## The fix, and the three ways past the first attempt

The first fix scoped pruning to the harness roots the scan actually walked. A
review of it found three ways past that scope, each deleting a record the run had
no authority over:

- **`--harness` narrowed the scan but not the scope.** Roots are discovered
  before the filter applies, so `sessions discover --harness codex --import`
  still carried `~/.claude` in its prune scope while rewriting nothing from it,
  and deleted every stored claude-code record. That is the example in the CLI's
  own `--help` text.
- **A record that would not parse was treated as belonging to nobody**, and
  deleted. But that is a producer mid-write, or a corrupt file — either way the
  owner is *unknown*, and deleting on unknown is how the original bug happened.
- **`Path.resolve()` ran unguarded.** A symlink loop raises `RuntimeError`, an
  embedded NUL raises `ValueError`, and neither was caught — aborting the write
  after the new files landed but before the manifest was rebuilt, leaving the
  store and its manifest disagreeing.

All three came from answering the same question the same wrong way. The rule now
written into the code: **every uncertain case answers "not mine to delete."**
Pruning is destructive and a scan's authority is narrow, so "I cannot show this
record is mine" has to mean "leave it alone."

Concretely, a stored record is deleted only when its transcript lives under a
root this run scanned **and** its harness is one this run scanned. Both halves
narrow independently. A `.md` page with no record behind it is still swept —
that is a genuine orphan, and sweeping those is what the prune was for.

Two smaller things fall out: a prune that removes records now prints the count
next to the import count, so a shrink can never again hide inside a line that
reports growth; and `write_sessions` now documents that omitting the scope with
`replace=True` still wipes the whole store, which is the old behaviour, still
reachable, and wanted by no caller in Tesserae.

## The contract is written down now

The bug was possible partly because nothing said how the two entry points differ.
A tool producing normalised `HarnessSession` JSON could call `sessions import`
and had no way to learn that a later discovery would delete what it wrote.
[`docs/session-history.md`](../session-history.md) now has a **How the store is
written** section stating it: import merges, discovery replaces only within what
it scanned, and everything else survives.

## Also in this release

Work on the graph-growth eval, which is developer-facing and changes no runtime
behaviour. It now slices the whole demo corpus — 73 documents rather than 50
papers, with repos, digests, syntheses and open questions dated from what they
already declare rather than from dates written into the corpus. Anchor
resolution matches label tokens instead of a literal phrase.

The honest result of running it: 15/15 questions answerable, and that number
means less than the 14/15 it replaced. On the larger graph, fourteen of fifteen
questions already answer in a *single* hop and 87% of arbitrary anchor pairs
connect within three. Answerability inflates with corpus size because anchor
resolution is set-based. `evals/growth/probe_anchors.py` measures exactly this,
and its finding is recorded rather than smoothed over — the eval's discriminating
power, not its score, is the open problem.
