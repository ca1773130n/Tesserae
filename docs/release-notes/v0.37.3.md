Released **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1 and v0.37.2 made a local OpenAI-compatible server reachable. Running one
exposed the next thing: the extraction pool is sized for a rate-limited cloud
API, and a model server on this machine serves one request at a time.

## What happened

`TESSERAE_EXTRACT_CONCURRENCY` defaults to 4. Ollama, llama.cpp and LM Studio
serve one request at a time, so three requests queued behind every call, and a
queued request the server dropped blocked its worker for the whole
`TESSERAE_EXTRACT_TIMEOUT`. From the outside that looks exactly like a memory
problem, and it cost hours before it was read correctly.

## What changed

- **Unset, the knob follows the endpoint.** A loopback `llm_base_url`
  (`localhost`, `127.0.0.1`, `::1`) means one document at a time, and a stderr
  note names the endpoint and the override.
- **The batch runner asks the extractor where its requests go.**
  `LLMResearchExtractor` exposes its client's `base_url` and the selective
  router answers for its LLM half, so nothing was plumbed through four call
  sites. A deterministic extractor has no endpoint and keeps 4.
- **An explicit value always wins.** A loopback proxy that fans out to a cloud
  API (LiteLLM, vLLM with batching) can take more: set it.

`docs/tuning.md` documents the new default.

## Upgrade

Nothing to migrate. If a local-model compile looked stuck or out of memory, it
was probably this. A `TESSERAE_EXTRACT_CONCURRENCY=1` you added as a workaround
can stay or go; the result is the same.
