Released **2026-08-28** · [PyPI](https://pypi.org/project/tesserae/0.34.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.34.0) · `pip install --upgrade tesserae==0.34.0`

A knowledge graph is worth what it knows. This release found out how little of
each document reached it, and fixed the four things standing between a corpus
and a graph that answers from it.

## One extraction call per document, however long the document

The extraction prompt embedded the whole document and nothing ever split it —
the timeout error's own advice, "split the document if it is large", was
addressed to the operator. So a 38 KB paper got one pass and the model returned
what it considered a complete answer.

Measured on 148 full papers:
**29.6 factual relations per document became 209.8**, a 7.1x increase, with
6.8x the nodes.

It is not truncation and not a token cap. Both were tested: the single call
stops on its own, and raising the output limit 6.4x bought 20% more output. The
model answers each REQUEST with a bounded graph whatever it was shown, so the
only way to get more is to ask more times. `TESSERAE_EXTRACT_CHUNK_CHARS` is
that dial, and the curve behind it is in the constant's docstring — there is no
knee, so it trades compile time for density in a straight line.

## Retrieval now beats the lexical baseline

Three defects were costing the retriever more than the graph was:

- The lexical lane claimed FTS5 `MATCH` semantics and matched **substrings** —
  `in` scored hits on "training", "domain" and "inference" — with no
  normalisation, fused at weight 1.0, equal to BM25.
- `hybrid_search(source_root=)` appends a document's own text to its lexical
  haystack, and no production caller passed it. The feature was inert.
- A document whose `SourceDocument` anchor lost a same-name merge stopped being
  findable as a document at all: **23% of one corpus, 138 of 1,552 in another**.

Gold-document recall went from **0.476 to 0.602** on the fixes alone, then to
**0.743 with the denser graph — against flat BM25's 0.605**.

## The bundle carries source text, at a threshold that is now measured

`compile_context` replaces a node's extracted body with the source document
behind it. The floor deciding when that is worth doing was 900 characters, and
900 sits inside the range where the swap makes the bundle **worse**:

| characters per document | extracted claims | source prose |
|---|---|---|
| 4,300 | 0.218 | **0.371** |
| 2,500 | 0.227 | **0.332** |
| 1,260 | 0.222 | **0.145** |

A claim is a self-contained sentence and survives slicing; a passage needs room
to carry an argument. At 4,300 characters per document the bundle beats a BM25
passage control by **+0.084** — 8 of 8 replicates, p=0.0078. The floor is now
2,500, the measured crossover.

## Also

- every `EvidenceSpan` is reachable from its own document; whether it was had
  been left to the model, which declined **89% of the time** on one corpus
- the DeepScholar arm resolved 1 cited paper of 14 and called the result
  evidence

## Upgrading

Nothing changes until you recompile. When you do, budget for it: chunked
extraction costs one call per chunk, and 148 full papers took **9 hours**
against 66 minutes. Raise `TESSERAE_EXTRACT_CHUNK_CHARS` to trade density back
for speed, or set it to `0` for the previous behaviour.
