Released **2026-08-07** · [PyPI](https://pypi.org/project/tesserae/0.29.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.29.0) · `pip install --upgrade tesserae==0.29.0`

This release makes Tesserae usable when several machines share a disk, and fixes
two things that were quietly making its output worse than it looked.

## Tesserae was ingesting its own LLM calls as your sessions

Every compile spawns the `claude` CLI once per document and once per session.
Each of those writes a transcript into `~/.claude/projects`, and session
discovery harvested them as if they were your coding work. On the maintainer's
own project:

| | |
|---|---|
| stored session records | 14,605 |
| Tesserae's own extraction calls | **14,377 (98.4%)** |
| genuine user sessions | 228 |

10,666 of them carried a single title — the extraction prompt.

A filter for this already existed, and so did a test whose whole job was keeping
it complete. That test scanned the source for prompts matching
`You (?:are|distill|write|decide|arbitrate|split)` — a hand-maintained allowlist
of opening **verbs**. The extraction prompt opens with "You extract", so the
highest-volume prompt in the system was the one prompt the guard could not see.

The guard now enumerates `system=` arguments from the AST and resolves
module-level constants, because a prompt is identified by **how it is passed**,
not how it happens to be worded. That immediately found five more uncovered
calls: the liveness probe, the activity summary (two wordings), the decision
extractor, the claim judge and the scope router.

`tesserae sessions prune-internal` now cleans the **file store** as well as
sqlite — it only cleaned sqlite before, and the file store is the one `compile`
reads, so cleaning appeared to do nothing. It takes `--dry-run`.

If you have been running Tesserae for a while, run it. Then recompile; your node
counts have been measuring noise.

## Several machines sharing one project directory

Nothing in Tesserae carried any machine identity, so every piece of per-machine
state living in a shared `.tesserae/` was read and written by every host as if
there were only one.

**Session records could be deleted by a host that never saw them.** `producer`
cannot separate two machines: every host's scan stamps the same constant, and
their `~/.claude` roots resolve to the same string, so both existing safety
gates passed on a host that never saw the transcript — and it deleted another
machine's record while reporting success. Records now carry the harvesting
host, and a host prunes only what it harvested.

The host id is persisted at `~/.tesserae/host_id` (override with
`TESSERAE_HOST_ID`) rather than derived from the hostname, because a fleet built
from one image reuses hostnames and a collision would hand one machine's records
to another.

Three more collisions are fixed: the engine pidfile is now `daemon.<host>.pid`
(liveness was `os.kill(pid, 0)` against the **local** process table, meaningless
for another machine's pid), the Codex scan watermark is per-host (one shared
floor meant whichever host ran last moved it past transcripts the other had not
read — those were never imported), and `doctor --fix` will not touch a foreign
host's pidfile at all.

**New: `tesserae engine --harvest-only`.** One host compiles; every other host
tails only the transcripts it can see and never takes the compile lock. That
removes the contention rather than arbitrating it.

## A background engine no longer blocks you

`compile` and `refresh` take `--wait [SECONDS]`, which queues for the project's
compile lock instead of exiting 2, reporting every five seconds and naming the
machine that holds it. The background daemon now defers with exponential backoff
capped at 60s rather than dropping its trigger.

`--wait` is an explicit flag rather than something inferred from whether stderr
is a terminal: the same command must not change behaviour under `tee`, in tmux
capture, or in CI. It is bounded because `flock` offers no fairness and
therefore no starvation bound.

## `compile --all` / `refresh --all`

One command over every registered project, with per-project failure isolation —
one project failing does not stop the others. A project whose compile lock is
held reports as **locked**, not **failed**, and gets its own exit code: on a
fleet that is the normal state, and giving it the same code as a traceback
teaches people to ignore the exit code. `--jobs` defaults to 1 because a compile
is LLM-heavy.

## Project-level LLM config now actually reaches the client

`ProjectWiki._build_json_client` resolved the project config and then called the
client factory **without it**, so the factory re-resolved against env plus the
global config only and discarded every project-level `llm_model`,
`llm_base_url` and `llm_api_key`. A custom endpoint written into
`.tesserae/config.json` never reached the client and the compile silently ran on
the default backend.

The documentation already described the correct behaviour — only the code
disagreed, which is the worst shape a bug can take, because it gives you no
reason to suspect the tool.

Repeating `--claude-config-dir` also collapsed to the first account, since
`CLAUDE_CONFIG_DIR` is a scalar. The full ordered list now travels in
`TESSERAE_CLAUDE_CONFIG_DIRS`.

## Honest reporting

`tesserae init` now registers the project. Without that, following the README
quickstart produced an `ask` that could not resolve a cwd alias, fell back to
federated scope, and answered a question about a three-file project out of
19,744 nodes belonging to unrelated repositories — while `--scope current`
exited 2 saying "not inside a registered project" from inside one.

`compile` now exits 1 when **every** document fell back to deterministic
extraction. It printed a summary and exited 0, so a graph with no concept layer
read as success and `query` then matched nothing.

`doctor` no longer reports `credentialed LLM CLI` on the strength of files that
only prove the CLI was once used — it printed a green check in the same second
`compile` failed on authentication. **This is a downgrade in confidence, not an
upgrade in capability**: verifying credentials costs a real LLM call, so the
check now states only what it actually verified.

New report-only `filesystem_locking` check. Every concurrency guarantee here
rests on `flock(2)` being enforced by the filesystem holding `.tesserae/`, and
over NFS or SMB that is configuration-dependent — without a working lock daemon
`flock` can silently degrade to a no-op. It warns on a network filesystem and is
explicit that a single host **cannot** prove cross-host enforcement. If you run
Tesserae from several machines against shared storage, test that directly.

## Concurrent writes

Five artifact writers published through a single fixed temp path — note that
`with_suffix` *replaces* the suffix, so `graph.json` published through
`.tesserae/graph.tmp`. Two publishers interleaved into that one file and renamed
the mixture into place. The manifest one mattered most: `_load_manifest` calls
`json.loads` unguarded, so an interleaved manifest raised out of every later
compile on every host.

`TESSERAE_REGISTRY` is now honoured by every command instead of by the engine's
fleet mode alone.

## Upgrading

Nothing to do. Single-machine installs behave exactly as before; the host field
is additive and a record without one is left alone until you pass
`--adopt-unowned`.

Two things worth running once:

```bash
tesserae sessions prune-internal --dry-run   # see how much of your store is noise
tesserae sessions prune-internal             # then clean it
tesserae compile                             # and rebuild on what is left
```
