Tesserae поставляется со stdio-сервером [Model Context Protocol](https://modelcontextprotocol.io), который открывает скомпилированный типизированный граф любому MCP-совместимому клиенту: Claude Code, Codex CLI, Cursor, Claude Desktop и другим. Сервер объявляет три полноценные поверхности MCP — **tools**, **resources** и **prompts** — поэтому клиенты могут как запрашивать граф по требованию, так и дешево подгружать контекст из канонических URI.

## Предварительные требования

Сервер читает из `.tesserae/graph.json`, поэтому требуется однократная компиляция:

```bash
cd /path/to/your-project
tesserae init    # interactive; or --yes for non-interactive
tesserae compile  # deterministic, no LLM calls, no API keys
```

Перекомпилируйте при каждом изменении источников. Сервер подхватит новый граф при следующем вызове инструмента без необходимости перезапуска.

## 1) Сгенерируйте конфиг клиента

```bash
tesserae projects mcp-config
```

Выводит JSON-фрагмент, примерно такой:

```json
{
  "mcpServers": {
    "tesserae": {
      "command": "python3",
      "args": [
        "-m", "tesserae.mcp_server",
        "--graph", "/path/to/your-project/.tesserae/graph.json"
      ]
    }
  }
}
```

Точный путь подставляется из текущего проекта. Передайте `--name <alias>`, если хотите задать имя записи сервера, отличное от `tesserae`.

## 2) Вставьте его в свой MCP-клиент

| Клиент | Расположение конфига |
|---|---|
| Claude Code | `~/.claude/mcp-servers.json` (или `~/.config/claude-code/mcp-servers.json`) |
| Claude Desktop | macOS: `~/Library/Application Support/Claude/claude_desktop_config.json` |
| Codex CLI | `~/.config/codex/mcp-servers.json` |
| Cursor | Settings → MCP Servers → вставьте JSON |
| Hermes | `~/.hermes/config.toml` (используйте TOML-эквивалентный блок, выводимый `mcp-config --format hermes`) |

После редактирования перезапустите клиент. Следующая сессия подключится и обнаружит поверхность Tesserae.

## 3) Что видит клиент

### Tools — вызываются моделью

Каждый инструмент принимает необязательный `graph_path` или `project` (псевдоним из реестра), поэтому один сервер может разрешать любой зарегистрированный vault при каждом вызове. При отсутствии — откат к активному проекту.

**Запросы к графу и извлечение**

| Инструмент | Назначение |
|---|---|
| `graph_map` | **Начинайте отсюда.** Бюджетная карта иерархии графа — точка входа Descent. Без области возвращает корневой набор карточек (счётчики, ключевые хабы, по карточке на каждое самое крупное сообщество); `scope='<scope_id карточки>'` спускается на уровень дендрограммы; `org:root` обходит дерево организации агентов. Ориентирует агента, избавляя от угадывания поисковых слов |
| `schema` | Управляемый словарь node, edge и wiki-kind |
| `graph_summary` | Количество узлов и рёбер и распределение типов для активного проекта |
| `search_nodes` | Фильтрация публичных узлов графа по `query`, `type`/`types`, `kind`, `limit`, гибридным `mode`/`weights`; `include_superseded` показывает выведенные из обращения узлы; `explain` добавляет профиль ретривела `profile` (см. ниже) |
| `node_context` | Узел + его инцидентные рёбра + соседние узлы. `use_ppr` ранжирует соседей персонализированным PageRank вместо обхода в 1 шаг; `include_superseded` и `limit` ограничивают результат. `node_id`, который потерял слияние при позднейшей компиляции, **не** промах: он разрешается через merge-ledger в узел, который его поглотил, и ответ приобретает `status: "merged"` с `merged_from` / `merged_into`, так что вы узнаёте id, который нужно держать от теперь. Ледник консультируется только после того, как граф не найдёт, поэтому живой id никогда не может быть перенаправлен |
| `embedding_status` | Сообщает об активном бэкенде эмбеддингов, питающем гибридный поиск, а также о его сохранённом кэше векторов — `vectors_cached` для этого ключа бэкенд/размерность и общепроцессные `cache_hits` / `cache_misses` / `cache_errors`, чтобы холодный или недоступный для записи кэш нельзя было принять за быстрый путь. Принимает `graph_path` / `project`, чтобы выбрать проект, чей сайдкар отражён в отчёте |
| `search_facts` | Временные факты, спроецированные из графа (в стиле Graphiti), ранжируются по СОДЕРЖАНИЮ факта — субъект, предикат, объект, свидетельство — а не по сериализованному факту, поэтому фрагмент id или метаданных не считается совпадением; `dated` (`any`, `dated`, `undated`) отбирает по тому, есть ли у факта пригодный `valid_from`; `current_only` фильтрует до актуальных, `as_of` отвечает по состоянию на прошлую дату. Вместе они отклоняются — это разные часы — а `undated_included` сообщает, сколько из возвращённых строк не имеют даты |
| `timeline` | Факты, упорядоченные по РАЗОБРАННОМУ `valid_from`, для лонгитюдного представления: факты без даты собираются в отдельную группу после всех датированных и возвращаются счётчиком `undated_events`, а не перемешиваются с ними; `dated` (`any`, `dated`, `undated`) отбирает по тому, есть ли у факта пригодный `valid_from`; `as_of` отвечает по состоянию на прошлую дату — это точка на интервалах действия, а не нижняя граница диапазона — а `undated_included` сообщает, сколько из возвращённых строк не имеют даты. Факт без даты `as_of` сохраняет, поэтому именно этот счётчик отличает скудный ответ от полного. Принимает `observed_as_of` тоже. `total_events` считает каждый факт, который СОВПАЛ, а не страницу, которую вам выдали — весь набор совпадений date-отсортирован перед срезом страницы, поэтому самые ранние события — те, которые timeline действительно возвращает, и `total_events > len(events)` — как вы скажете полной странице от полного ответа |
| `graph_ppr` | Персонализированный PageRank с затравкой в одном или нескольких `seed_node_id`; возвращает top-K наиболее релевантных узлов с настраиваемыми `alpha`, `directed`, `edge_type_weights` |
| `wiki_page` | Тело скомпилированной markdown-страницы для узла плюс внутренние ссылки, на которые она ссылается. Устаревший `node_id` следует той же перенаправке merge-ledger молча — поглощённый узел — имя-альтернатива на survivor, поэтому страница survivor *есть* страница, которую вы просили |
| `raw_source` | Исходный markdown (с ограничением до 16 KB). Никогда не возвращает байты: для узла `Artifact` он указывает вам на `drill_down`, который вместо этого сообщает путь актива и адрес на сайте |
| `verify_claim` | Проверяет ОДИН триплет по графу — точный поиск, без LLM, без нечёткого сопоставления, без ранжированных результатов. Возвращает `{verdict, reason, triple, citation, provenance, advisory}`; `verdict` — это `SUPPORTED` (ребро существует **и** его свидетельство является дословным фрагментом документа), `PRESENT_UNEVIDENCED` или отказ. Если у вас только проза, свяжите `search_nodes` → `verify_claim` |
| `doctor_run` | Запускает проверки здоровья и возвращает отчёт в JSON (`findings`, `exit_code` 0/1/2). **Всегда только чтение** — починки через MCP не выполняются; для ремонта используйте `tesserae doctor --fix` в CLI |
| `doctor_report` | Содержимое `.tesserae/doctor-report.md` (с ограничением до 64 KB); пусто, пока не отработает `tesserae doctor` |
| `lint_report` | Последние находки lint, полученные на этапе компиляции (с ограничением до 64 KB) |

**Профилирование ретривела.** `search_nodes` и `compile_context` принимают
`explain: true` и отвечают с `profile` — для каждой из ланий `bm25`, `lexical`
и `embedding` её вес, `candidates_in`, сколько она оценила,
`embed_calls` / `cache_hits` / `cache_misses` и её wall time, плюс всего
`candidates_in` / `admitted` / `returned` и какие ряды действительно внесли
каждый из узлов, которые он считает. `returned` и эта пер-узловая атрибуция полос —
**до бюджета**: слияние фиксирует оба на собственном top-`k` срезе, а обязывающий
`budget_chars` подрезает тот срез уже потом, в MCP-слое, не переписывая
профиль. Поэтому при плотном бюджете `returned` описывает срез, который
произвёл ретривер, а не строки в отклике, и разницу сообщает
строка `continuation`. `search_nodes` возвращает один профиль;
`compile_context` возвращает список, один на каждый поиск семян, который он запустил.

Выключено по умолчанию, и выключено — не формальность: измерение стоит время, поэтому это
диагностика, а не что-то, чтобы оставлять включённым. Оно не может сдвинуть ранжирование — каждое
число читается из таблиц score и rank, которые слияние уже произвело — и
с неустановленным флагом ответ несёт ровно те ключи, что всегда. `cache_hits` / `cache_misses`
счётчики — как вы скажете тёплому vector cache от холодного в live-запросе, чем
проверкой `embedding_status` после события.

**Компилятор контекста по запросу** (Phase 7)

| Инструмент | Назначение |
|---|---|
| `compile_context` | Компилирует адаптированный документ контекста **со ссылками** для `query` или явных `seeds`. Обходит подграф ограниченной глубины (`depth`, 1–10, по умолчанию 2), ранжирует через PPR и заполняет символьный `budget` (по умолчанию 32000; `0` — без ограничения). По умолчанию детерминирован; при `synthesize: true` создаётся написанный LLM нарративный срез "topic". Возвращает `body`, `citations`, `selected_node_ids` и `char_budget_used`. `view` ограничивает обход именованным разделом рёбер — `semantic`, `temporal`, `causal` или `entity`; передайте массив имён для выполнения одного обхода на каждый view и их объединения (взвешенный RRF). Всякий раз, когда запрашивается view — одно имя или несколько — каждая цитата содержит `via_views` (view'ы, чьим обходом была достигнута). `explain` добавляет `profile`, один на каждый поиск семян |
| `get_handle` | Постранично забирает большую полезную нагрузку, ранее возвращённую как `handle` (например, `compile_context` с `preview`), срезами (`offset`, `limit`) — догружая по мере надобности вместо того, чтобы вывалить всё в контекст |
| `list_communities` | Перечисляет узлы `COMMUNITY_SUMMARY`, созданные пост-компиляционным проходом, по числу участников (`min_size`, `limit`); через `node_context` пройдите по рёбрам `summarizes` обратно к участникам |
| `fresh_insights` | Находки сессий, ранжированные по баллу затухания в стиле Эббингауза (сначала новые и наиболее посещаемые); отфильтровывает находки, вытесненные более новыми почти-дубликатами. Необязательные `kind`, `limit`, `include_superseded` |

**Память сессий** (см. [sessions.md](sessions.ru.md))

| Инструмент | Назначение |
|---|---|
| `list_sessions` | Конверты сессий (id, started_at, title, files_touched, счётчики находок) для активного проекта; `since`, `limit` |
| `find_session_findings` | Все находки сессий, связанные с `node_id` через `discussed_in` / `references`, с возможной фильтрацией по `kinds` (insight / decision / question / todo / hypothesis / takeaway) |
| `find_code_symbol_mentions` | Расширяет находку сессии до символов `CodeFunction`/`CodeClass`/`CodeMethod`, которые она упоминает, через рёбра `discusses` из опционального прохода связывания insight↔symbol. Слой кода включается явно: без записи `external_tools` для `codegraph` он ничего не вернёт |
| `activity_summary` | Ежедневный/еженедельный дайджест по зарегистрированным проектам — сессии, находки, коммиты git, PR и загруженные документы, каждый по **своей собственной** отметке времени, никогда по `started_at` сессии. Отрисовывает детерминированный markdown и, если не отключено, предваряет его LLM-нарративом |
| `query_decisions` | Решения по зарегистрированным проектам в заданном интервале: явные **человеческие** выборы, детерминированно разобранные из `AskUserQuestion` в Claude Code (сам вопрос и выбранный вариант), плюс решения агентов, извлечённые из разговора |

**Память агентов и запись обратно** (см. [agent-memory.ru.md](../agent-memory.ru.md))

| Инструмент | Назначение |
|---|---|
| `agent_view_explain` | Объясняет область видимости агента, *не загружая её*: режим разрешения (worker / manager / org), агенты-участники, путь и число узлов каждого L1-артефакта, а также отметка устаревания `distilled_through` |
| `drill_down` | Возвращает `member_ref` дистиллята к исходному узлу L0 — явная, протоколируемая эскалация руководителя за пределы дистиллированной видимости. Возвращает статус `alive` / `changed` / `absorbed` / `gone`; каждый вызов пишется в сайдкар. Сверление **фигуры** `Artifact`, чей актив разрешился внутри проекта, добавляет три ключа никакой другой узел не несёт: `asset_path` (где байты живут на диске), `asset_sha256` (digest этих байтов, который с видом сеет id узла) и `asset_site_path` (content-addressed адрес под `raw-assets/` на построенном сайте). Таблица и уравнение Artifacts вообще не носят актива — их контент *есть* их описание — и фигура, разрешённая вне корня проекта, никогда не хранила путь; оба сверлят обратно с обычными ключами. Некорректный объявленный хеш выбрасывает `asset_site_path` вместо того, чтобы изобретать адрес |
| `read_audit` | Кто читал граф: записанные события чтения (`tool`, `actor`, `node_ids`, `at`, `tesserae_version`), сначала свежие, плюс сводка по акторам — чтобы счётчики доступа, управляющие забыванием по неиспользованию, можно было отнести к конкретному читателю. **По явному включению** — ничего не записывается, пока в процессе сервера не задан `TESSERAE_READ_AUDIT=1`, потому что постоянно включённый аудит превращает каждое чтение в запись. Уже записанные строки остаются доступными после выключения флага; `enabled` сообщает текущую настройку. Фильтры: `actor`, `tool`, `node_id` |
| `graph_write` | Пишет типизированные узлы и рёбра прямо в граф — без markdown и без прохода извлечения. Запись попадает в append-only оверлей и воспроизводится как производитель при компиляции, поэтому она **переживает пересборку**. Строго: неизвестные типы, ребро без свидетельства и конец ребра, которого нет ни в полезной нагрузке, ни среди существующих id узлов, отвергаются. **Чтобы отозвать** просто неверное, не выдумывая замену: направьте ребро `retracts` на неверный узел **по id** — цель выпадает из открытий (`search_nodes`, `fresh_insights`), из выбора контекста (`compile_context`), и из каждого списка соседей и рёбер инцидента `node_context` возвращает. Что оно *не* делает — это скрывает узел из того, кто его называет: точный поиск `node_context` по id или имени по-прежнему возвращает узел себя, помеченный `"retracted": true`, потому что вызывающий просил этого. `include_superseded: true` кладёт его обратно на поверхности открытия, и ничего не удаляется |

**Вопрос-ответ и реестр**

| Инструмент | Назначение |
|---|---|
| `ask` | Вопрос–ответ на естественном языке через настроенный бэкенд памяти (raganything, cognee или скомпилированную wiki). `backend`, `top_k`; веерный запрос по нескольким vault через `scope`/`scope_aliases`; `claude_config_dir` для маршрутизации между аккаунтами. На маршрутизованном по графу вопросе оболочка несёт `plan` (рассуждение планировщика, выбранные шаги, и `executed` — что действительно запустилось), и может носить `proposed_write`: узлы и рёбра, которые планировщик думает стоит записать, обоснованные только в том, что *вопрос* утверждал. Это **предложение, никогда не запись** — его происхождение всегда null, поэтому `graph_write` отказывает, пока вызывающий с ключом агента и внешней якорью его не предоставит. Мутация никогда не побочный эффект запроса |
| `query` | Сырой поиск без LLM — зеркалит `tesserae query`. `backend='wiki'` (по умолчанию) — детерминированный BM25/семантический поиск по скомпилированной вики с ранжированными попаданиями и выдержками; `backend='raganything'` обращается к опциональному мультимодальному индексу RAG, если проект его включил. За синтезированным ответом со ссылками идите в `ask` |
| `ingest` | Загружает сырой веб/текст (например, вырезку из браузера) в граф знаний разрешённого проекта |
| `list_projects` | Перечислить зарегистрированные проекты |
| `register_project` | Добавить проект в реестр |
| `unregister_project` | Удалить проект из реестра (привилегированного «активного» проекта не существует) |

**Управляемая настройка**

| Инструмент | Назначение |
|---|---|
| `tesserae_setup_plan` | Определяет окружение и предлагает план настройки в виде JSON. Только чтение — никогда не трогает `.tesserae/` |
| `tesserae_setup_apply` | Применяет (возможно отредактированный) план: записывает `.tesserae/config.json` и выполняет защищённые действия установки/запуска. Защищено `confirm_install_actions` / `confirm_run_actions` |

### Resources — автоматически подгружаются в контекст модели

URI, которые клиент может подтянуть через свой пикер ресурсов, не тратя ход инструмента:

- `tesserae://graph/schema` — та же полезная нагрузка, что и у инструмента `schema`, готовая как статический контекст
- `tesserae://graph/summary` — сводка по активному проекту
- `tesserae://lint-report` — последний lint-отчет в виде markdown

Плюс шаблоны URI, которые клиент может конструировать по требованию:

- `tesserae://wiki/{kind}/{slug}` — тело любой скомпилированной wiki-страницы
- `tesserae://raw/{source_path}` — любой исходный markdown

### Prompts — исследовательские шаблоны в один клик

Эти шаблоны появляются в slash-меню клиента (например, в палитре `/` Claude Code):

| Промпт | Аргументы | Что делает |
|---|---|---|
| `summarize-paper` | `slug` (обязательный) | Вызывает `node_context` + `wiki_page` + опционально `raw_source`, затем возвращает структурированное саммари: вклад, набросок метода, ключевые результаты, ограничения, связанные узлы |
| `find-related-work` | `topic` (обязательный), `limit` | Объединяет `search_nodes` + `node_context` для топ-K связанных элементов с обоснованиями релевантности |
| `compare-approaches` | `a`, `b` (оба обязательные) | Подтягивает `node_context` для обоих + `search_facts` для заявлений о производительности; возвращает сравнение бок о бок с синтезом |
| `gap-analysis` | `topic` (необязательный) | Выявляет нерешенные открытые вопросы, отсутствующие бенчмарки, недостаточно подкрепленные утверждения |
| `triage-open-questions` | _нет_ | Перечисляет все узлы `OpenQuestion`, группирует по теме, предлагает порядок приоритетов |

Каждый промпт рендерится в одно пользовательское сообщение, которое точно сообщает модели, какие инструменты Tesserae связать в цепочку, чтобы модель не пересоткрывала поверхность каждый раз заново.

## Multi-project: регистрация нескольких vault под одним сервером

Постоянный реестр в `~/.tesserae/registry.json` позволяет одному и тому же MCP-серверу разрешать любой зарегистрированный проект по имени:

```bash
tesserae register-project /path/to/research --name research
tesserae register-project /path/to/notes    --name notes
```

После этого каждый инструмент, принимающий `project` или `graph_path`, будет разрешать `project: "research"` по реестру, не требуя полного пути. Сервер даже проверяет, что зарегистрированный `graph_path` всё ещё существует, и возвращает понятную ошибку, если нужна перекомпиляция.

### Fan-out по всем зарегистрированным vault

Инструмент `ask` принимает `scope: "all-registered"` для параллельного запроса по каждому зарегистрированному проекту и возврата агрегированных результатов:

```jsonc
{
  "name": "ask",
  "arguments": {
    "question": "Where is splatting used?",
    "scope": "all-registered"
  }
}
```

Ограничьте подмножеством через `scope_aliases: ["research", "notes"]`.

## Multi-account Claude CLI

Если ваш инструмент `ask` маршрутизируется через Claude CLI и у вас несколько аккаунтов (например, `~/.claude` и `~/.claude-personal2`), передавайте `claude_config_dir` для каждого вызова:

```jsonc
{
  "name": "ask",
  "arguments": {
    "question": "...",
    "claude_config_dir": "/Users/you/.claude-personal2"
  }
}
```

Сервер экспортирует `CLAUDE_CONFIG_DIR` только на время этого вызова и восстанавливает предыдущее значение после. Никаких утечек между вызовами.

## Проверка

После перезапуска MCP-клиента подтвердите соединение:

- Claude Code: `/mcp` должен показать `tesserae` с количеством инструментов.
- Cursor: иконка MCP в чате должна показывать `tesserae: connected` с количеством tools/resources/prompts.
- Codex / Hermes: вызовите любой инструмент по имени (например, `schema`) и проверьте ответ.

Если ничего не появляется, дважды проверьте, что `--graph` указывает на существующий `.tesserae/graph.json` — сервер теперь валидирует это при старте и при каждом вызове инструмента, так что вы увидите понятное сообщение об ошибке вместо безмолвного 500.

## Где это уместно

MCP-сервер — это **интерфейс чтения** типизированного графа. Для **пути записи** (загрузка источников, перекомпиляция, обновление сопутствующих инструментов вроде RAG-Anything) используйте CLI напрямую. Эти две части развязаны: CLI обновляет `.tesserae/`, а MCP-сервер читает то, что там лежит, при следующем вызове инструмента.
