Tesserae может импортировать локальные транскрипты AI-агентов и отображать их
как память проекта в секции `sessions/` статического сайта.

Эта возможность намеренно отделена от `export harness`:

- `export harness` — исходящий контекст для инструментов вроде Claude Code,
  Codex, Gemini, Cursor, Kiro и OpenCode.
- `sessions ...` — входящая история: она нормализует прошлые сессии Claude
  Code/Codex для текущего проекта, сохраняет их под
  `.tesserae/harness_sessions/` и позволяет `export site` публиковать
  индексные и детальные страницы сессий.

## Два пути внутрь: пакетный импорт и живой мониторинг

Инжест сессий больше не только пакетный. Есть два пути в одно и то же
нормализованное хранилище:

- **Пакетный импорт** — `sessions discover/import` сканирует корни
  транскриптов по требованию и записывает одноразово. Ниже на этой странице
  описан именно этот поток.
- **Живой мониторинг** — демон-супервизор (`tesserae engine`) запускает
  `SessionTailer`, который наблюдает за транскриптами Claude Code и Codex
  *самого этого проекта* и вливает новые ходы по мере их появления. Каждый
  тик переходит к сохранённому пофайловому байтовому смещению, читает только
  новые байты и сохраняет завершённые ходы в SQLite `HarnessSessionsDB`
  (`.tesserae/sqlite.db`) **до** постановки в очередь дебаунсированной
  перекомпиляции, так что компиляция всегда читает согласованное состояние.
  Тейлер ограничен сессиями собственного проекта (Claude
  `projects/<slug>/*.jsonl`; Codex фильтруется по cwd) и после перезапуска
  возобновляет работу с сохранённых смещений без повторного проигрывания
  ходов.

Запуск живого цикла:

```bash
tesserae engine        # watch sources, coalesce bursts, auto-recompile
tesserae engine --once # single drain cycle then exit (deterministic)
```

`tesserae refresh` выполняет тот же конвейер ingest → compile → project один
раз, внутри процесса, без запуска долгоживущего наблюдателя (передайте
`--no-sessions`, чтобы пропустить сканирование harness-сессий).

## Модель приватности

Оба пути инжеста явные: живой тейлер работает только пока вы держите
`tesserae engine` живым, а пакетное обнаружение пишет только с `--import`.
Обычный `tesserae compile` или `tesserae export site` читает уже
нормализованные сессии из `.tesserae/harness_sessions/` и живые записи в
`.tesserae/sqlite.db`, но сам по себе не лезет неожиданно в приватные каталоги
транскриптов harness.

Импортированные записи сессий — локальные артефакты проекта. Просмотрите их
перед публикацией публичного сайта, особенно если транскрипты могут содержать
секреты, приватные пути, данные клиентов или невыпущенный код.

Текст хода копируется в имена и описания узлов, а они сериализуются в
`graph.json` и в каждую его проекцию — поэтому **домашние каталоги вырезаются на
входе**. `/Users/<name>` и `/home/<name>` никогда не попадают в граф, и это
важно, потому что путь — это те самые персональные данные, которые появляются
почти в каждом транскрипте, хотя никто этого не задумывал.

## Во что превращается ход сессии

На каждый *значимый* переход в сессии — вызов инструмента или содержательное
действие ассистента, а не болтовню — проход `Event`, не использующий LLM,
создаёт ровно один узел с `{turn_id, actor, action, краткое изменение
состояния}` и связывает последовательные события рёбрами `precedes`, так что
динамику сессии можно воспроизвести по порядку. Проход никогда не обращается к
модели, никогда не падает на плохом входе и байтово идемпотентен: каждый
созданный id, текст и `first_seen_at` выводятся из содержимого, поэтому
повторный запуск даёт те же узлы и рёбра.

**Результат инструмента — это ход.** Коды возврата и флаги ошибок переживают
загрузку и оседают на узле `Event`, так что граф отличает команду, которая
*упала*, от той, что просто была запущена. Раньше агент, читая собственную
историю, видел, что запускал `pytest`, и не имел понятия, прошли ли тесты, — а
это и есть разница между журналом и памятью.

### Ребро `recovers`

Из двух **наблюдённых** исходов одной сессии Tesserae выводит единственное
причинное ребро своего словаря: вызов инструмента, сообщивший об ошибке, и более
поздний вызов — тот же инструмент, то же семейство программ, тот же рабочий
каталог, тот же операнд, без единого наблюдённого успеха по этому операнду в
промежутке, — сообщивший об успехе. Успешный `Event` становится источником,
неудачный — целью; оба идентификатора ходов названы в свидетельстве, а
`metadata["basis"]` перечисляет каждое измерение, по которому два вызова должны
были совпасть.

В `CAUSAL_EDGE_TYPES` ровно один элемент, и это сделано намеренно. Обзор четырёх
ведущих систем памяти для агентов показал, что ни одна из них не выводит
причинное ребро: две выводят свою сильнейшую связь из совместной встречаемости,
одна принимает на веру открытый словарь реляционных меток от LLM без всякой
проверки, а у четвёртой рёбер нет вовсе. Провал, ради избежания которого эта
узость и существует, — выпустить `caused_by`, который на самом деле
`happened_near`: в графе их не различить, а неверный читается как доказательство.

Якорем служит **операнд**, а не команда: команды меняются в том, что не имеет
значения (флаги, порядок), тогда как повтор на самом деле повторяет действие над
конкретным объектом.

## Обнаружение и импорт локальных сессий

Из корня проекта:

```bash
tesserae sessions discover --import
```

Обнаружение сканирует локальные корни транскриптов Claude Code и Codex,
принадлежащие рабочему каталогу текущего проекта. Используйте `--root` для
сканирования конкретного каталога конфигурации и повторяйте `--harness`, чтобы
ограничить обнаружение:

```bash
tesserae sessions discover \
  --root ~/.claude \
  --root ~/.codex \
  --harness claude-code \
  --harness codex \
  --import
```

Без `--import` обнаружение печатает найденное, не записывая нормализованные
записи сессий.

## Прямой импорт нормализованного JSON

Если другой инструмент уже произвёл нормализованный JSON `HarnessSession`,
импортируйте один файл или список файлов:

```bash
tesserae sessions import path/to/session.json path/to/more-sessions.json
```

Каждый вход может содержать один объект сессии или список объектов сессий.

## Как записывается хранилище

Каждая запись в `.tesserae/harness_sessions/` несёт **производителя(`producer`)** — имортер, который её написал. `sessions discover --import` ставит печать `tesserae:discover`; `sessions import <path>` ставит печать `tesserae:import`. **Писатель может трогать только записи, которые он произвёл**: он удаляет только своё, и не будет перезаписывать запись другого производителя для того же сеанса — входящая запись пропускается и сообщается как `Left alone (written by another producer)`.

Это правило существует потому, что происхождение (provenance) — единственное, что действительно разделяет импортёры. Двое из них регулярно описывают *один и тот же* сеанс: локальное сканирование Tesserae создаёт обычную запись из транскрипта под `~/.claude`, а оркестратор экспортирует тот же сеанс с удостоверением агента, которое известно только ему. Оба выводят одно и то же имя файла из id сеанса, поэтому они конфликтуют. Ни местоположение транскрипта, ни имя harness не могут их различить — вот почему более ранние исправления с областью действия root для [#104](https://github.com/ca1773130n/Tesserae/issues/104) не сработали, и почему 0.28.6 всё ещё теряло такие записи двумя способами: удаляемые, когда сканирование больше не находит транскрипт, или молча перезаписываемые, когда находит.

Если вы пишете в это хранилище из своего инструмента, используйте `tesserae sessions import <file>` и ваши записи защищены с того момента. Ничего больше не требуется.

Область видимости сужается дальше как второй шлюз: запись удаляется только если её транскрипт тоже живёт под корнем, отсканированным этим запуском, и её harness был одним из отсканированных. Поэтому `--harness codex` оставляет записи claude-code в покое, даже если `~/.claude` был отсканирован.

### Несколько машин, делящих один каталог проекта

Каждая запись несёт ещё и **хост (`host`)** — машину, которая её собрала. **Хост удаляет только то, что собрал сам.**

Это по-настоящему отдельная ось от `producer`, и шлюзы выше её не заменяют. Когда несколько серверов запускают Claude Code и делят диск, они делят и `.tesserae` — но каждый видит только свои локальные транскрипты. Сканирование любого хоста ставит одну и ту же печать `tesserae:discover`, и `~/.claude` любого хоста разрешается в одну и ту же строку пути, так что шлюз производителя и шлюз области *оба проходят* на машине, которая транскрипт вообще не видела. Дальше она удаляет запись другой машины и рапортует об успехе. Теперь записи несут собравший их хост, и для удаления он обязан совпасть.

Идентификатор хоста живёт в `~/.tesserae/host_id` — свой на каждой машине, а не в общем каталоге проекта — и генерируется один раз при первом использовании. Переопределяется через `TESSERAE_HOST_ID`. Это сохранённый id, а не hostname, и намеренно: парк, собранный из одного образа, переиспользует hostname'ы, а их совпадение молча отдало бы записи одной машины другой.

Путь **записи** намеренно слеп к хосту. Два хоста могут записать один и тот же сеанс только если оба видят транскрипт, так что запись идемпотентна и просто перештамповывает владение на того, кто последним доказал, что видит его. Если бы записи шлюзовались по хосту, записи выведенной из эксплуатации машины замёрзли бы навсегда, и вернуть их было бы нечем.

Записи, написанные до появления этого поля, хоста не несут. По этой оси они бесхозные и переживают удаление любым хостом, пока их не заберёт `--adopt-unowned` — то же правило, что уже действует для `producer`. Здесь оно важно потому, что *каждая* запись, написанная 0.28.7, несёт производителя и не несёт хоста, так что шлюз производителя воздержится, а больше защитить их нечему.

Три поведения, стоящих того, чтобы их знать:

- **Записи, написанные до 0.28.7, не имеют производителя.** Они бесхозные, поэтому ни один импортер их не удаляет и не перезаписывает — безопасно, но обнаружение их тоже не обновляет. `sessions discover --import --adopt-unowned` требует их для обнаружения. Запустите один раз, если собственное сканирование Tesserae — единственное, что пишет в это хранилище; **не** запускайте, если другой инструмент тоже пишет здесь, так как это отдаст ваши записи обнаружению.
- Пустое обнаружение никогда не удаляет. Сканирование, которое ничего не находит — неправильный `HOME`, отсоединённые корни harness — объединяет вместо стирания.
- Обнаружение, которое удаляет или сохраняет записи, печатает оба счётчика рядом со счётчиком импорта, поэтому хранилище не может изменить размер в строке, которая только сообщает о росте.

## Список импортированных сессий

```bash
tesserae sessions list
```

Сессии хранятся ниже:

```text
.tesserae/harness_sessions/
  manifest.json
  <harness>/
    <session>.json
    <session>.md
```

Сессии живого мониторинга дополнительно отслеживаются в SQLite
`HarnessSessionsDB` (`.tesserae/sqlite.db`), которая также персистит
пофайловые смещения чтения, с которых возобновляется тейлер.
`tesserae sessions list` отображает объединённое представление.

## Сборка статических страниц сессий

После импорта сессий пересоберите сайт:

```bash
tesserae export site
```

Сайт эмитирует:

```text
.tesserae/site/sessions/index.html
.tesserae/site/sessions/<project>/<session>.html
```

Сгенерированный сайт ссылается на Sessions из глобального рейла, домашних
карточек Browse, записей поиска и хлебных крошек каждой детальной страницы
сессии.

## Быстрый поиск по транскриптам (memex)

Когда вы поднимаете сайт через `tesserae serve`, **дашборд сессий** получает
поле полнотекстового поиска по каждому проиндексированному транскрипту
Claude/Codex на базе [`nicosuave/memex`](https://github.com/nicosuave/memex)
(BM25). Результаты показывают `project · role · date · score` плюс совпадающий
сниппет.

```bash
cargo install --git https://github.com/nicosuave/memex --locked   # or: tesserae config deps --install memex
memex index                                                        # build the index once
tesserae serve                                                     # search box appears on /sessions
```

Он **опционален и деградирует мягко**: без бинарника `memex` (или индекса)
поле показывает понятное, действенное сообщение, а остальной дашборд не
затрагивается. Поисковый эндпоинт (`GET /api/transcript-search`) ограничен
same-origin/loopback-вызовами, так что посещённая веб-страница не может
прощупать вашу локальную историю.

## Раскладка детальной страницы сессии

Детальные страницы сессий используют общий каркас статического сайта, а не
автономный дамп транскрипта. Они включают:

- hero и полосу статистики;
- высокоуровневую сводку;
- таймлайн и метаданные размера;
- решения, файлы, команды, инструменты и ошибки, когда они есть;
- свёрнутое дерево субагентов;
- поход за ходом диалог user/assistant;
- свёрнутые блоки использования инструментов, прикреплённые под предыдущим
  ходом assistant;
- левый рейл диалога со ссылками на якоря `#turn-N`.

Markdown диалога рендерится через markdown-рендерер сайта. Семантические
поверхности — inline-код, явная разметка команд/тегов, пути, имена файлов и
хэштеги — оформляются как компактные чипы; случайные существительные с
заглавной буквы автоматически чипами не становятся.

Текущая типографика транскриптов:

| Поверхность | Селектор | Размер |
|---|---|---|
| Markdown-проза диалога | `.session-turn-text`, дочерние элементы прозы | `8px` |
| Обычные code-фенсы диалога | `.session-turn-text pre` | `10px` |
| Содержимое bash/shell-фенсов | `.session-code-block code.language-bash`, `.language-sh`, `.language-shell`, `.language-zsh` | `11px` |
| Details/summary инструментов | `.session-tool-details`, `.session-tool-details > summary` | `10px` |
| Заголовок tool-use | `.session-tool-use-header` | `8px` |
| Текст payload инструмента | `.session-tool-use-text` | `6px` |

## Чек-лист публикации для сессий

Перед развёртыванием публичного сайта, включающего сессии:

1. Запустите `tesserae sessions list` и убедитесь, что количество ожидаемое.
2. Просмотрите `.tesserae/harness_sessions/` на чувствительное содержимое.
3. Пересоберите с `tesserae export site`.
4. Откройте локально `sessions/index.html` и хотя бы одну детальную страницу
   сессии.
5. Убедитесь, что блоки инструментов свёрнуты по умолчанию и что сырые payload
   инструментов допустимо публиковать.
6. Разверните с `tesserae export site --deploy`, когда дерево исходников
   закоммичено.
