`tesserae doctor` проверяет рабочее пространство Tesserae от начала до конца —
инициализацию, целостность графа, согласованность реестра, свежесть,
блокировки, вход в LLM и гигиену диска — и печатает чек-лист. По умолчанию
команда **только читает**; `--fix` применяет лишь те исправления, которые
безопасно перезапускать и которые никогда не могут разрушить живое состояние.

```bash
tesserae doctor                 # check the current project
tesserae doctor --fix           # apply the safe repairs, then re-check
tesserae doctor --all --json    # every registered project, JSON report
tesserae doctor --project ~/src/other
```

## Что проверяется

Проверки, сгруппированные по категориям:

| Проверка | Категория | Что проверяет | Действие `--fix` |
|---|---|---|---|
| `project_initialized` | core | `.tesserae/` существует и выглядит как рабочее пространство Tesserae | только отчёт (предлагает `tesserae init`) |
| `graph_parse` | core | `graph.json` парсится и имеет ожидаемую форму | только отчёт (предлагает `tesserae compile`) |
| `config_valid` | core | `.tesserae/config.json` парсится и валиден относительно шаблона init | только отчёт |
| `vault_configured` | core | настроенный путь vault разрешается | **SAFE**: создаёт разрешённый каталог vault, если он находится внутри проекта |
| `registry_consistent` | registry | записи `~/.tesserae/registry.json` указывают на реальные корни проектов | **SAFE**: удаляет записи с исчезнувшим корнем, убирает устаревший ключ `active`; отсутствующий граф — только отчёт |
| `graph_staleness` | freshness | git-дельта с момента `git_head`, записанного при последней компиляции | только отчёт (предлагает `tesserae refresh` — компиляции тяжелы) |
| `site_search_index` | freshness | статический сайт / `search-index.json` новее, чем `graph.json` | **SAFE**: пересобирает сайт |
| `backend_artifacts` | freshness | артефакты RAG-Anything актуальны | только отчёт (их обновление тяжёлое по LLM/сети) |
| `session_chunks` | freshness | покрытие [дневных чанков сессий](session-chunks.ru.md) не имеет пропусков в недавнем окне | только отчёт (предлагает `tesserae sessions chunk-backfill`) |
| `wiki_lint` | graph | дрейф графа ⇄ wiki + тривиально исправимые находки линта | **SAFE**: применяет тривиальные исправления линта (`fix_trivial`) |
| `compile_lock` | processes | удерживается ли живая блокировка компиляции, и каким pid **и на каком хосте** | только отчёт — doctor **никогда не убивает процесс и не снимает живую блокировку** |
| `filesystem_locking` | processes | лежит ли `.tesserae/` на сетевой файловой системе, где `flock(2)` может молча оказаться no-op | только отчёт (доказать межхостовое соблюдение блокировок он не может — см. ниже) |
| `daemon_pid` | processes | `daemon.<host>.pid` указывает на живой процесс движка | **SAFE**: удаляет pid-файл **этого хоста**, если его владелец мёртв; о чужом только сообщает и никогда его не трогает |
| `llm_login` | environment | существуют ли каталоги конфигурации, которые проект реально стал бы использовать | только отчёт — **учётные данные не проверяются** (см. ниже) |
| `optional_deps` | environment | статус опциональных зависимостей (memex, raganything) | только отчёт (установки требуют сети) |
| `embedding_backend` | environment | доступен настоящий семантический бэкенд эмбеддингов | только отчёт (предлагает `pip install tesserae[semantic]`) |
| `environment` | environment | сводка полной диагностики окружения | секция только-отчёт |
| `build_history` | hygiene | размер и форма `.build-history` | **SAFE**: обрезает её, всегда сохраняя самую свежую запись `git_head` (от неё зависит проверка staleness) |
| `idempotence` | hygiene | «растяжка» `idempotence_suspect` в output-snapshot | только отчёт (это сигнал о баге, а не то, что нужно автопочинить) |
| `orphan_worktrees` | hygiene | устаревшие регистрации `git worktree` | **SAFE**: `git worktree prune`; удаление каталогов — только отчёт |
| `hook_log_bloat` | hygiene | рост `.tesserae/.session-*-hook.log` | **SAFE**: ротирует/усечает логи больше 10 МБ |
| `sidecars` | hygiene | записи `.tesserae/` против реестра сайдкаров ([`tesserae/sidecars.py`](sidecars.ru.md)): осиротевшие `*.tmp.<pid>.<hex>`, ручные копии `graph.json.bak-*`, неклассифицированные записи | **SAFE**: удаляет только осиротевшие tmp-файлы, чей процесс-писатель мёртв и которым больше 24 ч; резервные копии и неклассифицированное — только отчёт |
| `code_scope_leftovers` | hygiene | остатки выведенного из области кода слоя: `code-graph*.json`, строки кодовых типов в `sqlite.db` | только отчёт — очистка это массовое удаление, поэтому она вынесена в отдельную команду (см. ниже) |

Упавшая проверка сообщается как находка-ошибка — сам doctor никогда не бросает
исключение.

## О чём `llm_login` говорит, а о чём нет

Он сообщает, что каталог конфигурации существует. Он **не** сообщает, что CLI
внутри него держит валидный токен, и прямо пишет об этом в тексте собственной
находки.

Это различие — не занудство. Раньше проверка рапортовала `credentialed LLM CLI:
claude, codex` на основании файлов вроде `~/.claude/history.jsonl` — а они
доказывают, что CLI *использовали*, а не что он может аутентифицироваться
*сейчас*. Запущенные подряд в одну и ту же секунду, `tesserae compile` печатал
`Claude CLI not logged in (tried 1 config dir)`, а doctor печатал зелёную
галочку. Диагностика, противоречащая сбою, в котором вы прямо сейчас стоите,
хуже, чем отсутствие диагностики.

Проверить учётные данные — значит тратить настоящий вызов LLM на каждый
`tesserae doctor`, а такую цену эта проверка по собственной инициативе на себя
не берёт. Поэтому она сообщает только то, что действительно проверила.
Авторитетный ответ даёт `tesserae compile`.

Проверка ограничена теми каталогами, которые проект реально попробовал бы,
разрешёнными через тот же путь, что использует `ProjectWiki._build_json_client`,
— и она ничего не говорит про каталоги конфигурации claude, если провайдер
проекта — `codex`.

## Общие диски и `flock(2)`

Все гарантии конкурентности в Tesserae — и блокировка компиляции прежде всего —
держатся на том, что `flock(2)` соблюдается файловой системой, на которой лежит
`.tesserae/`. На NFS и SMB это зависит от конфигурации: без работающего
lock-демона `flock` может молча выродиться в no-op, и тогда два хоста будут
компилировать один и тот же проект одновременно, каждый в уверенности, что
держит эксклюзивную блокировку.

`filesystem_locking` сообщает то, что способен определить один хост: тип
файловой системы под проектом, является ли она сетевой и удаётся ли вообще взять
`flock`. На сетевой файловой системе он выдаёт предупреждение.

Доказать межхостовое соблюдение блокировок он **не может** — и не претендует на
это. То, что блокировку взял один хост, ничего не говорит о том, будет ли отказано
второму. Если вы запускаете Tesserae с нескольких машин против общего хранилища,
проверьте это напрямую на реальном железе, прежде чем полагаться на блокировку
компиляции.

`filesystem_locking` — это проба только `flock` и сообщает "unsupported on this
platform — skipped" на Windows. Сами блокировки не такие: `compile.lock`
и оверлей записи агента используют `flock(2)`, где она существует, и `msvcrt.locking`,
где нет, а проверка `compile_lock` зондирует этими же двумя помощниками,
поэтому она не может сообщить "unsupported" о блокировке, которая работает там. На
интерпретаторе, не носящем ни один из примитивов, блокировка деградирует в no-op,
который говорит об этом один раз за процесс, а не молчаливо.

## `tesserae doctor migrate-code-scope`

Разовая очистка рабочего пространства, скомпилированного до того, как исходный код
вышел из области Tesserae. Новые компиляции больше не создают слой кода, но старое
рабочее пространство всё ещё несёт его, и большая часть этого убирается только по
явной просьбе.

```bash
tesserae doctor migrate-code-scope            # пробный прогон — отчёт, ничего не удаляет
tesserae doctor migrate-code-scope --apply    # действительно удаляет
```

Удаляет в таком порядке:

* спроецированные страницы в `.tesserae/markdown_projection/`, чей собственный
  frontmatter `type:` называет выведенный из обращения тип кода;
* те же страницы в хранилище Obsidian — и в настроенном, и во внутрипроектном
  умолчании, потому что проект, позже нацеленный на настоящее хранилище, оставляет
  старое как есть, полным таких страниц. Страница кода с непустым содержимым
  `user-notes` сохраняется и подсчитывается, но никогда не удаляется;
* `code-graph.json` и `code-graph-cache.json`;
* строки sidecar-таблиц SQLite (`node_provenance`, `edge_provenance`,
  `node_memory`), чей узел или ребро больше не существует, затем `VACUUM`.

Две вещи, которые стоит знать.

**Читайте число выживших, а не число удалённых.** Каталог проекции подавляюще
производен от кода — здесь измерено 218 796 из 224 876 страниц — поэтому ошибка
предиката, удаляющая всё, и корректный прогон по числу удалённых почти неотличимы.
Отчёт первым делом сообщает, сколько некодовых страниц выжило: именно это число
рухнуло бы при неверном предикате. Решение принимается строго по каждому файлу, по
его собственному frontmatter.

**Сначала компиляция, потом миграция.** Таблицы `nodes` / `edges` и sidecar-и
provenance переписываются каждой компиляцией, так что именно компиляция превращает
эти строки в мусор; эта команда возвращает место, потому что SQLite не уменьшается
от `DELETE`. Запустить её раньше безвредно — она скажет об этом и сообщит, что
возвращать нечего. `VACUUM` никогда не выполняется внутри компиляции: он берёт
исключительную блокировку и требует свободного места порядка размера файла базы, и
пропускается с пометкой, когда диск не выдержит перестройку.

Она намеренно недоступна из `--fix`, который задокументирован как только безопасные
починки.

## Политика `--fix`

- `--fix` запускает **только** проверки, помеченные выше как SAFE, а затем
  выполняет повторную диагностику, чтобы отчёт отражал состояние после
  исправлений.
- Каждое исправление идемпотентно: двойной запуск `doctor --fix` оставляет
  второй прогон чистым.
- Doctor **никогда не убивает процесс и никогда не снимает живую блокировку
  компиляции** — удерживаемая блокировка сообщается с pid и хостом владельца и
  не трогается.
- Doctor **никогда не трогает pid-файл чужой машины.** На общем хранилище
  локальная таблица процессов ничего не говорит о pid, записанном другим хостом,
  поэтому `daemon.<other-host>.pid` безусловно сообщается и пропускается — его
  даже не читают на предмет живости. Удалён может быть только собственный
  pid-файл этого хоста.
- Тяжёлые или сетевые операции (перекомпиляции, установка зависимостей,
  обновление бэкендов) никогда не включаются в `--fix`; doctor печатает
  команду, которую вы должны запустить сами.

## Коды выхода

Та же конвенция, что у `tesserae lint`:

| Код выхода | Значение |
|---|---|
| `0` | здорово — нет находок выше OK |
| `1` | есть предупреждения |
| `2` | есть ошибки |

## `tesserae lint` — коды находок

`doctor` выполняет лишь тривиально исправимое подмножество линта; весь набор
запускает `tesserae lint`, и подробности живут здесь. У каждой находки есть
устойчивый код, так что отчёт можно грепать, а CI — гейтить по одному из них.
`--severity {info,warning,error}` задаёт порог для **кода выхода** — находки
ниже него всё равно попадают в отчёт.

| Код | Уровень | Что означает |
|---|---|---|
| `AGENT_METADATA_KEY` | error | Узел агента несёт ключ метаданных вне контролируемого набора. Единственный код уровня error; некорректный агент ломает области видимости. |
| `AGENT_WRITE_SKIPPED` | warning | Строка в `.tesserae/agent-writes.jsonl`, которую повторное воспроизведение пропустило — эта запись **не** в графе. Урезанная строка — разорванный конкурентный append, и агент должен её переподать; отредактированная вручную должна быть исправлена или удалена. Повторное воспроизведение пропускает с предупреждением, а не падает, так что одна плохая строка никогда не сломает каждую будущую компиляцию — но строка stderr во время компиляции — не то место, где ты ищешь запись, которую агент считает поданной. |
| `ORPHAN_PAPER` | warning | Paper без исходящих рёбер и только с `mentioned_in` на входе — загружен, но так и не связан. |
| `MISSING_IMPLEMENTED_IN` | warning | Paper и Repository делят `arxiv_id`, но их не соединяет ребро `implemented_in`. `--fix-trivial` его добавит. |
| `STALE_CITATION` | warning | Вики-страница ссылается на несуществующую страницу. |
| `DANGLING_HTML_LINK` | warning | Сгенерированный HTML указывает на отсутствующий файл. |
| `GRAPH_WIKI_DRIFT` | warning | Граф и вики разошлись — публичный узел без страницы или страница без узла. |
| `CONTRADICTING_CLAIMS` | warning · info | Два утверждения противоречили друг другу; сообщается, как это разрешилось. |
| `REASONING_EDGE_RATIO` | warning | Слишком мало рёбер несут рассуждение. Граф из голых `mentions` — это поисковый индекс, а не база знаний. |
| `SYNTHESIS_GHOST_INPUT` | warning | Frontmatter синтеза ссылается на id узла, которого больше нет. `--fix-trivial` его вычистит. |
| `AGENT_FORGET_LEDGER` | warning | Последняя дистилляция понизила часть находок — журнал того, что агент перестал показывать. |
| `INTERVAL_COVERAGE` | info | *Сколько фактов не имеют `valid_from`* и потому сортируются последними в любом временном ответе. Раньше это молчало, теперь называется в процентах. |
| `LINT_PROBE_FAILED` | info | `INTERVAL_COVERAGE` не смог отработать, потому что граф не загрузился — проверка воздержалась, и об этом сказано вслух, а не зачтено как успех. |
| `PROCEDURAL_POOLS` | info | Насколько на самом деле создан процедурный слой, принадлежащий производителям. Зарезервированное процедурное место в выдаче зарабатывается происхождением; этот код сообщает, когда его нечем честно заполнить. |
| `AGENT_UNDISTILLED_BACKLOG` | info | У агента накопились находки далеко за его отметкой дистилляции. |
| `LOW_TITLE_QUALITY` | info | Заголовок Paper похож на имя файла или обрывок, а не на название. |
| `SUGGESTED_MERGE` | info | Несколько узлов Repository делят один `github_repo` — кандидаты на слияние, но автоматически они не сливаются. |
| `SUGGESTED_SUBTYPE` | info | Кластер узлов одного типа, для которого schema-drift предложил подтип — выявлен, но никогда не применён автоматически. Продвижение — это ручное редактирование `ResearchNodeType`, затем `"approved": true` в `.tesserae/schema-drift-proposals.json`. |
| `PENDING_REVIEW` | info | Пары-кандидаты на слияние, всё ещё ожидающие человеческого вердикта в `.tesserae/candidate-same-as.json`. Пара, отклонённая рецензентом, больше никогда не выводится, поэтому это число — незакрытая работа, а не размер корпуса. Ответить можно через `tesserae extract --apply-review-decisions … --reviewed-by <вы>`. |
| `STALE_BUILD_HISTORY` | info | Запись истории сборок старше 90 дней. |
| `CODE_GRAPH_BEHIND` · `CODE_GRAPH_HEAD_UNRESOLVED` · `CODE_GRAPH_STALE_FILE` | info | Опциональный слой кода разошёлся с `HEAD` — собран на более старом коммите, на коммите, который git уже не разрешает, или по файлам, изменившимся с тех пор. |
| `CLAIM_SUPPORT_SKIPPED` · `CLAIM_SUPPORT_SUMMARY` | info | Результаты опционального прохода `--verify-claims`: что было выбрано и как оценено, либо почему он не запускался. |

`--fix-trivial` применяет только безопасные починки (`MISSING_IMPLEMENTED_IN`,
`SYNTHESIS_GHOST_INPUT`). Всё остальное лишь сообщается, чтобы решал человек.
`--verify-claims` включается явно, требует LLM-бэкенда и стоит одного пакетного
вызова.

## Артефакты отчёта

Каждый запуск записывает обе формы отчёта в рабочее пространство:

```text
.tesserae/doctor-report.md      # human checklist
.tesserae/doctor-report.json    # structured findings
```

`--json` дополнительно печатает JSON-отчёт в stdout вместо markdown-чек-листа.
`--all` перебирает каждый проект из реестра (игнорируя `--project`) и
отчитывается по каждому проекту.

## MCP: `doctor_report`

MCP-сервер выставляет тот же отчёт как инструмент `doctor_report` (зеркально
`lint_report`, включая его байтовый лимит на возвращаемое содержимое), чтобы
агент мог проверить здоровье рабочего пространства посреди диалога без выхода
в шелл. Ему нужен корень проекта — передайте `graph_path`/`project` или
настройте граф по умолчанию.
