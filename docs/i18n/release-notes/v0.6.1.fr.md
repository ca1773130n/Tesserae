Date de publication **2026-06-08** · [PyPI](https://pypi.org/project/tesserae/0.6.1/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.6.1) · `pip install --upgrade tesserae==0.6.1`

Une petite suite à la [refonte de la CLI de la v0.6.0](v0.6.0.md) : deux améliorations de confort pour la nouvelle CLI à verbes plats et une véritable correction de bogue pour les utilisateurs de codex disposant de plusieurs comptes.

## 1. `tesserae compile` affiche désormais la progression en direct

Une compilation longue restait auparavant silencieuse. Elle affiche maintenant un indicateur de progression multiphase, dans le style de `codegraph index`, sur un terminal interactif :

```
◆ Scanning sources — 2036 found
  Extracting ████████████████░░░░░░░░  64%  1302/2036  0:12
◆ Extracted 2036 files
⠙ Finalizing — community summaries, vault, site…
◆ Compiled  ·  220243 nodes · 679073 edges  ·  41s
```

Il s'appuie sur `rich` (déjà une dépendance) et ne s'affiche que sur un TTY — les exécutions via un tube, en CI, sur le serveur MCP et en démon restent identiques octet pour octet (la ligne de résumé simple `Compiled project wiki: …` est conservée), donc rien ne change pour les scripts.

## 2. `tesserae projects register` s'initialise automatiquement

Enregistrer un répertoire qui n'était pas encore un projet Tesserae échouait avec `No .tesserae/graph.json found`. Désormais, si le chemin est un répertoire existant dépourvu d'espace de travail `.tesserae/`, register en crée d'abord un vide (puis affiche une indication pour exécuter `tesserae compile`). Un chemin inexistant ou mal saisi reste une erreur — il n'est jamais créé automatiquement — et un projet déjà initialisé est laissé intact.

## 3. Correction : `llm_provider: codex` est désormais respecté par chaque passe LLM

Si vous aviez sélectionné codex (via `tesserae config llm --llm-provider codex` ou le `config.json` du projet), plusieurs passes LLM au moment de la compilation utilisaient malgré tout la CLI de Claude — produisant `ClaudeCLIJsonClient … You've hit your Sonnet limit` alors même que vous aviez choisi codex. La cause : la passe de résumés de communautés, les passes de mémoire de la Phase 5 et les commandes `lab schema-drift` / `lab evolve` / `query --llm` construisaient leur client LLM sans consulter le réglage du fournisseur, et se rabattaient donc toujours sur Claude par défaut. Toutes résolvent désormais le backend de la même manière que le reste du moteur — **variable d'environnement > `config.json` du projet > `~/.tesserae/config.json` global > valeur par défaut** — de sorte que `llm_provider: codex` est respecté partout.

## Mise à niveau depuis la v0.6.0

Rien à changer — les trois sont prêtes à l'emploi. Si vous aviez précédemment défini `llm_provider: codex` et que vous voyiez quand même Claude être appelé pendant la compilation, cette version corrige cela ; il suffit de relancer `tesserae compile`.
