Fecha de publicación **2026-06-08** · [PyPI](https://pypi.org/project/tesserae/0.6.1/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.6.1) · `pip install --upgrade tesserae==0.6.1`

Un pequeño seguimiento del [rediseño de la CLI en v0.6.0](v0.6.0.es.md): dos mejoras de comodidad para la nueva CLI de verbos planos y una corrección real de un error para los usuarios de codex con varias cuentas.

## 1. `tesserae compile` ahora muestra el progreso en vivo

Una compilación larga solía permanecer en silencio. Ahora muestra una visualización de progreso de varias fases, al estilo de `codegraph index`, en una terminal interactiva:

```
◆ Scanning sources — 2036 found
  Extracting ████████████████░░░░░░░░  64%  1302/2036  0:12
◆ Extracted 2036 files
⠙ Finalizing — community summaries, vault, site…
◆ Compiled  ·  220243 nodes · 679073 edges  ·  41s
```

Está impulsado por `rich` (que ya es una dependencia) y solo se muestra en una TTY: las ejecuciones canalizadas, en CI, en el servidor MCP y en el demonio permanecen idénticas byte a byte (se conserva la línea de resumen sencilla `Compiled project wiki: …`), por lo que nada cambia para los scripts.

## 2. `tesserae projects register` se inicializa automáticamente

Registrar un directorio que aún no era un proyecto Tesserae fallaba con `No .tesserae/graph.json found`. Ahora, si la ruta es un directorio existente sin un espacio de trabajo `.tesserae/`, register crea primero uno vacío (y luego imprime una sugerencia para ejecutar `tesserae compile`). Una ruta inexistente o mal escrita sigue siendo un error —nunca se crea automáticamente— y un proyecto ya inicializado se deja intacto.

## 3. Corrección: `llm_provider: codex` ahora es respetado por cada pasada de LLM

Si seleccionabas codex (mediante `tesserae config llm --llm-provider codex` o el `config.json` del proyecto), varias pasadas de LLM en tiempo de compilación seguían usando la CLI de Claude de todos modos, produciendo `ClaudeCLIJsonClient … You've hit your Sonnet limit` aunque hubieras elegido codex. La causa: la pasada de resúmenes de comunidad, las pasadas de memoria de la Fase 5 y los comandos `lab schema-drift` / `lab evolve` / `query --llm` construían su cliente de LLM sin consultar la configuración del proveedor, por lo que siempre recurrían a Claude por defecto. Ahora todos ellos resuelven el backend de la misma manera que el resto del motor —**variable de entorno > `config.json` del proyecto > `~/.tesserae/config.json` global > valor por defecto**—, de modo que `llm_provider: codex` se respeta en todas partes.

## Actualizar desde v0.6.0

No hay nada que cambiar: las tres son de incorporación directa. Si anteriormente habías configurado `llm_provider: codex` y aun así veías que se llamaba a Claude durante la compilación, esta versión lo corrige; simplemente ejecuta `tesserae compile` de nuevo.
