发布于 **2026-09-04** · [PyPI](https://pypi.org/project/tesserae/0.38.0/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.38.0) · `pip install --upgrade tesserae==0.38.0`

`node_provenance` 只回答哪些文档提到了某个实体，到此为止。一个在 30 篇论文中出现过
的节点会交回 30 篇看上去毫无差别的文档，而真正展开讲这个实体的那一篇就在其中某处。

## 发生了什么

2026-09-02 在两个语料库上测得：provenance 集合有 55-64% 的时候确实包含那篇展开讲
的文档，但对该集合排序后把它排到前面的只有 10-15%。集合是对的，顺序是抛硬币，因为
从边车看过去，里面每篇文档都长得一样。

## 改了什么

- **一个派生的 `node_mentions` 边车** — `(node_id, source_path, mentions)`。一个
  编译期流程会按词边界，统计每个节点的名称及其别名在其 provenance 所指的每篇文档
  中出现的次数。
- **`SqliteGraphStore.node_documents` 按提及次数从多到少返回
  这些文档。** 该读取由
  `node_provenance` 驱动并 LEFT JOIN 计数，因此两个边车不会彼此漂移：没有计数的
  文档仍会出现，计为 0。
- **是一张独立的表，而不是一个列。** 已有的 `sqlite.db` 无需迁移，provenance 的
  字节稳定性也未被触动。
- **名称与别名重叠的区间会被合并**，因此 `BERT-base` 只计一次而不是两次。
- **只有在语料库正文还在手上时才能统计这个次数**，所以它发生在编译期。下游没有任何
  东西能从图谱里把它重建出来。

实测开销：148 篇全文论文的 43,151 对用时 31.5 秒，1,552 篇摘要的 27,669 对用时
5.2 秒，而编译本身是以小时计的。

## 目前还没有做的事

已发布的检索路径里没有任何地方按这些计数排序。`node_documents` 是一个你可以调用的
API；打包器仍然按节点首次出现的位置来排列该节点的文档。在促成这项工作的基准上，
mention density 在两个语料库上分别以 0.92 和 0.85 的比例挑中了归属文档，而已发布
的规则是 0.52 和 0.55。把它接进去是以后的版本，不是这一版。

## 升级

没有需要迁移的东西。这张表会在下一次 `tesserae compile` 时出现，计数也一并出现。在
你重新编译之前，`node_documents` 会按路径顺序返回 provenance 集合，每个计数都是 0
—— 还是你原本拥有的那些文档，不会更差。
