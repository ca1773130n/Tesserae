Veröffentlicht am **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [GitHub-Release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

Ein benutzerdefinierter LLM-Anbieter ließ sich nicht konfigurieren – aus drei unabhängigen Gründen –, und das Symptom war jedes Mal ein Fehler zu einem Modell, das du nie konfiguriert hast. Ein Audit des Anbieter-Codes bestätigte 23 Mängel; dieses Release behebt sie.

## Das Wire-Protokoll wurde nie modelliert

`llm_provider` vermischte *welches Backend* mit *welche HTTP-Variante*, und `custom` erstellte immer den Anthropic-Client, der an `{base}/v1/messages` POSTet. Jeder OpenAI-kompatible Server – vLLM, LiteLLM, OpenRouter, Together, Ollama, LM Studio – antwortet darauf mit 404. Die einzige Klasse, die `chat/completions` spricht, wurde von keinem Code-Pfad erstellt und `api.openai.com` war hardcodiert, daher konnte sie deinen Endpunkt auch nicht bedienen.

`llm_api_style` nennt jetzt das Wire-Protokoll und ist das einzige, das den Client auswählt. Ungesetzt bleibt es `anthropic` für `custom`, daher verhält sich eine vorhandene Custom-Konfiguration genau wie zuvor.

```bash
# ein OpenAI-kompatibler Endpunkt (vLLM, LiteLLM, OpenRouter, Ollama, LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# ein anthropic-kompatibler Endpunkt – kein /v1, das SDK hängt es an
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## Das Modell wurde gelöscht, und etwas anderes antwortete

Das konfigurierte `llm_model` war an die Config- *Ebene* gebunden, die `llm_provider` lieferte – stellte den Anbieter über ein Flag und das Modell in einer Config-Datei ein, und dein Modell wurde für einen hardcodierten Standard verworfen. Der benutzerdefinierte Endpunkt fiel dann zum Claude CLI durch, das mit `--model sonnet` gegen deine eigene base URL aufgerufen wurde und ein nicht unterstütztes Modell meldete. Nichts benannte die echte Ursache.

Ein explizit konfigurierter **Endpunkt**-Anbieter (`anthropic`, `openai`, `custom`) ist jetzt ein Vertrag: er wird allein erstellt, und ein Fehler wirft einen Fehler auf, der den Anbieter, das Wire-Protokoll, die base URL, das Modell und welche Anmeldedaten-Art verwendet wurde, benennt. `llm_allow_fallback: true` stellt die alte Verkettung wieder her. Die beiden OAuth CLIs fallen immer noch aufeinander zurück, da keine ein Endpunkt von dir trägt.

## Es gab keine Bearer-Anmeldedaten

Ein einzelnes `llm_api_key` wurde vom SDK als `X-Api-Key` und von der CLI als Bearer-Token versendet, und es an das SDK zu übergeben unterdrückte des SDK eigene auth-token-Auflösung – daher war ein Gateway, das `Authorization: Bearer` wollte, unerreichbar. `llm_auth_token` ist die Bearer-Anmeldedaten, auf beiden Wires.

## Konfiguration, die du sehen kannst

Eine Rangfolge für jeden Schlüssel: `TESSERAE_LLM_*` Umgebung → Projekt `.tesserae/config.json` → `~/.tesserae/config.json` → Standard, mit den veralteten `ANTHROPIC_*` Variablen eine Stufe tiefer. Der Resolver zeichnet auf, welche Ebene jeden Schlüssel gewonnen hat, und `tesserae config status` gibt das aus – es pflegte zu raten und schrieb dem Resolver eine Umgebungsvariable zu, die dieser absichtlich ignoriert. Status zeigt auch das Wire-Protokoll, die Anmeldedaten-Art und den Client, der seine Probe bediente.

`ask`, `query`, lint, die MCP-Zusammenfassungen und der Engine-Daemon lösten nur gegen die Umgebung und die globale Konfiguration auf, daher wurde ein Endpunkt auf Projektebene von `compile` geehrt und überall sonst stillschweigend ignoriert. Sie lesen jetzt alle das Projekt.

## Auch

- Ein ungültiger `llm_provider` wird gemeldet, statt stillschweigend `claude` zu werden.
- Anthropic base URLs werden normalisiert, was das verdoppelte `/v1/v1/messages` behebt, das die Schnellstartanleitung dieses Projekts dokumentiert hat.
- `401`/`403` werden als Authentifizierungsfehler und `404`/model-not-found als Endpunktfehler klassifiziert, statt alle als „unavailable" gemeldet zu werden.
- `init` und `setup` persistieren die neuen Schlüssel; sie pflegten sie zu akzeptieren und zu verwerfen.

## Upgrade

Nichts zu migrieren. Zwei sichtbare Änderungen: ein expliziter Endpunkt-Anbieter fällt nicht mehr auf ein anderes Backend zurück, und `config status` gibt die Anmeldedaten- *Art* statt `set`/`unset` aus.
