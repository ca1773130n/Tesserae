Publié le **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [Version GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

La configuration d'un fournisseur LLM personnalisé ne fonctionnait pas, pour trois
raisons indépendantes, et le symptôme était à chaque fois une erreur sur un modèle
que vous n'aviez jamais configuré. Un audit du code du fournisseur a confirmé 23
défauts ; cette version les corrige.

## Le protocole de câblage n'a jamais été modélisé

`llm_provider` confondait *quel backend* avec *quel dialecte HTTP*, et `custom`
construisait toujours le client Anthropic, qui envoie des requêtes à
`{base}/v1/messages`. Tous les serveurs compatibles OpenAI — vLLM, LiteLLM,
OpenRouter, Together, Ollama, LM Studio — répondent 404 à cela. La seule classe qui
parle `chat/completions` n'était construite par aucun chemin de code et codait en dur
`api.openai.com`, donc elle ne pouvait pas servir non plus votre point de terminaison.

`llm_api_style` désigne maintenant le câblage et est la seule chose qui choisit le
client. Laissé non défini, il reste `anthropic` pour `custom`, donc une configuration
personnalisée existante se comporte exactement comme avant.

```bash
# un point de terminaison compatible OpenAI (vLLM, LiteLLM, OpenRouter, Ollama, LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# un point de terminaison compatible Anthropic — pas de /v1, le SDK l'ajoute
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## Le modèle a été supprimé, et quelque chose d'autre a répondu

Le `llm_model` configuré était limité au *niveau* de configuration qui fournissait
`llm_provider` — définissez le fournisseur par drapeau et le modèle dans un fichier
de configuration, et votre modèle était jeté en faveur d'une valeur par défaut codée
en dur. Le point de terminaison personnalisé tombait ensuite en cascade vers Claude
CLI, qui était lancé avec `--model sonnet` contre votre propre URL de base et
signalait un modèle non pris en charge. Rien ne nommait la cause réelle.

Un fournisseur **point de terminaison** explicitement configuré (`anthropic`, `openai`,
`custom`) est maintenant un contrat : il est construit seul, et une défaillance lève
une erreur nommant le fournisseur, le câblage, l'URL de base, le modèle et quel type
d'identifiant a été utilisé. `llm_allow_fallback: true` restaure le chaînage ancien.
Les deux CLI OAuth s'entrelacent toujours l'un l'autre, puisque ni l'un ni l'autre ne
porte un point de terminaison du vôtre.

## Il n'y avait pas d'identifiant porteur

Un seul `llm_api_key` était envoyé comme `X-Api-Key` par le SDK et comme jeton porteur
par la CLI, et le transmettre au SDK supprimait la résolution propre du jeton auth du
SDK — donc une passerelle voulant `Authorization: Bearer` était inaccessible.
`llm_auth_token` est l'identifiant porteur, sur les deux câblages.

## Configuration que vous pouvez voir

Une précédence pour chaque clé : `TESSERAE_LLM_*` environnement → projet
`.tesserae/config.json` → `~/.tesserae/config.json` → défaut, avec les variables
héritées `ANTHROPIC_*` un cran plus bas. Le résolveur enregistre quel niveau a remporté
chaque clé et `tesserae config status` l'imprime — il avait l'habitude de deviner, et
d'attribuer une variable d'environnement que le résolveur ignore délibérément. Le
statut affiche aussi le câblage, le type d'identifiant, et le client qui a servi sa
sonde.

`ask`, `query`, lint, les résumés MCP et le daemon du moteur se résolvaient contre
l'environnement et la configuration globale uniquement, donc un point de terminaison
au niveau du projet était respecté par `compile` et silencieusement ignoré partout
ailleurs. Ils lisent tous le projet maintenant.

## Aussi

- Un `llm_provider` invalide est signalé au lieu de devenir silencieusement `claude`.
- Les URL de base Anthropic sont normalisées, corrigeant le `/v1/v1/messages` doublé
  que le quickstart de ce projet lui-même documentait.
- `401`/`403` sont classés comme des défaillances d'authentification et `404`/modèle
  non trouvé comme des défaillances de point de terminaison, plutôt que tous d'être
  signalés comme « indisponible ».
- `init` et `setup` persistent les nouvelles clés ; ils avaient l'habitude de les
  accepter et les rejeter.

## Mise à niveau

Rien à migrer. Deux changements visibles : un fournisseur de point de terminaison
explicite ne retombe plus en cascade vers un backend différent, et `config status`
imprime le *type* d'identifiant plutôt que `set`/`unset`.
