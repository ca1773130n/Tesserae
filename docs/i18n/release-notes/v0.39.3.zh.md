发布于 **2026-09-08** · [PyPI](https://pypi.org/project/tesserae/0.39.3/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.3) · `pip install --upgrade tesserae==0.39.3`

明明登录了两个 Claude 账户，却被告知去运行 `claude /login`。其中一个账户配额已耗尽，而它是这次运行唯一被允许尝试的账户。

## 发生了什么

配置好的账户列表被当成了一堵墙。在 `llm_claude_config_dirs` 里——或者在旧版 `init` 写下的单数 `extraction.claude_config_dir` 里——指定一个目录，那个目录就是轮换的全部。当它的周配额耗尽时，那个专为熬过账户耗尽而存在的机制无处可去，于是编译降级为确定性抽取，而同一台机器上一个健康的账户正闲着。

到了第二台机器，这就变成了登录提示。账户列表保存的是绝对路径，而绝对路径不会迁移：CLI 收到一个磁盘上没有的配置目录，回答 `Not logged in`，于是打印出来的解决办法是用户早已做过的登录。

两个诊断都没抓住它。`doctor` 因为目录存在而报告 `[ok] llm_login`，而这正是它检查的全部。`tesserae test` 报告 “Backend is answering”，因为 provider 链已经悄悄落到了 codex——这是真的，但不是在问的那个问题。

## 有哪些变化

- **配置好的列表优先被尝试，而非排他。** 机器上其他所有已授权的 `~/.claude*` / `~/.codex*` 都会追加在它后面。只要你指定的账户中还有一个能用，被消耗的仍然只有它们——客户端在第一次成功时就返回——而这条尾链只有在每个指定账户都被证实是死路之后才会被触及。`llm_claude_config_dirs_exclusive` 和 `llm_codex_homes_exclusive` 为那些认为动用未指定账户是账单问题而非救援的人恢复旧行为。
- **过期的 OAuth 会话就是认证失败。** 判别子串只有 `not logged in` 一个，因此 MAX 账户刷新令牌失效时呈现的形态——`Failed to authenticate: OAuth session expired and could not be refreshed`——落入了通用错误路径，得到的是“去读错误”，而不是唯一能修好它的那条命令。
- **`tesserae test` 会点名它尝试过的每个账户。** 两个 CLI 客户端现在都会为轮换派生的每个账户记录一行，不增加任何开销，命令把它们打印出来：配置目录、发生了什么，以及 CLI 自己的原话。它还附上每种结果应得的解决办法，指出不在本机上的配置目录，并在你配置的 provider 已死而由回退作答时报告 **degraded** 判定。
- **`doctor` 不再在这件事上一路绿灯。** 不在本机上的已配置目录是一个警告，`doctor --fix` 会把它从 `config.json` 中删除——不存在的目录无法被登录，所以删除它不可能让你损失一个账号。被排除在轮换之外的已授权账户也会被点名。doctor 仍然不花费任何 LLM 调用；这两件事是它可以免费判定的。

## 用法

```bash
tesserae test          # which account answered, and what the others said
tesserae doctor --fix  # drops account dirs that are not on this machine
```

## 升级

没有需要迁移的东西，也不需要改动配置就能拿到这个修复。如果你原本依赖配置列表的排他性——固定一个账户，使其他账户永不被计费——请设置 `"llm_claude_config_dirs_exclusive": true`（或 `llm_codex_homes_exclusive`）来保留它。
