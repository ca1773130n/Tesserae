リリース **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

カスタム LLM プロバイダの設定は互いに無関係な3つの理由により機能せず、その度に症状は設定したことのないモデルについてのエラーだった。プロバイダコードの監査で23個の欠陥が確認され、このリリースがそれらを修正する。

## ワイヤプロトコルはモデル化されたことがない

`llm_provider` は *どのバックエンド* と *どの HTTP 方言* を混同しており、`custom` は常に `{base}/v1/messages` に POST する Anthropic クライアントを構築した。vLLM、LiteLLM、OpenRouter、Together、Ollama、LM Studio などの OpenAI 互換サーバはすべてここに 404 で応答する。`chat/completions` を話す唯一のクラスはどのコードパスからも構築されず、`api.openai.com` をハードコードしていたため、それもあなたのエンドポイントを処理することはできなかった。

`llm_api_style` が今、ワイヤを指名し、クライアントを選ぶ唯一のものだ。設定されないままだと `custom` に対して `anthropic` のままなので、既存のカスタム設定は以前とまったく同じように動作する。

```bash
# OpenAI互換エンドポイント (vLLM、LiteLLM、OpenRouter、Ollama、LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# Anthropic互換エンドポイント — /v1はなし、SDK が追加する
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## モデルが削除され、別の何かが応答した

設定された `llm_model` は `llm_provider` を提供した設定 *層* に対してスコープされた — プロバイダをフラグで設定し、モデルを設定ファイルで指定するとモデルは破棄され、ハードコードされたデフォルトが使用された。カスタムエンドポイントは Claude CLI にフォールスルーし、CLI はあなた自身の base URL に対して `--model sonnet` で起動し、サポートされていないモデルと報告した。何も実際の原因を述べなかった。

明示的に設定された **エンドポイント** プロバイダ(`anthropic`、`openai`、`custom`)は今、契約である: それは単独で構築され、障害はプロバイダ、ワイヤ、base URL、モデル、どのクレデンシャル種別が使用されたかを述べるエラーを発生させる。`llm_allow_fallback: true` は古いチェーニングを復元する。2つの OAuth CLI は互いにフォールバックし続ける — どちらもあなたのエンドポイントを携えていないため。

## ベアラクレデンシャルはなかった

1つの `llm_api_key` は SDK で `X-Api-Key` として、CLI ではベアラトークンとして送信され、それを SDK に渡すと SDK 自体の auth-token 解決が抑制された — そのため `Authorization: Bearer` を要求するゲートウェイには到達不可能だった。`llm_auth_token` が両方のワイヤのベアラクレデンシャルである。

## 見ることができる設定

すべてのキーに1つの優先順位: `TESSERAE_LLM_*` 環境変数 → プロジェクト `.tesserae/config.json` → `~/.tesserae/config.json` → デフォルト、レガシ `ANTHROPIC_*` 変数は1段下。リゾルバは各キーをどの層が勝ったかを記録し、`tesserae config status` がそれを出力する — 以前は推測していたし、リゾルバが意図的に無視する環境変数を所有物として並べていた。status はまたワイヤ、クレデンシャル種別、そしてプローブに応えたクライアントを示す。

`ask`、`query`、lint、MCP サマリー、エンジンデーモンは環境変数とグローバル設定のみに対して解決したため、プロジェクトレベルのエンドポイントは `compile` では尊重され、他のすべての場所では静かに無視された。それらすべてが今、プロジェクトを読む。

## また

- 無効な `llm_provider` は静かに `claude` になるのではなく、報告される。
- Anthropic base URL は正規化され、このプロジェクト自身のクイックスタートが文書化していた重複した `/v1/v1/messages` を修正する。
- `401`/`403` は認証障害として、`404`/モデルなしはエンドポイント障害として分類され、すべてが「unavailable」として報告されるのではなく。
- `init` と `setup` が新しいキーを永続化する; 以前は受け入れて破棄した。

## アップグレード

移行するものはない。2つの目に見える変化: 明示的なエンドポイントプロバイダはもはや別のバックエンドにフォールバックせず、`config status` は `set`/`unset` ではなくクレデンシャル *種別* を出力する。
