Veröffentlicht am **2026-09-08** · [PyPI](https://pypi.org/project/tesserae/0.39.2/) · [GitHub-Release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.2) · `pip install --upgrade tesserae==0.39.2`

Zwei Lücken an derselben Stelle: nichts sagte dir, ob dein LLM-Backend wirklich funktioniert, und `doctor --fix` beendete nicht, was es anfing.

## Was passiert ist

`doctor --fix` wandte jede Reparatur einmal an, in Registry-Reihenfolge. Eine Reparatur, die eine frühere Prüfung entwertete, ließ diese Arbeit einem zweiten Aufruf, von dem niemand wusste: Lint zu reparieren schreibt `graph.json` neu, wodurch die Site veraltet, und die Site-Prüfung war schon vorbei. Zudem druckte ein Reparaturlauf dieselbe Tabelle wie ein Nur-Lese-Lauf, sodass man zwei Bildschirme vergleichen musste, um zu erfahren, welche Warnungen beabsichtigt waren. Unterdessen war das Einzige, was das Backend berührte, `config status --ping`, das als Nebeneffekt des Konfigurationsdrucks einen Aufruf macht.

## Was sich geändert hat

- **`doctor --fix` konvergiert.** Reparaturen wiederholen sich, bis ein Durchlauf nichts mehr ändert, gedeckelt bei drei, und der Projektkontext wird zwischen den Durchläufen neu aufgebaut, sodass eine Reparatur, die erzeugt, was eine spätere Prüfung liest, von ihr auch gesehen wird.
- **Alles, was es ablehnt, wird benannt.** Was noch falsch ist, landet unter **Still open** mit dem Befehl und dem Grund. Der Grund ist ehrlich über den Lauf, der ihn erzeugt hat: ein Nur-Lese-Lauf sagt, der Befund sei per `--fix` reparierbar, nie dass eine Reparatur lief und scheiterte. Vier ständige Gründe decken jede reine Meldeprüfung ab — spend, install, authenticate, destroy — und ein Test schlägt fehl, wenn eine Prüfung ohne einen davon hinzukommt.
- **Drei weitere Prüfungen reparieren sich selbst.** `config_valid` füllt fehlende erforderliche Schlüssel atomar mit den Werten, die `init` schreibt; eine Konfiguration, die nicht parst, wird gemeldet und nie überschrieben. `--fix --deep` ergänzt langsame lokale Reparaturen, beginnend mit dem Session-Chunk-Backfill. Keine Reparatur auf irgendeiner Stufe führt eine Kompilierung aus.
- **`tesserae test` beweist, dass das Backend antwortet.** Es löst die Einstellungen so auf, wie es die Kompilierung tut, baut denselben Client und gibt dann einen JSON-Aufruf und einen Prosa-Aufruf aus, denn ein Gateway kann den ersten bedienen und den zweiten ablehnen. Keiner wird zwischengespeichert. Es endet nur dann mit 0, wenn beide zurückkommen.

## Verwendung

```bash
tesserae test                 # resolve, build, one JSON call, one prose call
tesserae doctor --fix         # repeats until a pass changes nothing
tesserae doctor --fix --deep  # + the slow local repairs
```

## Upgrade

Nichts zu migrieren. `doctor --fix` hält sein altes Versprechen — nur sichere Reparaturen, nie eine Kompilierung, nie ein getöteter Prozess — es wiederholt sich jetzt nur und meldet, was es liegen ließ. `--deep` ohne `--fix` endet mit 2.
