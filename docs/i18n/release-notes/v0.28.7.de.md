Veröffentlicht **2026-08-05** · [PyPI](https://pypi.org/project/tesserae/0.28.7/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.7) · `pip install --upgrade tesserae==0.28.7`

**Aktualisieren Sie, wenn ein anderes Tool Sitzungsdatensätze in Ihren Tesserae-Speicher schreibt.** Problem [#104](https://github.com/ca1773130n/Tesserae/issues/104) wurde zweimal behoben, in 0.28.5 und 0.28.6, und verlor diese Datensätze trotzdem beide Male. Diese Version behebt das Problem auf der Achse, die wirklich einen `producer` von einem anderen unterscheidet.

## Was die beiden früheren Korrektionen falsch verstanden haben

Beide beschränkten die Bereinigung auf *wo der Scan aussah* : Eine Erkennung konnte nur Datensätze löschen, deren Transkript unter einer Harness-Root lebte, die sie durchlaufen hatte. Diese Begründung gilt nur, wenn verschiedene Producer unterschiedliche Verzeichnisse lesen.

Das tun sie nicht. Ein Orchestrator, der seine eigenen Agent-Sitzungen exportiert, beschreibt die **gleichen** `~/.claude`-Transkripte, die Tesseraes lokaler Scan liest — er trägt nur die Agent-Identität, die der Scan nicht ableiten kann. Seine Datensätze waren konstruktionsbedingt im Bereich.

Gemessen an 0.28.6 gegenüber einem echten 375-Datensatz-Speicher überlebten zwei Verlustformen:

- **Gelöscht.** Ein Datensatz, dessen Transkript der Scan nicht mehr findet, wird bereinigt. Der ursprüngliche Fehler, unverändert.
- **Stillschweigend überschrieben.** Ein Datensatz, dessen Transkript der Scan *findet*, wird durch die schlichtere Version des Scans ersetzt — Agent-Identität und Metadaten sind weg. Beide Writer leiten denselben Dateinamen von der Session-ID ab, also landet einer auf dem anderen. Nichts wird gelöscht, also bleibt die Löschzahl bei 0 und die Ausführung meldet Erfolg.

Die zweite Form ist überhaupt kein Bereinigungs-Problem, weshalb keine Verfeinerung des Bereichs sie erreichte.

## Herkunft

Jeder Datensatz trägt jetzt ein **`producer`** — der Importer, der ihn geschrieben hat. `sessions discover --import` kennzeichnet `tesserae:discover` ; `sessions import <path>` kennzeichnet `tesserae:import`. Ein Writer kann nur Datensätze berühren, die er produziert hat:

- er bereinigt nur seine eigenen;
- er wird **nicht** den Datensatz eines anderen Producer für die gleiche Sitzung überschreiben. Der eingehende Write wird übersprungen und als `Left alone (written by another producer)` gemeldet.

Wenn Sie aus Ihrem eigenen Tool in diesen Speicher schreiben, verwenden Sie `tesserae sessions import <file>` und Ihre Datensätze sind von diesem Punkt an geschützt. Sonst ist nichts erforderlich.

Root- und Harness-Scoping bleiben als zweites Tor, aber sie sind nicht mehr das, was Datensätze sicher hält.

## Upgrade

**Datensätze, die vor dieser Version geschrieben wurden, tragen keinen Producer.** Sie sind Herrenlos, daher kein Importer bereinigt oder überschreibt sie — das Upgrade kann nicht verlieren, was Sie bereits haben, einschließlich Datensätze, die ein anderes Tool geschrieben hat.

Die Kosten dieser Wahl: Die Erkennung wird auch Legacy-Datensätze nicht aktualisieren. Falls Tesseraes eigener Scan das Einzige ist, das in Ihren Speicher schreibt, führen Sie aus

```bash
tesserae sessions discover --import --adopt-unowned
```

einmal, um diese Datensätze an die Erkennung zu übergeben. **Führen Sie das nicht aus, wenn ein anderes Tool in den gleichen Speicher schreibt** — es tut genau das, was das Flag sagt.

Verlustfrei war die richtige Standardeinstellung. Der behobene Fehler ist stiller Datenverlust, und die andere Standardeinstellung hätte die Datensätze des Berichtsprojekts ein letztes Mal beim Upgrade gelöscht, das sie schützen sollte.

## Anerkennung

Gemeldet, reproduziert und diagnostiziert vom Agenten, der am [Agented](https://github.com/ca1773130n/Agented)-Projekt arbeitet, das Tesserae über seine CLI nutzt. Sie maßen gegen einen echten Speicher anstelle einer Fixture, weshalb sie fanden, was zwei Korrekturrunden und eine fünf-Reviewer-Code-Review nicht fanden — jeder hier geschriebene Test machte « ein anderer Producer » bedeuten « ein anderes Verzeichnis », so dass die Tests die Annahme bestätigten, anstatt sie zu überprüfen. Sie schlugen auch Herkunft vor, die Richtung, die #104 von Anfang an suggerierte.
