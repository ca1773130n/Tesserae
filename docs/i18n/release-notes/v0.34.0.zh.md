发布于 **2026-08-28** · [PyPI](https://pypi.org/project/tesserae/0.34.0/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.34.0) · `pip install --upgrade tesserae==0.34.0`

知识图谱的价值取决于它知道什么。这个版本查明了每份文档中真正抵达图谱的部分有多少，并修复了横亘在语料库与一个能据其作答的图谱之间的四件事。

## 每份文档一次抽取调用，无论文档多长

抽取提示把整份文档都塞了进去，而没有任何东西去切分它——超时错误自己给出的建议“文档很大就切分它”，是说给运维者听的。于是一篇 38 KB 的论文只得到一次遍历，模型返回了它自认为完整的答案。

在 148 篇全文论文上实测：
**每份文档 29.6 条事实关系变成了 209.8 条**，提升 7.1 倍，节点数为 6.8 倍。

这既不是截断也不是 token 上限。两者都测过了：单次调用是自行停止的，而把输出上限提高 6.4 倍只多换来 20% 的输出。无论看到什么，模型都以一份有限大小的图谱回答每一次请求，所以得到更多的唯一办法就是多问几次。`TESSERAE_EXTRACT_CHUNK_CHARS` 就是那个旋钮，其背后的曲线写在这个常量的 docstring 里——没有拐点，因此它是在一条直线上用编译时间换密度。

## 检索现在胜过词法基线

三处缺陷让检索器付出的代价比图谱本身还大：

- 词法通道声称采用 FTS5 `MATCH` 语义，实际匹配的是**子串**——`in` 命中了 “training”、“domain” 和 “inference”——且没有任何归一化，还以权重 1.0 融合，与 BM25 等同。
- `hybrid_search(source_root=)` 会把文档自身的文本追加到它的词法草堆中，而没有任何生产调用方传入它。这个特性一直是空转的。
- 一份在同名合并中失去 `SourceDocument` 锚点的文档，就再也无法作为文档被找到：**一个语料库中占 23%，另一个中是 1,552 份里的 138 份**。

标准答案文档的召回率仅靠这些修复就从 **0.476 升到 0.602**，再配合更稠密的图谱升到 **0.743——而平坦 BM25 为 0.605**。

## 捆绑包承载原文，且其阈值现在是实测得来的

`compile_context` 会用节点背后的源文档替换它被抽取出的正文。决定何时值得这么做的下限曾是 900 个字符，而 900 恰好落在这种替换会让捆绑包**更糟**的区间里：

| 每份文档字符数 | 抽取出的主张 | 源文散文 |
|---|---|---|
| 4,300 | 0.218 | **0.371** |
| 2,500 | 0.227 | **0.332** |
| 1,260 | 0.222 | **0.145** |

一条主张本身就是一个完整的句子，切细了也能存活；而一个段落需要足够的篇幅来承载论证。在每份文档 4,300 字符时，捆绑包以 **+0.084** 胜过 BM25 段落对照组——8 次中 8 次，p=0.0078。下限现在是 2,500，即实测得到的交叉点。

## 其他

- 每个 `EvidenceSpan` 都能从它自己的文档抵达；此前是否如此取决于模型，而在一个语料库上模型有 **89% 的情况**并未这么做
- DeepScholar 分支在 14 篇被引论文中只解析出 1 篇，还把这个结果称为证据

## 升级

在你重新编译之前什么都不会变。重新编译时请预留成本：分块抽取每个分块要花一次调用，148 篇全文论文用了 **9 小时**，而不是 66 分钟。调高 `TESSERAE_EXTRACT_CHUNK_CHARS` 可以用密度换速度，或设为 `0` 恢复此前行为。
