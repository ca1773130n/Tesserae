Released **2026-08-07** · [PyPI](https://pypi.org/project/tesserae/0.29.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.29.0) · `pip install --upgrade tesserae==0.29.0`

このリリースは、複数のマシンが 1 つのディスクを共有する状況で Tesserae を使えるようにし、
出力を見た目より静かに劣化させていた 2 つの問題を修正します。

## Tesserae は自分自身の LLM 呼び出しをあなたのセッションとして取り込んでいました

コンパイルのたびに、ドキュメントごとに 1 回、セッションごとに 1 回 `claude` CLI が
起動されます。そのそれぞれが `~/.claude/projects` にトランスクリプトを書き込み、
セッション ディスカバリはそれをあなたのコーディング作業であるかのように収集して
いました。メンテナ自身のプロジェクトでは：

| | |
|---|---|
| 保存されたセッション レコード | 14,605 |
| Tesserae 自身の抽出呼び出し | **14,377 (98.4%)** |
| 本物のユーザー セッション | 228 |

そのうち 10,666 件は同一のタイトル — 抽出プロンプト — を持っていました。

これに対するフィルタはすでに存在し、そのフィルタを完全に保つことだけを仕事とする
テストも存在しました。そのテストはソースを走査して
`You (?:are|distill|write|decide|arbitrate|split)` に一致するプロンプトを探していました —
手作業で維持された、冒頭の**動詞**の許可リストです。抽出プロンプトは "You extract" で
始まるため、システム内で最も量の多いプロンプトが、ガードには見えない唯一のプロンプト
になっていました。

ガードは現在、AST から `system=` 引数を列挙し、モジュール レベルの定数を解決します。
プロンプトを識別するのは**どう渡されるか**であって、たまたまどう書かれているかでは
ないからです。これによって、カバーされていない呼び出しがただちにさらに 5 つ
見つかりました：liveness プローブ、アクティビティ サマリー（2 種類の文面）、
決定抽出器、クレーム judge、スコープ ルーターです。

`tesserae sessions prune-internal` は sqlite に加えて**ファイル ストア**も掃除する
ようになりました。以前は sqlite しか掃除せず、`compile` が読むのはファイル ストアの
ほうなので、掃除しても何も起きていないように見えていました。`--dry-run` を
受け付けます。

Tesserae をしばらく動かしているなら、実行してください。そのうえで再コンパイルを。
あなたのノード数はノイズを計測してきました。

## 1 つのプロジェクト ディレクトリを複数のマシンで共有する

Tesserae のどこにもマシンの識別情報がなかったため、共有された `.tesserae/` に置かれた
マシンごとの状態は、どのホストからもマシンが 1 台しかないかのように読み書きされて
いました。

**セッション レコードは、それを一度も見ていないホストに削除され得ました。**
`producer` では 2 台のマシンを区別できません：どのホストのスキャンも同じ定数を
スタンプし、それぞれの `~/.claude` ルートは同じ文字列に解決されるため、
トランスクリプトを一度も見ていないホストでも既存の 2 つの安全ゲートを両方とも
通過し、別のマシンのレコードを削除したうえで成功を報告していました。レコードは
収集したホストを保持するようになり、ホストは自分が収集したものだけを prune します。

ホスト ID は、ホスト名から導出するのではなく `~/.tesserae/host_id` に永続化されます
（`TESSERAE_HOST_ID` で上書き）。1 つのイメージから構築されたフリートはホスト名を
再利用し、衝突すればあるマシンのレコードが別のマシンに渡ってしまうからです。

さらに 3 つの衝突が修正されました：エンジンの pidfile は `daemon.<host>.pid` になり
（liveness は**ローカル**のプロセス テーブルに対する `os.kill(pid, 0)` であり、
別マシンの pid に対しては無意味です）、Codex のスキャン ウォーターマークはホスト
ごとになり（共有された下限が 1 つしかないと、最後に走ったホストが、他方がまだ
読んでいないトランスクリプトの先までそれを進めてしまい、それらは決してインポート
されませんでした）、`doctor --fix` は他ホストの pidfile に一切触れなくなりました。

**新機能：`tesserae engine --harvest-only`。** 1 台のホストがコンパイルし、他のホストは
自分に見えるトランスクリプトを tail するだけで、コンパイル ロックを取りません。
競合を調停するのではなく、取り除きます。

## バックグラウンド エンジンがあなたをブロックしなくなりました

`compile` と `refresh` は `--wait [SECONDS]` を受け付けます。exit 2 で終了する代わりに
プロジェクトのコンパイル ロックを待ち行列に並び、5 秒ごとに状況を報告し、ロックを
保持しているマシン名を示します。バックグラウンド デーモンは、トリガーを捨てるのでは
なく、60 秒を上限とする指数バックオフで延期するようになりました。

`--wait` は、stderr が端末かどうかから推測されるものではなく、明示的なフラグです：
同じコマンドが `tee` の下、tmux のキャプチャ内、CI 内で挙動を変えてはなりません。
上限があるのは、`flock` が公平性を提供せず、したがって飢餓の上限も存在しないからです。

## `compile --all` / `refresh --all`

登録済みの全プロジェクトに対する 1 つのコマンドで、プロジェクトごとに失敗が
隔離されます — 1 つのプロジェクトが失敗しても他は止まりません。コンパイル ロックが
保持されているプロジェクトは **failed** ではなく **locked** として報告され、専用の
終了コードを持ちます：フリートではそれが通常の状態であり、トレースバックと同じ
コードを与えることは、終了コードを無視するよう人に教えることになります。コンパイルは
LLM を多用するため、`--jobs` のデフォルトは 1 です。

## プロジェクト レベルの LLM 設定が実際にクライアントへ届くようになりました

`ProjectWiki._build_json_client` はプロジェクト設定を解決したうえで、それを**渡さずに**
クライアント ファクトリを呼んでいました。そのためファクトリは環境変数とグローバル設定
だけで再解決し、プロジェクト レベルの `llm_model`、`llm_base_url`、`llm_api_key` を
すべて捨てていました。`.tesserae/config.json` に書き込んだカスタム エンドポイントは
クライアントに届かず、コンパイルは黙ってデフォルトのバックエンドで走っていました。

ドキュメントはすでに正しい挙動を記述していました — 食い違っていたのはコードだけです。
これはバグが取り得る最悪の形です。ツールを疑う理由が何ひとつ与えられないからです。

`--claude-config-dir` を繰り返し指定しても最初のアカウントに潰れていました。
`CLAUDE_CONFIG_DIR` がスカラーだからです。順序を保った完全なリストは、今後は
`TESSERAE_CLAUDE_CONFIG_DIRS` で渡されます。

## 正直な報告

`tesserae init` はプロジェクトを登録するようになりました。これがないと、README の
クイックスタートに従った結果、`ask` は cwd のエイリアスを解決できず、フェデレーテッド
スコープにフォールバックし、3 ファイルのプロジェクトについての質問に、無関係な
リポジトリに属する 19,744 ノードの中から答えていました — 一方で `--scope current` は、
登録済みプロジェクトの中にいるのに「not inside a registered project」と言って exit 2
していました。

`compile` は、**すべての**ドキュメントが決定的抽出にフォールバックした場合に exit 1
するようになりました。以前はサマリーを表示して exit 0 していたため、概念レイヤーの
ないグラフが成功として読まれ、そのあと `query` は何にも一致しませんでした。

`doctor` は、CLI がかつて使われたことしか証明しないファイルを根拠に
`credentialed LLM CLI` を報告しなくなりました — `compile` が認証で失敗したのと同じ秒に、
緑のチェックを表示していたのです。**これは能力の向上ではなく、確信度の引き下げです**：
認証情報の検証には実際の LLM 呼び出しが必要なので、このチェックは実際に検証した
ことだけを述べるようになりました。

レポート専用の `filesystem_locking` チェックを追加しました。ここでの並行性の保証は
すべて、`.tesserae/` を保持するファイルシステムが `flock(2)` を強制することに依存して
おり、NFS や SMB ではそれが構成次第です — 動作するロック デーモンがなければ `flock` は
黙って no-op に劣化し得ます。ネットワーク ファイルシステム上では警告を出し、単一の
ホストではホスト間の強制を**証明できない**ことを明示します。共有ストレージに対して
複数のマシンから Tesserae を動かすなら、それは直接テストしてください。

## 並行書き込み

5 つのアーティファクト ライターが、固定された 1 つの一時パスを通して公開して
いました — `with_suffix` はサフィックスを*置き換える*ので、`graph.json` は
`.tesserae/graph.tmp` を通して公開されていた点に注意してください。2 つのパブリッシャが
その 1 つのファイルに交互に書き込み、混ざったものを所定の場所へ rename していました。
最も影響が大きかったのはマニフェストです：`_load_manifest` はガードなしに `json.loads`
を呼ぶため、交錯したマニフェストは、それ以降すべてのホストのすべてのコンパイルで
例外を投げました。

`TESSERAE_REGISTRY` は、エンジンのフリート モードだけでなく、すべてのコマンドで
尊重されるようになりました。

## アップグレード

何もする必要はありません。単一マシンのインストールはこれまでとまったく同じように
動作します。host フィールドは追加的なもので、それを持たないレコードは
`--adopt-unowned` を渡すまでそのまま残されます。

一度実行しておく価値があるものが 2 つあります：

```bash
tesserae sessions prune-internal --dry-run   # ストアのどれだけがノイズかを見る
tesserae sessions prune-internal             # そして掃除する
tesserae compile                             # 残ったものの上で再構築する
```
