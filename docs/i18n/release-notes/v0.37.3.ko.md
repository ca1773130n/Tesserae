공개일 **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1과 v0.37.2는 로컬 OpenAI 호환 서버에 닿을 수 있게 만들었다. 하나를 실제로
돌려 보니 다음 문제가 드러났다: 추출 풀은 rate limit이 있는 클라우드 API에 맞춰
크기가 정해져 있는데, 이 컴퓨터의 모델 서버는 한 번에 요청 하나만 처리한다.

## 무슨 일이 있었나

`TESSERAE_EXTRACT_CONCURRENCY`의 기본값은 4다. Ollama, llama.cpp, LM Studio는 한 번에
요청 하나만 처리하므로 모든 호출 뒤에 요청 세 개가 큐에 쌓였고, 서버가 버린 큐 속
요청은 그 worker를 `TESSERAE_EXTRACT_TIMEOUT` 전체 동안 막았다. 밖에서 보면 메모리
문제와 똑같아 보였고, 제대로 읽어내기까지 몇 시간이 들었다.

## 무엇이 바뀌었나

- **설정하지 않으면 이 값은 엔드포인트를 따른다.** 루프백 `llm_base_url`
  (`localhost`, `127.0.0.1`, `::1`)이면 문서를 한 번에 하나씩 처리하고, stderr
  알림이 엔드포인트와 덮어쓰는 방법을 알려 준다.
- **배치 러너가 추출기에 요청이 어디로 가는지 묻는다.**
  `LLMResearchExtractor`가 클라이언트의 `base_url`을 노출하고 선택적 라우터가
  LLM 쪽을 대신 답하므로, 호출 지점 네 곳을 거쳐 배관을 깔 필요가 없었다.
  결정론적 추출기는 엔드포인트가 없으니 4를 유지한다.
- **명시적으로 설정한 값이 항상 이긴다.** 클라우드 API로 흩뿌리는 루프백 프록시
  (LiteLLM, 배칭을 쓰는 vLLM)는 더 받을 수 있다: 직접 설정하라.

`docs/tuning.md`에 새 기본값이 문서화되어 있다.

## 업그레이드

이전할 것은 없다. 로컬 모델 컴파일이 멈춘 듯 보였거나 메모리가 부족해 보였다면
아마 이것이었다. 우회책으로 넣어 둔 `TESSERAE_EXTRACT_CONCURRENCY=1`은 남겨도 지워도
된다. 결과는 같다.
