发布于 **2026-09-17** · [PyPI](https://pypi.org/project/tesserae/0.41.4/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.4) · `pip install --upgrade tesserae==0.41.4`

`engine --serve` 和 `engine --proactive` 发布时带有单元测试，但从未在真实机器上端到端运行过。
实际运行后发现了两个缺陷，都出在引擎的启动方式和触发编译的条件上。`--proactive` 本身工作正常。

## 改了什么

- **引擎立即开始提供服务。** 在一个项目中首次运行时，会话 tailer 会读取机器上的每一份 Codex
  转录，找出属于该项目的那些。这次读取在其他一切启动之前执行。在一台转录共 15 GB 的机器上，
  `engine --serve` 在 344 秒内没有响应任何请求，同样长的时间里也不理会 SIGTERM，监督进程只能强行
  终止它，留下一个过期的 pidfile。现在这次读取在独立线程上运行。
- **一次编译不再安排另一次编译。** 每次编译都会重写 Obsidian vault，而 vault 监视器把这些写入
  当成了用户编辑。即使已经记录 `applied (no changes)`，它每次仍会排入一次完整重编译。修改一个
  文档会跑三次编译，其中两次是完整编译。现在只有当 vault 编辑确实改变了图时，引擎才会重新编译。

## 升级

无需迁移。如果引擎正在运行，请重启它：运行中的进程仍持有旧代码。
