リリース **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1 と v0.37.2 はローカルの OpenAI 互換サーバーに到達できるようにした。実際に
1 つ動かしてみると次の問題が露わになった。抽出プールはレート制限のあるクラウド API
向けのサイズになっているが、このマシン上のモデルサーバーは一度に 1 つのリクエスト
しか処理しない。

## 何が起きたか

`TESSERAE_EXTRACT_CONCURRENCY` のデフォルトは 4 だ。Ollama、llama.cpp、LM Studio は
一度に 1 つのリクエストしか処理しないため、すべての呼び出しの後ろに 3 つのリクエストが
並び、サーバーが落としたキュー内のリクエストは `TESSERAE_EXTRACT_TIMEOUT` の間ずっと
そのワーカーをブロックした。外から見るとメモリの問題とまったく同じに見え、正しく
読み解くまでに何時間もかかった。

## 何が変わったか

- **未設定なら、この値はエンドポイントに従う。** ループバックの `llm_base_url`
  （`localhost`、`127.0.0.1`、`::1`）なら一度に 1 つのドキュメントを処理し、stderr
  の通知がエンドポイントと上書き方法を伝える。
- **バッチランナーが抽出器にリクエストの宛先を尋ねる。**
  `LLMResearchExtractor` がクライアントの `base_url` を公開し、選択的ルーターが
  LLM 側の代わりに答えるので、4 つの呼び出しサイトに配管を通す必要はなかった。
  決定論的抽出器にはエンドポイントがなく、4 のままだ。
- **明示的な値が常に優先される。** クラウド API に振り分けるループバックプロキシ
  （LiteLLM、バッチ処理付きの vLLM）はもっと受け付けられる。設定すればよい。

`docs/tuning.md` に新しいデフォルトが記載されている。

## アップグレード

移行するものはない。ローカルモデルのコンパイルが止まったように、あるいはメモリ不足に
見えたなら、おそらくこれだった。回避策として追加した `TESSERAE_EXTRACT_CONCURRENCY=1`
は残しても消してもよい。結果は同じだ。
