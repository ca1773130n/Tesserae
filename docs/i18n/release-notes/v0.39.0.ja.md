公開日 **2026-09-06** · [PyPI](https://pypi.org/project/tesserae/0.39.0/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.0) · `pip install --upgrade tesserae==0.39.0`

`tesserae compile` は常にコンセプトと主張のレイヤーを、設定した LLM を通じて構築してきた。コンパイルへのその他すべての経路はそうではなかった。`refresh`、エンジン デーモン、MCP の `materialize` パス、`deploy --build` はいずれもエクストラクターを指定せずにコンパイルを要求し、"none" は決定論的エクストラクターを意味していた。

## 何が起きたか

あるプロジェクトで `tesserae refresh` を一度実行したところ、文書レイヤー全体が LLM なしで再構築された。すべてのファイルはグラフ化済みのままマークされ、どの文書もフォールバックとしてフラグが立てられず、グラフはコンセプト、機能、モデル、トピックがすべて消えた状態で戻ってきた。466 のコンセプトが 0 になった。リフレッシュループ上のデーモンであれば、最初の再コンパイル時に同じことをしていただろう。修正はテストで最初に確認された。増分差分器は、変更されていないファイルの LLM 型ノードを保持する。エントリーポイントがその穴だった。

## 何が変わったか

- **エクストラクターを指定しないコンパイルは、設定した LLM のものを構築するようになった**。`tesserae compile` が構築するのと同じ形で、ドキュメント単位のフォールバックは決定論的エクストラクター。使用可能なバックエンドがなければ、警告を表示しながら構造グラフにダウングレードされ、決してサイレントで行わない。`compile --extractor deterministic` は明示的なオプトアウトのままである。
- **コンテキスト バンドルは、そのエンティティを詳述する文書を引用してパックするようになった**。v0.38.0 はドキュメントあたりのメンション密度を保存していた。それを読むものはなかった。エンティティのバンドルのセクションは、その文書の文章をパックし、その文書を名前で引用するようになり、新しい SQLite ミラーが存在しないときは最初に見つかったパスにフォールバックする。`node_context` はランク付けされた加算的な `documents` リストを得る。2 つのコーパスで測定すると、最初に見つかったパスは所有文書を約半分の割合で当てるが、言及回数が最も多い文書は 10 回に 9 回の割合で当てる。
- **`verify_attribution`**、MCP ツールと `verify-attribution` CLI 動詞として。カバレッジチェックは、すべてのトークンが証拠にあるため、隣の表行から取られた実数をパスしてしまう。これは代わりに所有権をチェックする。その図がどのレコードに座っているか、その文書がベンチマークに名前をつけているかどうか。決定論的、グラフなし、LLM なし。33 の真の答えの中で 4 つの偽陽性とともに 15 の帰属誤りを 14 で検出した。
- **クレジット不足の codex アカウントは、伝送ブリップではなく消耗である。** 1 回のスポーン、評決 `exhausted`、実行のために記憶される。そしてプロバイダー チェーンは、呼び出し時にログインした Claude CLI にフォールバックする（そのドキュメント文字列は常にそう約束していた）。以前は、4 つのホームのリトライに約 55 秒を費やし、何も返さなかった。

## アップグレード

デーモンまたは `refresh` ループを実行している場合、今後、変更されたドキュメントに対して LLM コールの費用が発生することを想定してください。変更されていないドキュメントはプロンプトアドレス指定キャッシュにヒットする。以前のバージョンで `refresh` によってコンパイルされたグラフは、構造レイヤーのみである。1 つの完全な `tesserae compile` で LLM レイヤーが復元される。移行するものはない。
