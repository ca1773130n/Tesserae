公開日 **2026-09-07** · [PyPI](https://pypi.org/project/tesserae/0.39.1/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.1) · `pip install --upgrade tesserae==0.39.1`

`claude` プロバイダーを自前のゲートウェイ — ベース URL、ベアラートークン、`~/.claude` ではない設定ディレクトリ — に向けても、Tesserae は相変わらず CLI のデフォルトアカウントを使っていた。バグは 1 つではなく、入口ごとに 1 つずつあった。

## 何が起きたか

`ClaudeCLIJsonClient` には `llm_auth_token` を受け取る手段がなく、CLI は資格情報なしでゲートウェイに達し、設定ディレクトリにあるログインへ戻っていた。`tesserae ask`、`query --llm`、アクティビティ要約、デーモンは設定済みの `llm_claude_config_dirs` なしでクライアントを組み立て、`compile` がリストに従う一方でマシン上のあらゆる `~/.claude*` をローテーションしていた。`init --yes` とウィザードは `--llm-auth-token` と `--llm-api-style` を受け付けながら、プランを書く前に両方を捨てていた。クリップの TL;DR は独自に `claude` を呼んでいた。そして古いウィザードが書いた 2 つのキー `llm_claude_config_dir` と `extraction.claude_config_dir` は何にも読まれず、セットアップ時に選んだディレクトリは一度も反映されなかった。

## 何が変わったか

- **すべての入口が CLI にエンドポイントとトークンを渡す。** ビルダーは `llm_base_url`、`llm_api_key`、`llm_auth_token` をまとめて渡し、子プロセスはそれらを `ANTHROPIC_BASE_URL` と `ANTHROPIC_AUTH_TOKEN` として受け取る。空の設定ディレクトリで本物の `claude -p` に対して検証済み: リクエストはベアラートークン付きで `/v1/messages` に到達し、`claude /login` は関与しなかった。
- **設定された設定ディレクトリはどこでも尊重され、`~` も含む。** ローテーションクライアントは解決済み設定から `llm_claude_config_dirs` を読み、`~/.claude*` の外にある設定ディレクトリも使用可能とみなす。古い単数形キーと `extraction.claude_config_dir` は複数形キーより下位のプロジェクト設定として扱われ、`config status` は `default` を表示する代わりにどの層が勝ったかを示す。
- **`init`、`setup`、ウィザードがすべてのノブを保持する。** `--llm-auth-token` と `--llm-api-style` はウィザード経路でも永続化され、`claude` プロバイダーではウィザードがエンドポイントとベアラートークンを尋ねるようになった。
- **Doctor とクリップの TL;DR も同じ設定に従う。** `llm_login` はルーティングされた CLI にログインは不要だと報告し、クリップ要約は独自の `claude` 呼び出しではなくプロジェクト設定を携えて `build_default_json_client` を通る。

## アップグレード

古いウィザードが `.tesserae/config.json` に `extraction.claude_config_dir` を残していれば、今後はそのディレクトリが尊重される。`tesserae config status --no-ping` でどの層が勝ったかを確認し、変えるなら `llm_claude_config_dirs` を設定する。他に移行するものはない。
