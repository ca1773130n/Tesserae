공개일 **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

커스텀 LLM 프로바이더 설정은 서로 무관한 세 가지 이유로 동작할 수 없었고, 증상은
매번 설정한 적 없는 모델에 대한 오류였다. 프로바이더 코드 감사에서 결함 23건을
확인했고, 이번 릴리스가 그것들을 고친다.

## 와이어 프로토콜이 모델링된 적이 없었다

`llm_provider`는 *어떤 백엔드*와 *어떤 HTTP 방언*을 뒤섞었고, `custom`은 항상
`{base}/v1/messages`로 POST하는 Anthropic 클라이언트를 만들었다. vLLM, LiteLLM,
OpenRouter, Together, Ollama, LM Studio 등 OpenAI 호환 서버는 모두 여기에 404로
답한다. `chat/completions`를 말하는 유일한 클래스는 어떤 코드 경로에서도 생성되지
않았고 `api.openai.com`을 하드코딩하고 있어서, 그것 역시 사용자의 엔드포인트를
서비스할 수 없었다.

이제 `llm_api_style`이 와이어를 지정하며, 클라이언트를 고르는 것은 이 값뿐이다.
설정하지 않으면 `custom`에 대해 `anthropic`으로 유지되므로, 기존 커스텀 설정은
이전과 똑같이 동작한다.

```bash
# an OpenAI-compatible endpoint (vLLM, LiteLLM, OpenRouter, Ollama, LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# an Anthropic-compatible endpoint — no /v1, the SDK appends it
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## 모델이 버려지고, 다른 무언가가 답했다

설정한 `llm_model`은 `llm_provider`를 제공한 설정 *레이어*를 기준으로 범위가
정해졌다 — 프로바이더를 플래그로, 모델을 설정 파일로 주면 모델이 버려지고
하드코딩된 기본값이 쓰였다. 그다음 커스텀 엔드포인트는 Claude CLI로 흘러갔고,
CLI는 사용자의 base URL을 향해 `--model sonnet`으로 실행되어 지원하지 않는
모델이라고 보고했다. 실제 원인을 말해주는 것은 없었다.

명시적으로 설정된 **엔드포인트** 프로바이더(`anthropic`, `openai`, `custom`)는
이제 계약이다: 단독으로 생성되며, 실패하면 프로바이더, 와이어, base URL, 모델,
사용한 자격 증명 종류를 밝히는 오류를 던진다. `llm_allow_fallback: true`는 이전
연쇄 동작을 되살린다. OAuth CLI 둘은 여전히 서로 대체한다 — 어느 쪽도 사용자의
엔드포인트를 지니지 않기 때문이다.

## 베어러 자격 증명이 없었다

하나뿐인 `llm_api_key`가 SDK에서는 `X-Api-Key`로, CLI에서는 베어러 토큰으로
전송되었고, SDK에 그것을 넘기면 SDK 자체의 auth-token 해석이 억제되었다 —
그래서 `Authorization: Bearer`를 원하는 게이트웨이에는 닿을 수 없었다.
`llm_auth_token`이 두 와이어 모두에서 베어러 자격 증명이다.

## 볼 수 있는 설정

모든 키에 하나의 우선순위: `TESSERAE_LLM_*` 환경변수 → 프로젝트
`.tesserae/config.json` → `~/.tesserae/config.json` → 기본값, 레거시
`ANTHROPIC_*` 변수는 한 단계 아래. 리졸버는 각 키를 어느 레이어가 차지했는지
기록하고 `tesserae config status`가 그것을 출력한다 — 예전에는 추측했고, 리졸버가
의도적으로 무시하는 환경변수를 출처로 지목했다. status는 와이어, 자격 증명 종류,
프로브를 처리한 클라이언트도 보여준다.

`ask`, `query`, lint, MCP 요약, 엔진 데몬은 환경변수와 전역 설정만 보고
해석했으므로, 프로젝트 수준 엔드포인트는 `compile`에서만 존중되고 나머지에서는
조용히 무시되었다. 이제 모두 프로젝트를 읽는다.

## 그 밖에

- 잘못된 `llm_provider`는 조용히 `claude`가 되는 대신 보고된다.
- Anthropic base URL이 정규화되어, 이 프로젝트의 퀵스타트가 문서화하고 있던
  중복된 `/v1/v1/messages`가 고쳐진다.
- `401`/`403`은 인증 실패로, `404`/모델 없음은 엔드포인트 실패로 분류된다.
  전부 "unavailable"로 보고되지 않는다.
- `init`과 `setup`이 새 키를 저장한다. 이전에는 받아들이고 버렸다.

## 업그레이드

이전할 것은 없다. 눈에 띄는 변화 둘: 명시적 엔드포인트 프로바이더는 더 이상 다른
백엔드로 대체되지 않으며, `config status`는 `set`/`unset` 대신 자격 증명 *종류*를
출력한다.
