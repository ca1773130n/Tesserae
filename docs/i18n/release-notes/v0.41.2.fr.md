Publié le **2026-09-12** · [PyPI](https://pypi.org/project/tesserae/0.41.2/) · [Version GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.2) · `pip install --upgrade tesserae==0.41.2`

Chaque commande a été auditée en l'exécutant. Sur 42 défauts candidats, 31 ont
survécu à la reproduction et à un deuxième avis contradictoire. Cette version
ferme les douze plus sérieux : cinq qui ont rapporté le succès d'un travail
qu'elles n'avaient pas fait, cinq qui ont détruit des données, un drapeau qui
a été ignoré, et un laissé intentionnellement de côté.

## Succès rapporté pour un travail non effectué

- **Une compilation sur des chemins ne contenant pas de markdown est refusée.** `tesserae compile
  README.txt` — un vrai fichier avec le mauvais suffixe — reconstruisait le graphe à
  partir de rien, le remplaçait par un vide, et quittait avec le code 0. Le refus
  intervient avant toute écriture, donc le graphe est toujours là quand vous le
  lisez. Les chemins se résolvent maintenant contre `--project` plutôt que contre
  le répertoire de travail.
- **`code ingest` refuse un chemin qui n'existe pas**, au lieu d'écrire un
  graphe de code vide sur un vrai et de rapporter le succès.
- **`query` sur quelque chose qui n'est pas un projet est une erreur.** Il
  répondait « Aucune correspondance » avec le code 0, ce qui ressemble à une vraie
  recherche qui n'a rien trouvé, donc une faute de frappe dans `--project` se
  lisait comme un corpus vide.
- **`lint` dit quand il ne peut pas lire le graphe.** Il avalait l'erreur d'analyse,
  exécutait chaque contrôle sur un graphe vide, et rapportait « Aucun résultat. Le
  wiki est propre. » avec le code 0 à propos d'un `graph.json` qui ne peut pas être
  analysé du tout.
- **`engine --once` quitte avec un code non nul quand la compilation a échoué.** Il
  retournait 0 quoi qu'il se passe, donc l'intégration continue voyait du vert
  pour un pipeline qui levait. Le même bogue explique pourquoi une flotte imprimait
  `2/2 units ok` pour un lot dans lequel un projet échouait : elle lit le code
  de sortie de chaque unité.

## Destruction de données

- **Une config à l'échelle de la machine qui ne peut pas être analysée n'est plus remplacée.** Chaque
  écrivain fusionne sur un dictionnaire vide quand le fichier est illisible, puis
  écrivait le résultat, donc une virgule égarée coûtait le token de clip stocké et
  chaque clé sauvegardée. Lire au-delà d'un fichier corrompu fonctionne toujours ;
  écrire dessus ne l'est pas.
- **`projects register` ne réinitialise plus un projet qui n'a jamais été compilé**,
  ce qui remplaçait sa configuration et perdait ses sources, son nom et son
  fournisseur. Le commentaire propre du garde le promettait déjà ; il testait le
  mauvais fichier.
- **`sessions discover --import` conserve les dossiers d'une racine qu'il ne pouvait pas lire.**
  Une `--root` qui n'est pas sur le disque était toujours
  remise à la portée d'élagage, donc l'importation supprimait tout ce qui était
  récolté d'elle tout en n'ayant rien appris à son sujet. Un disque démonté
  suffisait.
- **`vault sync` enregistre le remplacement qu'il dit avoir appliqué.** Il
  rapportait l'édition, écrivait uniquement le vault, et la prochaine exécution
  remettait votre modification comme elle était.
- **`vault export` conserve une page orpheline qui contient vos notes** —
  exactement ce que `vault prune` refuse déjà de supprimer. Les deux n'étaient pas
  d'accord, et celui qui était silencieux s'exécutait à chaque exportation.

## Ignoré

- **`engine --all --harvest-only` ne compile plus.** Le drapeau atteignait un
  projet unique et était supprimé en mode flotte, ce qui est la forme pour laquelle
  il a été écrit : plusieurs machines partageant un répertoire, chacune lisant ce
  qu'elle seule peut voir, l'une d'elles compilant.

## Laissé intentionnellement de côté

`lint --fix-trivial` énumère les résultats qu'il vient de réparer. Cela se lit
comme « voici ce que j'ai réparé », un test l'épingle, et ce n'est pas un défaut.
Il est nommé ici parce que l'audit l'a levé et la réponse est non.

## Mise à niveau

Rien à migrer. Les commandes qui avaient l'habitude de quitter avec le code 0
tout en ne faisant rien d'utile quittent maintenant avec le code 2 et disent
pourquoi, donc un script qui dépendait du silence commencera à rapporter les
défaillances qu'il avait déjà.
