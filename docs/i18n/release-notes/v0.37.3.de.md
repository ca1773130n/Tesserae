Veröffentlicht am **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [GitHub-Release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1 und v0.37.2 machten einen lokalen OpenAI-kompatiblen Server erreichbar.
Einen zu betreiben legte das Nächste offen: Der Extraktionspool ist für eine
ratenbegrenzte Cloud-API bemessen, und ein Modellserver auf dieser Maschine
bedient eine Anfrage nach der anderen.

## Was passiert ist

`TESSERAE_EXTRACT_CONCURRENCY` steht standardmäßig auf 4. Ollama, llama.cpp und
LM Studio bedienen eine Anfrage nach der anderen, also warteten hinter jedem
Aufruf drei Anfragen, und eine wartende Anfrage, die der Server verwarf,
blockierte ihren Worker für das gesamte `TESSERAE_EXTRACT_TIMEOUT`. Von außen
sieht das genau wie ein Speicherproblem aus, und es kostete Stunden, bis es
richtig gelesen wurde.

## Was sich geändert hat

- **Nicht gesetzt, folgt der Wert dem Endpunkt.** Eine Loopback-`llm_base_url`
  (`localhost`, `127.0.0.1`, `::1`) bedeutet ein Dokument nach dem anderen, und
  ein Hinweis auf stderr nennt den Endpunkt und wie man ihn übersteuert.
- **Der Batch-Runner fragt den Extraktor, wohin seine Anfragen gehen.**
  `LLMResearchExtractor` legt die `base_url` seines Clients offen, und der
  selektive Router antwortet für seine LLM-Hälfte, sodass nichts durch vier
  Aufrufstellen verdrahtet werden musste. Ein deterministischer Extraktor hat
  keinen Endpunkt und behält 4.
- **Ein expliziter Wert gewinnt immer.** Ein Loopback-Proxy, der an eine
  Cloud-API verteilt (LiteLLM, vLLM mit Batching), verträgt mehr: Setzen Sie ihn.

`docs/tuning.md` dokumentiert den neuen Standard.

## Upgrade

Nichts zu migrieren. Wenn ein Compile mit lokalem Modell festgefahren oder
speicherknapp aussah, war es wahrscheinlich das. Ein als Umgehung gesetztes
`TESSERAE_EXTRACT_CONCURRENCY=1` kann bleiben oder weg; das Ergebnis ist dasselbe.
