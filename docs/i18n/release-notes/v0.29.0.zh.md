Released **2026-08-07** · [PyPI](https://pypi.org/project/tesserae/0.29.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.29.0) · `pip install --upgrade tesserae==0.29.0`

此版本让 Tesserae 在多台机器共享同一块磁盘时可用，并修掉了两件一直在悄悄让它的
输出比看上去更差的事。

## Tesserae 一直把自己的 LLM 调用当成你的会话摄取进来

每次编译都会为每个文档启动一次 `claude` CLI，再为每个会话启动一次。这些调用每一次
都往 `~/.claude/projects` 写下一份转录，而会话发现把它们当作你的编码工作采集了进来。
在维护者自己的项目上：

| | |
|---|---|
| 存储的会话记录 | 14,605 |
| Tesserae 自己的抽取调用 | **14,377（98.4%）** |
| 真实的用户会话 | 228 |

其中 10,666 条带着同一个标题——抽取提示词本身。

针对这一点的过滤器早就存在，专门负责让它保持完整的测试也早就存在。那个测试扫描源码，
寻找匹配 `You (?:are|distill|write|decide|arbitrate|split)` 的提示词——一份手工维护的
开头**动词**白名单。而抽取提示词以 "You extract" 开头，于是系统里调用量最大的那条
提示词，恰好就是这道守卫看不见的那一条。

现在这道守卫改为从 AST 枚举 `system=` 参数并解析模块级常量，因为一条提示词是靠
**它如何被传递**来识别的，而不是靠它碰巧怎么措辞。这一下立刻找出了另外五处未覆盖的
调用：存活探测、活动摘要（两种措辞）、决策抽取器、断言评判器和范围路由器。

`tesserae sessions prune-internal` 现在除了 sqlite 之外也会清理**文件存储**——它之前
只清理 sqlite，而 `compile` 读的恰恰是文件存储，所以清理看上去什么都没做。它支持
`--dry-run`。

如果你已经跑了 Tesserae 一段时间，就执行它。然后重新编译；你的节点计数一直在度量噪声。

## 多台机器共享一个项目目录

Tesserae 里没有任何东西携带机器身份，因此共享的 `.tesserae/` 中每一份按机器区分的
状态，都被每台主机当成世上只有一台机器那样读写。

**会话记录可能被一台从未见过它们的主机删除。** `producer` 无法区分两台机器：每台主机
的扫描都盖上同一个常量，而它们的 `~/.claude` 根目录解析成同一个字符串，所以在一台
从未见过该转录的主机上，现有的两道安全关卡都通过了——它删掉了另一台机器的记录，还
报告成功。记录现在携带采集它的主机，而一台主机只修剪自己采集过的东西。

主机 id 持久化在 `~/.tesserae/host_id`（可用 `TESSERAE_HOST_ID` 覆盖），而不是从主机名
推导，因为用同一个镜像构建出来的舰队会重复使用主机名，一次碰撞就会把一台机器的记录
交给另一台。

另外三处碰撞也被修掉了：引擎的 pidfile 现在是 `daemon.<host>.pid`（存活判断原本是对
**本机**进程表做 `os.kill(pid, 0)`，对另一台机器的 pid 毫无意义）；Codex 扫描的水位线
现在按主机区分（一条共享的下限意味着最后运行的那台主机会把它推过另一台还没读过的
转录——那些转录就永远不会被导入）；`doctor --fix` 也完全不再碰别的主机的 pidfile。

**新增：`tesserae engine --harvest-only`。** 一台主机负责编译；其他每台主机只跟踪自己
能看到的转录，从不去取编译锁。这是把争用消除掉，而不是去仲裁它。

## 后台引擎不再挡住你

`compile` 和 `refresh` 新增 `--wait [SECONDS]`：它会排队等待项目的编译锁，而不是以 2
退出，期间每五秒报告一次，并指出锁在哪台机器手里。后台守护进程现在改为按指数退避
（上限 60s）推迟执行，而不是把触发丢掉。

`--wait` 是一个显式标志，而不是从 stderr 是不是终端推断出来的：同一条命令不能在 `tee`
下、在 tmux 捕获里、在 CI 中表现出不同的行为。它是有界的，因为 `flock` 不提供公平性，
因此也就没有饥饿上界。

## `compile --all` / `refresh --all`

一条命令跑遍每一个已注册的项目，并按项目隔离失败——一个项目失败不会让其他项目停下。
编译锁被占用的项目报告为 **locked**（锁定）而不是 **failed**（失败），并有自己的退出码：
在一支舰队上这才是常态，而给它和 traceback 一样的退出码，只会教会人们忽略退出码。
`--jobs` 默认为 1，因为编译是 LLM 密集型的。

## 项目级 LLM 配置现在真的能到达客户端

`ProjectWiki._build_json_client` 解析了项目配置，然后调用客户端工厂时**没把它传进去**，
于是工厂只依据环境变量加全局配置重新解析了一遍，丢弃了每一个项目级的 `llm_model`、
`llm_base_url` 和 `llm_api_key`。写进 `.tesserae/config.json` 的自定义端点从来没到达过
客户端，而编译就这么悄无声息地跑在默认后端上。

文档描述的一直是正确的行为——只有代码不同意，而这是一个 bug 能有的最糟糕的形态，因为
它不给你任何理由去怀疑这个工具。

重复传 `--claude-config-dir` 同样会塌缩成第一个账户，因为 `CLAUDE_CONFIG_DIR` 是标量。
完整的有序列表现在通过 `TESSERAE_CLAUDE_CONFIG_DIRS` 传递。

## 诚实的报告

`tesserae init` 现在会注册项目。在此之前，照着 README 的快速上手走，得到的 `ask` 解析
不了 cwd 别名，于是回退到联邦范围，用属于无关仓库的 19,744 个节点去回答一个关于三个
文件的项目的问题——与此同时，`--scope current` 在一个已注册项目内部却以 2 退出，说
"not inside a registered project"。

`compile` 现在在**每一个**文档都回退到确定性抽取时以 1 退出。它原本打印一份摘要就以 0
退出，于是一张没有概念层的图读起来像是成功，而 `query` 随后什么都匹配不到。

`doctor` 不再仅凭那些只能证明 CLI 曾经被用过的文件就报告 `credentialed LLM CLI`——它
曾经在 `compile` 因认证而失败的同一秒里打出绿色对勾。**这是置信度的下调，而不是能力的
提升**：验证凭据要付出一次真实的 LLM 调用，所以这项检查现在只陈述它确实验证过的东西。

新增仅作报告用途的 `filesystem_locking` 检查。这里的每一条并发保证，都建立在持有
`.tesserae/` 的文件系统会真正强制执行 `flock(2)` 之上，而在 NFS 或 SMB 上这取决于配置
——没有可用的锁守护进程，`flock` 可能悄无声息地退化成空操作。它会在网络文件系统上发出
警告，并明确指出单台主机**无法**证明跨主机的强制执行。如果你从多台机器针对共享存储
运行 Tesserae，请直接测试这一点。

## 并发写入

五个工件写入器都通过同一个固定的临时路径发布——注意 `with_suffix` 是*替换*后缀，所以
`graph.json` 是通过 `.tesserae/graph.tmp` 发布的。两个发布者交错写进同一个文件，然后把
混合物重命名到位。其中 manifest 那个影响最大：`_load_manifest` 调用 `json.loads` 时毫无
防护，于是一份被交错写坏的 manifest 会让之后每一台主机上的每一次编译都抛错。

`TESSERAE_REGISTRY` 现在被每一条命令遵守，而不再只被引擎的舰队模式遵守。

## 升级

无需任何操作。单机安装的行为与以前完全一致；主机字段是增量的，没有该字段的记录会被
原样放着，直到你传 `--adopt-unowned`。

有两件事值得跑一次：

```bash
tesserae sessions prune-internal --dry-run   # see how much of your store is noise
tesserae sessions prune-internal             # then clean it
tesserae compile                             # and rebuild on what is left
```
