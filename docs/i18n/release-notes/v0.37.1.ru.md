Выпущено **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [Релиз на GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

Настройка пользовательского провайдера LLM не работала по трём независимым
причинам, и симптом каждый раз был ошибкой о модели, которую вы никогда не
настраивали. Аудит кода провайдера обнаружил 23 дефекта; этот выпуск их исправляет.

## Проводной протокол никогда не был смоделирован

`llm_provider` смешивал *какой бэкенд* с *каким HTTP диалектом*, и `custom`
всегда создавал клиент Anthropic, который отправляет POST на
`{base}/v1/messages`. Каждый совместимый с OpenAI сервер — vLLM, LiteLLM,
OpenRouter, Together, Ollama, LM Studio — отвечает на это 404. Единственный класс,
который говорит на `chat/completions`, не был создан никаким путём кода и
жёстко кодировал `api.openai.com`, поэтому он также не мог служить вашей
конечной точке.

`llm_api_style` теперь называет провод и это единственное, что выбирает клиент.
Если не установлено, для `custom` остаётся `anthropic`, поэтому существующая
пользовательская конфигурация ведёт себя ровно как раньше.

```bash
# OpenAI-совместимая конечная точка (vLLM, LiteLLM, OpenRouter, Ollama, LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# Anthropic-совместимая конечная точка — никакого /v1, SDK добавляет его
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## Модель была отброшена, и что-то другое ответило

Настроенная `llm_model` была ограничена в зависимости от того, какой
*слой* конфигурации предоставил `llm_provider` — задайте провайдер флагом и
модель в файл конфигурации и ваша модель была отброшена в пользу жёстко
кодированного значения по умолчанию. Пользовательская конечная точка
затем попадала в Claude CLI, который был запущен с `--model sonnet` против
вашего собственного базового URL и сообщал об неподдерживаемой модели. Ничего
не называло настоящую причину.

Явно настроенный провайдер **конечной точки** (`anthropic`, `openai`, `custom`)
теперь является контрактом: он создаётся один, и при ошибке выбрасывается
исключение, называющее провайдер, провод, базовый URL, модель и какой вид
учётных данных использовался. `llm_allow_fallback: true` восстанавливает старую
цепочку. Два OAuth CLI по-прежнему подменяют друг друга, так как ни один из них
не несёт конечную точку вас.

## Учётные данные авторизации отсутствовали

Одна `llm_api_key` отправлялась как `X-Api-Key` SDK и как маркер носителя CLI,
и передача её в SDK подавляла собственное разрешение auth-token SDK — так что
шлюз, желающий `Authorization: Bearer`, был недостижим. `llm_auth_token` —
учётные данные авторизации на обоих проводах.

## Конфигурация, которую вы можете видеть

Один приоритет для каждого ключа: окружение `TESSERAE_LLM_*` → проект
`.tesserae/config.json` → `~/.tesserae/config.json` → значение по умолчанию,
с унаследованными переменными `ANTHROPIC_*` на ступень ниже. Распознаватель
записывает, какой слой выиграл каждый ключ, и `tesserae config status`
выводит это — раньше он угадывал и приписывал переменную окружения, которую
распознаватель намеренно игнорирует. Вывод также показывает провод, вид
учётных данных и клиент, обслужившей зонд.

`ask`, `query`, lint, сводки MCP и демон двигателя разрешались только против
окружения и глобальной конфигурации, поэтому конечная точка уровня проекта
была использована `compile` и тихо игнорирована везде ещё. Теперь все читают
проект.

## Кроме того

- Неправильный `llm_provider` сообщается вместо тихого превращения в `claude`.
- Базовые URL Anthropic нормализованы, исправляя дублированный `/v1/v1/messages`,
  который документирует собственный быстрый старт этого проекта.
- `401`/`403` классифицируются как отказы аутентификации, а `404`/отсутствие
  модели как отказы конечной точки, а не все как "unavailable".
- `init` и `setup` сохраняют новые ключи; раньше они принимали и отбрасывали их.

## Обновление

Мигрировать нечего. Видны два изменения: явный провайдер конечной точки больше
не откатывается к другому бэкенду, и `config status` выводит *вид* учётных
данных, а не `set`/`unset`.
