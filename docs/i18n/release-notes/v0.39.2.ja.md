公開日 **2026-09-08** · [PyPI](https://pypi.org/project/tesserae/0.39.2/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.2) · `pip install --upgrade tesserae==0.39.2`

同じ場所に 2 つの穴があった。LLM バックエンドが実際に動くかを何も教えてくれず、`doctor --fix` は始めた仕事を終えなかった。

## 何が起きたか

`doctor --fix` は各修復をレジストリ順に 1 回だけ適用していた。先行するチェックを無効にする修復は、誰も実行すると知らない 2 回目の呼び出しにその仕事を残した: lint を直すと `graph.json` が書き換わり、そのためサイトが古くなるが、サイトのチェックはすでに過ぎていた。修復の実行は読み取り専用の実行と同じ表を出力したので、どの警告が意図的かを知るには 2 画面を突き合わせる必要があった。一方、バックエンドに触れる唯一のものは、設定を印字する副作用として 1 回呼び出す `config status --ping` だけだった。

## 何が変わったか

- **`doctor --fix` は収束する。** あるパスが何も変えなくなるまで修復を繰り返し、上限は 3 回。パスの間にプロジェクトコンテキストを作り直すので、後のチェックが読むものを作り出す修復も反映される。
- **断ったものはすべて名指しされる。** まだ誤っているものは **Still open** の下にコマンドと理由とともに現れる。理由はそれを生んだ実行について正直だ: 読み取り専用の実行は、その所見が `--fix` で修復可能だと言い、修復が走って失敗したとは言わない。4 つの常設理由がすべての報告専用チェックを覆い — spend、install、authenticate、destroy — 理由なしにチェックを追加するとテストが落ちる。
- **さらに 3 つのチェックが自分を直す。** `config_valid` は `init` が書く値で欠けた必須キーをアトミックに補完する。パースできない設定は報告するだけで決して書き換えない。`--fix --deep` は遅いローカル修復を追加し、セッションチャンクのバックフィルから始まる。どの段階の修復もコンパイルを実行しない。
- **`tesserae test` がバックエンドの応答を証明する。** コンパイルと同じやり方で設定を解決し、同じクライアントを構築し、JSON 呼び出しを 1 回と散文呼び出しを 1 回使う。ゲートウェイは前者を提供して後者を拒むことがあるからだ。どちらもキャッシュしない。両方が返ったときだけ 0 で終了する。

## 使い方

```bash
tesserae test                 # resolve, build, one JSON call, one prose call
tesserae doctor --fix         # repeats until a pass changes nothing
tesserae doctor --fix --deep  # + the slow local repairs
```

## アップグレード

移行するものはない。`doctor --fix` は以前の約束をそのまま守る — 安全な修復だけ、コンパイルは決してせず、プロセスも決して kill しない — ただ今は繰り返し、何を残したかを報告する。`--fix` なしの `--deep` は 2 で終了する。
