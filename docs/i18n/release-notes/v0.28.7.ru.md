Released **2026-08-05** · [PyPI](https://pypi.org/project/tesserae/0.28.7/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.7) · `pip install --upgrade tesserae==0.28.7`

**Обновляйтесь, если другой инструмент пишет записи сессий в ваше хранилище Tesserae.**
[#104](https://github.com/ca1773130n/Tesserae/issues/104) было исправлено дважды, в 0.28.5 и 0.28.6, и при этом по-прежнему теряло эти записи оба раза. Данный релиз исправляет проблему по оси, которая действительно разделяет одного импортёра от другого.

## Что не получилось в двух более ранних исправлениях

Обе версии ограничивали удаление по *месту сканирования*: обнаружение могло удалить только записи, стенограмма которых находилась под корнем хареса, который оно прошло. Это рассуждение верно только если разные производители читают разные каталоги.

Они этого не делают. Оркестратор, экспортирующий свои собственные сессии агента, описывает те же **самые** стенограммы `~/.claude`, которые сканирует Tesserae локально — он просто несёт идентификацию агента, которую сканирование не может вывести. Его записи находились в пределах области по конструкции.

Измеренные на 0.28.6 в настоящем хранилище из 375 записей, две формы потери пережили исправление:

- **Удалено.** Запись, стенограмма которой больше не находится при сканировании, удаляется. Исходная ошибка, неизменная.
- **Перезаписано молча.** Запись, стенограмма которой *находится* при сканировании, заменяется на более простую версию при сканировании — идентификация агента и метаданные пропадают. Оба автора выводят одно имя файла из идентификатора сессии, поэтому один приземляется поверх другого. Ничего не удаляется, поэтому количество удалений остаётся 0 и запуск сообщает об успехе.

Вторая форма вообще не является проблемой обрезки, вот почему никакое уточнение области не достигало её.

## Происхождение

Каждая запись теперь содержит **`producer`** — импортёр, который её написал.
`sessions discover --import` проставляет `tesserae:discover`; `sessions import <path>`
проставляет `tesserae:import`. Автор может трогать только записи, которые он произвёл:

- он удаляет только свои;
- он **не** перезапишет запись другого производителя для той же сессии. Входящая запись пропускается и сообщается как
  `Left alone (written by another producer)`.

Если вы пишете в это хранилище из вашего собственного инструмента, используйте `tesserae sessions import
<file>` и ваши записи защищены с этого момента. Ничего больше не требуется.

Ограничения корня и хареса остаются как вторая защита, но они больше не то, что обеспечивает безопасность записей.

## Обновление

**Записи, написанные до этого релиза, не содержат производителя.** Они не имеют хозяина, поэтому ни один импортёр их не удаляет и не перезаписывает — обновление не может потерять то, что у вас уже есть, включая записи, которые написал другой инструмент.

Стоимость этого выбора: обнаружение также не обновит унаследованные записи. Если собственное сканирование Tesserae — единственное, что пишет в ваше хранилище, запустите

```bash
tesserae sessions discover --import --adopt-unowned
```

один раз, чтобы передать эти записи обнаружению. **Не запускайте это, если другой инструмент пишет в то же хранилище** — это делает ровно то, что говорит флаг.

Без потерь был правильным выбором по умолчанию. Исправляемая ошибка — это молчаливая потеря данных, и другой вариант по умолчанию разрушил бы записи проекта отчётности один последний раз при обновлении, которое должно было их защитить.

## Благодарность

Доложено, воспроизведено и диагностировано агентом, работающим над проектом
[Agented](https://github.com/ca1773130n/Agented), который потребляет Tesserae через его CLI. Они измеряли в настоящем хранилище, а не в приборе, вот почему они нашли то, что не нашли два раунда исправлений и пятирецензионный пересмотр кода — каждый написанный здесь тест означал, что «другой производитель» означает «другой каталог», поэтому тесты подтвердили предположение вместо проверки его. Они также предложили происхождение, направление, которое #104 предложил с самого начала.
