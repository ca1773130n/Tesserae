공개일 **2026-09-18** · [PyPI](https://pypi.org/project/tesserae/0.41.8/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.8) · `pip install --upgrade tesserae==0.41.8`

`tesserae init`과 `tesserae compile`은 자기 프로젝트를 머신 전역 레지스트리인
`~/.tesserae/registry.json`에 추가하고, 프로젝트 범위를 지정하지 않은 쿼리는 그 안의 모든 프로젝트를
검색합니다. 문제가 드러난 머신에서 레지스트리에는 디렉터리 204개에 걸쳐 항목 286개가 있었고, 그중
실제 프로젝트는 6개였습니다. 나머지는 벤치마크 실행, 에이전트의 임시 디렉터리, 테스트 하나가 남긴
일회용 프로젝트와, `init` 때 이름을 붙인 모든 프로젝트의 두 번째 별칭이었습니다.

## 무엇이 바뀌었나

- **두 번째 별칭이 생기지 않습니다.** `init --name`은 받은 이름으로 등록하는데, 그 뒤의 컴파일은
  `--name`이 없어서 디렉터리 이름으로도 등록했습니다. HypePaper는 만드는 전문가마다
  `hp-topic-<topic>`이라는 이름을 붙이므로, 전문가가 모두 두 번씩 올라 있었습니다. 이제 어떤 별칭으로든
  이미 레지스트리에 있는 디렉터리는 그대로 둡니다.
- **벤치마크 실행은 자기 프로젝트를 자기 안에 둡니다.** DeepScholar, growth, LongMemEval, LoCoMo
  하니스는 쿼리나 대화마다 프로젝트를 하나씩 만듭니다. 이제 이들의 `init`과 `compile`은 작업
  디렉터리 안의 레지스트리를 씁니다. DeepScholar 실행 한 번이 `0`부터 `62`까지 이름 붙은 프로젝트
  63개를 남긴 적이 있습니다.
- **테스트 스위트가 더 이상 사용자 레지스트리에 쓰지 않습니다.** 테스트 하나가 스위트의 레지스트리
  격리가 닿지 않는 하위 프로세스에서 `init`을 실행해, 임시 디렉터리 아래의 `cwd_wiki`를 등록했습니다.

## 업그레이드

이전할 것은 없습니다. 레지스트리에 이미 있는 항목은 지울 때까지 남습니다.
`tesserae projects list`로 확인하고, `tesserae projects unregister <name>`으로 하나씩 지울 수
있습니다. 프로젝트 자체는 건드리지 않습니다.
