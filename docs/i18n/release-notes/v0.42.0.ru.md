Выпущено **2026-10-06** · [PyPI](https://pypi.org/project/tesserae/0.42.0/) · [Релиз на GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.42.0) · `pip install --upgrade tesserae==0.42.0`

Словарь узлов и рёбер был закрытым: новый тип связи требовал нового релиза, а граф,
который его использовал, не читался более старой установкой. Хост, который каждую
неделю расширяет собственную онтологию, так работать не может. Этот релиз позволяет
хосту регистрировать типы во время работы, каждый под базовым родителем, и любой
записанный хостом файл по-прежнему загружается в 0.41.

## Что изменилось

- **Реестр типов.** `tesserae.type_registry` хранит записи `TypeSpec`, зарегистрированные
  из кода, из JSON-файла или через `TESSERAE_TYPE_REGISTRY`. Каждый тип указывает
  `core_parent`. Узлы сохраняют базовый тип, а более точный вид хранят в
  `metadata.subtype`. Активный тип ребра из реестра принимается в памяти.
- **Мягкая загрузка.** `TESSERAE_TYPE_MODE=lenient` сопоставляет незнакомый читателю тип
  с его родителем в реестре, а иначе с `Concept` или `references`. Исходный тип
  сохраняется в `metadata.raw_type` и учитывается в `load_stats`. По умолчанию
  по-прежнему действует `strict`, который выбрасывает исключение точно так же, как раньше.
- **Представления из реестра.** Тип из реестра попадает в объявленное представление,
  а иначе в представление родителя. Новое представление `crossdomain` содержит
  междисциплинарные связи вроде `transfers_to` и `inspired_by`. Пока хост их не
  зарегистрирует, оно пусто.
- **Уверенность и статус рёбер.** У рёбер есть необязательные `confidence`, `status`,
  `asserted_by`, `valid_from`, `invalid_at` и `provenance`. PPR умножает вес типа на
  `confidence` и пропускает рёбра `candidate`, `refuted` и `retracted`, если их не
  запросили явно. Опровергнутое ребро `supersedes` больше не скрывает свою цель.
- **Резолвер содержимого.** `compile_context(content_resolver=...)` сначала запрашивает
  содержимое узла у хоста, начиная с самого дешёвого представления, и только потом
  переходит к странице вики и описанию. Цитаты перечисляют использованные ссылки.
- **Идентичность понятий.** Федерация объединяет узлы с общим `metadata.concept_id`,
  Wikidata QID или классом MSC2020. `federate_graphs(identity_resolver=...)` позволяет
  хосту передавать идентичности из своих таблиц, не меняя ни одного `graph.json`.
- **Дрейф схемы.** `analyze_schema_drift(kind="edge")` предлагает подотношения,
  `embedder` заменяет Jaccard по токенам имён, записи журнала несут метрики гейта, а
  `apply_ledger_to_registry` записывает одобренные предложения в файл реестра. Тип узла
  он никогда не меняет.
- **Ограниченный запрос соседей.** `store_neighbors` и `store_iterate_edges` используют
  собственные `neighbors` / `iterate_edges` хранилища, если они есть, а иначе работают
  через запасной путь. Сам `GraphStore` не изменился.
- **Рёбра только для производителей.** `transfers_to`, `candidate_transfer`,
  `analogous_to` и `merged_into` никогда не извлекаются LLM и не записываются
  агентом: ни как тип ребра, ни как тип из реестра, унаследованный от них, ни как
  `metadata.relation` на базовом ребре, а именно так хранится мост. Записать их может
  только код хоста, который сам является производителем, передав
  `allow_producer_only=True` в `record_agent_write`. Инструмент MCP `graph_write`
  никогда его не передаёт, какой бы `agent` ни назвал клиент.
- **Записи агентов.** `graph_write` сопоставляет тип из реестра с его базовым родителем
  до записи и добавляет `metadata.subtype` или `metadata.relation`. Рёбра могут
  содержать `metadata`.

## Совместимость

`graph.json` из 0.41 загружается в строгом режиме с теми же числами узлов, рёбер и
типов. Граф без новых полей сериализуется байт в байт как раньше. Ничто из того, что
этот релиз записывает в `graph.json` или `agent-writes.jsonl`, не использует типы из
реестра, поэтому возврат на 0.41 остаётся безопасным.

## Обновление

Миграция не нужна. Без реестра все значения по умолчанию ведут себя как в 0.41.
