Veröffentlicht am **2026-09-11** · [PyPI](https://pypi.org/project/tesserae/0.40.0/) · [GitHub-Release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.40.0) · `pip install --upgrade tesserae==0.40.0`

Seit v0.5.0 ist der inkrementelle Compiler hinter einem ausgeschalteten Flag ausgeliefert worden, als experimentell gekennzeichnet, mit einem Byte-Parität-Gate, das sagte, es sei für sieben Bearbeitungsformen bewiesen. Dieses Release aktiviert das Flag. Zuvor musste das Gate ehrlich gemacht werden.

## Was passiert ist

Das Parität-Gate verglich eine inkrementelle Kompilierung mit einer vollständigen und fand sie byte-identisch. Es verglich eine vollständige Kompilierung mit einer vollständigen Kompilierung. Kantenprovenienz wurde gegen IDs von vor der Kanonisierung aufgezeichnet, also bei einer 4-Paper-Fixture 8 korrekte Kanten 4 Provenienzeilen hatten, der Bereitschaftscheck antwortete nein, und jeder inkrementelle Arm beschleunigt stillschweigend zu einer vollständigen Recompile. Das Gate behauptet jetzt `mode == "incremental"` aus dem Build-Ledger. Mit der Remap behoben und inkrementell tatsächlich laufend, sieben Tests fehlgeschlagen. Alle sieben sind geschlossen: Multi-Owner-Payloads re-extrahieren die Owner-Union, Producer-owned Layers werden entfernt und regeneriert, umbenannte Dateien behalten die Aliase, die ein vollständiger Compile faltet, und drei subtraktive Lecks, die behielten, was ein vollständiger Compile ablegt.

Gemessen an der echten 1,422-Datei-Corpus berührt eine korrekte Owner-Union einen Median von 24 Dateien pro Bearbeitung. Das ist, was „inkrementell" jetzt kostet.

## Was sich geändert hat

- **`incremental_compile` ist standardmäßig an.** Eine nur-geänderte Kompilierung auf einem Standard-Projekt läuft inkrementell, und die Ledger-Zeile sagt das. `incremental_compile: false` opt-out zurück zu vollständiger Recompile.
- **Das Build-Ledger erfasst, was eine Kompilierung gekostet hat.** Jede `.build-history.jsonl`-Zeile trägt den Modus, die Dauer, wie viele Quellen extrahiert wurden, und der Grund für jeden Downgrade zu einer vollständigen Kompilierung.
- **Sidecars werden gekürzt.** `node_memory` und `fact_observed` wurden nie abgestimmt; auf einem 1.19 GB Store gehörten 95% der `node_memory` Zeilen zu Knoten, die nicht mehr existierten. Vollständige Compilierungen kürzen jetzt, und `doctor` meldet den Speicherverschleiß. Gemessen: 0.42 GB nachher, 65% zurückgefordert.
- **`tesserae engine --serve` stellt die Site vom Daemon dar.** Gleicher Handler wie `tesserae serve`, einschließlich `/api/ask`, auf einem eigenen Thread, gestoppt durch einen expliziten Closer beim Herunterfahren. Ein Bind-Fehler protokolliert, und die Engine kompiliert weiter. Fleet-Modus stellt niemals dar; `--serve` lehnt `--once`, `--harvest-only` und `--all` ab.
- **Der Site-Build ist ein atomarer Tausch.** Das Compile löschte früher `.tesserae/site` und schrieb es um, also eine bereite Seite 404'd während der Länge einer Kompilierung. Der Build landet jetzt in einem Staging-Directory und wird mit der Live-Site in einem Syscall ausgetauscht. Ein Leser, der den bereitgestellten Index während dreier Rebuilds hämmert, sieht null Misses; gegen den alten Pfad sah er 33,202.
- **`tesserae serve` ist gewindelt.** Ein LLM `/api/ask` blockiert nicht länger jedes statische Asset dahinter.
- **Ein gescheiterter Pages-Push klemmt das Repo nicht mehr fest.** `deploy.py` entfernt den Worktree, den er bei jedem Exitpfad erzeugt hat, und kürzt stale Registrierungen zuerst.
- **`tesserae/frontend.py` ist gelöscht.** 648 Zeilen toter Code hinter einer Einzeiler-Rebind; ein Test hält sie weg.

## Upgrade

Das erste nur-geänderte Compile nach dem Upgrade läuft inkrementell. Wenn ein Graph danach falsch aussieht, ist `tesserae compile` immer noch ein vollständiges Compile und `incremental_compile: false` in `.tesserae/config.json` stellt die alte Standard wieder her. Das Veröffentlichen bleibt absichtlich manuell: `deploy` braucht einen sauberen Tree und `gh-pages` ist weltweit lesbar, also nichts im Daemon drückt.
