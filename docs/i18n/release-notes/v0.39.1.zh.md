发布于 **2026-09-07** · [PyPI](https://pypi.org/project/tesserae/0.39.1/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.1) · `pip install --upgrade tesserae==0.39.1`

把 `claude` 提供方指向你自己的网关——基础 URL、Bearer 令牌、一个不是 `~/.claude` 的配置目录——Tesserae 仍然照用 CLI 的默认账号。不是一个 bug，而是每个入口各一个。

## 发生了什么

`ClaudeCLIJsonClient` 没有任何办法接收 `llm_auth_token`，所以 CLI 到达网关时没有凭据，退回到其配置目录里的登录。`tesserae ask`、`query --llm`、活动摘要和守护进程在构建客户端时没有带上配置的 `llm_claude_config_dirs`，在机器上的每个 `~/.claude*` 之间轮转，而 `compile` 却遵守该列表。`init --yes` 和向导接受了 `--llm-auth-token` 和 `--llm-api-style`，却在写入计划之前把两者都丢掉了。剪藏 TL;DR 自己调用 `claude`。还有旧向导写入的两个键 `llm_claude_config_dir` 和 `extraction.claude_config_dir` 没有任何代码读取，所以安装时选的目录从未生效。

## 变更内容

- **每个入口都把端点和令牌交给 CLI。** 构建器把 `llm_base_url`、`llm_api_key` 和 `llm_auth_token` 一起传递，子进程以 `ANTHROPIC_BASE_URL` 和 `ANTHROPIC_AUTH_TOKEN` 看到它们。已用空配置目录对真实的 `claude -p` 验证：请求带着 Bearer 令牌到达 `/v1/messages`，全程不涉及 `claude /login`。
- **配置的配置目录在任何地方都被遵守，包括 `~`。** 轮转客户端从解析后的设置读取 `llm_claude_config_dirs`；`~/.claude*` 之外的配置目录也算可用；旧的单数键和 `extraction.claude_config_dir` 作为项目配置排在复数键之下；`config status` 会说明是哪一层胜出，而不是打印 `default`。
- **`init`、`setup` 和向导保留每一个选项。** `--llm-auth-token` 和 `--llm-api-style` 在向导路径上也会持久化；在 `claude` 提供方下，向导现在会询问端点和 Bearer 令牌。
- **Doctor 和剪藏 TL;DR 遵循同一套配置。** `llm_login` 会报告被路由的 CLI 无需登录；剪藏摘要改为带着项目设置走 `build_default_json_client`，而不是自行调用 `claude`。

## 升级

如果旧向导在你的 `.tesserae/config.json` 里留下了 `extraction.claude_config_dir`，从现在起该目录会被遵守。运行 `tesserae config status --no-ping` 查看哪一层胜出；要更改就设置 `llm_claude_config_dirs`。其他无需迁移。
