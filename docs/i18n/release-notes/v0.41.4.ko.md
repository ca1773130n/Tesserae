공개일 **2026-09-17** · [PyPI](https://pypi.org/project/tesserae/0.41.4/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.4) · `pip install --upgrade tesserae==0.41.4`

`engine --serve`와 `engine --proactive`는 단위 테스트와 함께 출시됐지만, 실제 머신에서
처음부터 끝까지 실행해 본 적은 없었습니다. 실행해 보니 결함이 두 개 나왔고, 둘 다 엔진이 시작하는
방식과 컴파일을 일으키는 조건에 있었습니다. `--proactive` 자체는 제대로 동작했습니다.

## 무엇이 바뀌었나

- **엔진이 곧바로 서빙을 시작합니다.** 프로젝트에서 처음 실행될 때 세션 테일러는 머신에 있는
  모든 Codex 트랜스크립트를 읽어 그 프로젝트에 속한 것을 찾습니다. 이 읽기가 다른 어떤 것보다 먼저
  실행됐습니다. 트랜스크립트가 15 GB인 머신에서 `engine --serve`는 344초 동안 어떤 요청에도
  응답하지 않았고 그동안 SIGTERM도 무시했기 때문에, 감독 프로세스가 강제로 종료해야 했고 낡은
  pidfile이 남았습니다. 이제 이 읽기는 별도 스레드에서 실행됩니다.
- **컴파일이 또 다른 컴파일을 예약하지 않습니다.** 컴파일할 때마다 Obsidian 볼트를 다시 쓰는데,
  볼트 감시자는 그 쓰기를 사용자 편집으로 받아들였습니다. `applied (no changes)`를 기록한 뒤에도
  매번 전체 재컴파일을 대기열에 넣었습니다. 문서 하나를 고치면 컴파일이 세 번 돌았고 그중 두 번은
  전체 컴파일이었습니다. 이제 엔진은 볼트 편집이 그래프를 바꿨을 때만 다시 컴파일합니다.

## 업그레이드

이전할 것은 없습니다. 엔진이 실행 중이라면 재시작하세요. 실행 중인 프로세스는 이전 코드를 그대로
들고 있습니다.
