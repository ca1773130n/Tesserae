发布于 **2026-09-11** · [PyPI](https://pypi.org/project/tesserae/0.40.0/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.40.0) · `pip install --upgrade tesserae==0.40.0`

自 v0.5.0 以来，增量编译器一直在关闭的标志后面发布，标记为实验性的，配备了一个字节奇偶性门来宣称它已为七种编辑形式证明。此版本打开了该标志。在此之前，必须使该门真实可信。

## 发生了什么

奇偶性门将增量编译与完整编译进行比较，发现它们字节相同。但它实际上是在比较一个完整编译和另一个完整编译。边缘溯源是针对规范化前的 id 记录的，所以在一个 4 篇论文的装置上，8 条正确的边有 4 行溯源，准备就绪检查回答否，每个增量臂都默默降级为完整重新编译。该门现在从构建分类账中断言 `mode == "incremental"`。随着重新映射被修复和增量实际运行，七个测试失败了。全部七个都已解决：多所有者有效负载重新提取所有者并集，生产者拥有的层被剥离并重新生成，重命名文件保持完整编译折叠的别名，三个减法泄漏保留了完整编译会删除的内容。

在真实的 1,422 文件语料库上测量，正确的所有者并集每次编辑接触中值 24 个文件。这就是"增量"现在的成本。

## 改了什么

- **`incremental_compile` 默认打开。** 默认项目上的仅改变编译以增量方式运行，分类账行也这样说。`incremental_compile: false` 选择退出到完整重新编译。
- **构建分类账记录编译的成本。** 每个 `.build-history.jsonl` 行都携带模式、持续时间、提取了多少源，以及任何降级到完整编译的原因。
- **边车被修剪。** `node_memory` 和 `fact_observed` 从未调和；在一个 1.19 GB 存储上，95% 的 `node_memory` 行属于不再存在的节点。完整编译现在修剪它们，`doctor` 报告膨胀。测量：之后 0.42 GB，回收 65%。
- **`tesserae engine --serve` 从守护进程提供站点。** 与 `tesserae serve` 相同的处理程序，包括 `/api/ask`，在其自己的线程上，由关闭时的显式关闭器停止。绑定失败日志并且引擎继续编译。Fleet 模式永不提供；`--serve` 拒绝 `--once`、`--harvest-only` 和 `--all`。
- **站点构建是原子交换。** 编译过去会删除 `.tesserae/site` 并重写它，所以已提供的页面在编译期间会 404。构建现在落在暂存目录中，在一个系统调用中与活站点交换。一个在三次重建过程中持续请求已提供索引的读者看到零失误；对着旧路径它看到 33,202。
- **`tesserae serve` 是多线程的。** 一个 LLM `/api/ask` 不再阻止它后面的每个静态资产。
- **失败的 Pages push 不再卡住仓库。** `deploy.py` 在每个退出路径上移除它创建的工作树，并首先修剪陈旧的注册。
- **`tesserae/frontend.py` 被删除。** 648 行通过一条线变化隐藏的死代码；一个测试确保它保持删除。

## 升级

升级后的第一个仅改变编译以增量方式运行。如果之后图谱看起来错误，`tesserae compile` 仍然是完整编译，`.tesserae/config.json` 中的 `incremental_compile: false` 恢复旧默认值。发布保持手动是有意的：`deploy` 需要一棵干净的树，`gh-pages` 是世界可读的，所以守护进程不会进行任何推送。
