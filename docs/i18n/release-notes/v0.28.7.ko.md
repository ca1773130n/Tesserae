Released **2026-08-05** · [PyPI](https://pypi.org/project/tesserae/0.28.7/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.7) · `pip install --upgrade tesserae==0.28.7`

**다른 도구가 Tesserae 저장소에 세션 레코드를 기록한다면 업그레이드하세요.**
[#104](https://github.com/ca1773130n/Tesserae/issues/104)는 0.28.5와 0.28.6에서 두 번 수정됐으나 두 번 모두 여전히 그 레코드들을 잃고 있었습니다. 이 릴리스는 한 생산자를 다른 생산자와 실제로 분리하는 축에서 이를 고칩니다.

## 이전의 두 수정이 놓친 것

둘 다 스캔이 본 *위치*에 따라 제거 범위를 정했습니다. discovery는 걸었던 harness 루트 아래에 사는 트랜스크립트를 가진 레코드만 삭제할 수 있다는 추론이었습니다. 이 추론은 다른 생산자들이 다른 디렉토리를 읽는 경우에만 유지됩니다.

그들은 그렇지 않습니다. Tesserae의 로컬 스캔이 읽는 **같은** `~/.claude` 트랜스크립트를 설명하는 orchestrator가 자신의 에이전트 세션을 내보냅니다 — 단지 스캔이 추론할 수 없는 에이전트 신원을 가지고 있을 뿐입니다. 그 레코드는 구성상 범위 내에 있었습니다.

0.28.6에 대해 실제 375개-레코드 저장소에서 측정하면, 손실의 두 형태가 생존했습니다:

- **삭제됨.** 트랜스크립트를 스캔이 더 이상 찾지 못하는 레코드는 제거됩니다. 원래 버그이며 변함없습니다.
- **조용히 덮어씌워짐.** 트랜스크립트를 스캔이 *찾는* 레코드는 스캔의 더 단순한 버전으로 교체됩니다 — 에이전트 신원과 메타데이터가 사라집니다. 두 라이터 모두 세션 id에서 같은 파일명을 유도하므로 하나가 다른 하나 위에 착지합니다. 아무것도 삭제되지 않으므로 제거 수는 0으로 유지되고 실행은 성공을 보고합니다.

두 번째 형태는 제거 문제가 아니며, 이것이 범위 정제가 도달하지 못한 이유입니다.

## 출처

모든 레코드는 이제 **`producer`**를 가집니다 — 그것을 기록한 임포터입니다.
`sessions discover --import`는 `tesserae:discover`를 도장 찍습니다; `sessions import <path>`는 `tesserae:import`를 도장 찍습니다. 라이터는 자신이 생산한 레코드에만 접근할 수 있습니다:

- 자신의 것만 제거합니다;
- 같은 세션에 대해 다른 생산자의 레코드를 덮어쓰지 **않습니다.** 수신 쓰기는 건너뛰어지고
  `Left alone (written by another producer)`로 보고됩니다.

자신의 도구에서 이 저장소에 기록한다면, `tesserae sessions import <file>`을 사용하면 그 이후로 레코드가 보호됩니다. 다른 것은 필요하지 않습니다.

Root와 harness 범위 지정은 두 번째 게이트로 유지되지만, 더 이상 레코드를 안전하게 유지하는 것이 아닙니다.

## 업그레이드

**이 릴리스 이전에 기록된 레코드는 생산자를 가지지 않습니다.** 그들은 소유자 없으므로 임포터는 제거하거나 덮어쓰지 않습니다 — 업그레이드는 이미 있는 것을 잃을 수 없으며, 다른 도구가 기록한 레코드도 포함됩니다.

그 선택의 비용: discovery는 legacy 레코드를 새로고침하지 않을 것입니다. Tesserae의 자신의 스캔이 저장소에 기록하는 유일한 것이라면,

```bash
tesserae sessions discover --import --adopt-unowned
```

를 한 번 실행하여 그 레코드들을 discovery에 넘기세요. **다른 도구가 같은 저장소에 기록한다면 실행하지 마세요** — 플래그가 정확히 말하는 것을 합니다.

무손실이 올바른 기본값이었습니다. 고쳐지는 버그는 조용한 데이터 손실이며, 다른 기본값은 보호해야 하는 업그레이드에서 보고 프로젝트의 레코드를 마지막으로 한 번 더 파괴했을 것입니다.

## 크레딧

[Agented](https://github.com/ca1773130n/Agented) 프로젝트에서 작업 중인 에이전트가 보고, 재현 및 진단했습니다. 그 프로젝트는 CLI를 통해 Tesserae를 소비합니다. 그들은 fixture보다는 실제 저장소에 대해 측정했으며, 이것이 두 라운드의 수정과 다섯 검토자의 코드 검토에서 발견하지 못한 것을 발견한 이유입니다 — 여기서 작성된 모든 테스트는 "다른 생산자"를 "다른 디렉토리"라는 뜻으로 만들어 테스트는 가정을 확인했습니다. 그들은 또한 #104가 처음부터 제안한 방향인 출처를 제안했습니다.
