Released **2026-08-07** · [PyPI](https://pypi.org/project/tesserae/0.29.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.29.0) · `pip install --upgrade tesserae==0.29.0`

Этот релиз делает Tesserae пригодным к работе, когда несколько машин делят один диск, и исправляет две вещи, которые незаметно делали его результат хуже, чем он выглядел.

## Tesserae поглощал собственные вызовы LLM как ваши сессии

Каждая компиляция запускает CLI `claude` — один раз на документ и один раз на сессию. Каждый такой вызов пишет стенограмму в `~/.claude/projects`, а обнаружение сессий собирало их так, будто это была ваша работа над кодом. На собственном проекте мейнтейнера:

| | |
|---|---|
| сохранённых записей сессий | 14,605 |
| собственных вызовов извлечения Tesserae | **14,377 (98.4%)** |
| настоящих пользовательских сессий | 228 |

10,666 из них несли один и тот же заголовок — промпт извлечения.

Фильтр для этого уже существовал, как и тест, вся работа которого состояла в том, чтобы держать фильтр полным. Тест сканировал исходники на промпты, подходящие под `You (?:are|distill|write|decide|arbitrate|split)` — поддерживаемый вручную список разрешённых начальных **глаголов**. Промпт извлечения начинается с «You extract», поэтому самый частый промпт в системе оказался ровно тем единственным, которого защита не могла увидеть.

Теперь защита перечисляет аргументы `system=` из AST и разрешает константы уровня модуля, потому что промпт опознаётся по тому, **как он передаётся**, а не по тому, как он случайно сформулирован. Это сразу нашло ещё пять непокрытых вызовов: проверку живости, сводку активности (две формулировки), извлечение решений, судью утверждений и маршрутизатор области.

`tesserae sessions prune-internal` теперь чистит **файловое хранилище**, а не только sqlite — раньше он чистил только sqlite, а `compile` читает именно файловое хранилище, поэтому чистка выглядела так, будто она ничего не делает. Команда принимает `--dry-run`.

Если вы пользуетесь Tesserae какое-то время, запустите её. Затем перекомпилируйте: ваши счётчики узлов всё это время измеряли шум.

## Несколько машин с общим каталогом проекта

Ничто в Tesserae не несло идентичности машины, поэтому каждый кусок помашинного состояния, живущего в общем `.tesserae/`, читался и писался каждым хостом так, будто хост был только один.

**Записи сессий мог удалить хост, который их вообще не видел.** `producer` не способен разделить две машины: сканирование каждого хоста проставляет одну и ту же константу, а их корни `~/.claude` разрешаются в одну и ту же строку, поэтому обе существующие защиты пропускали хост, который никогда не видел стенограмму, — и он удалял запись другой машины, отчитываясь об успехе. Теперь записи несут хост, который их собрал, и хост подчищает только то, что собрал сам.

Идентификатор хоста сохраняется в `~/.tesserae/host_id` (переопределяется через `TESSERAE_HOST_ID`), а не выводится из имени машины, потому что парк, развёрнутый из одного образа, переиспользует имена хостов, и коллизия отдала бы записи одной машины другой.

Исправлены ещё три коллизии: pidfile движка теперь `daemon.<host>.pid` (проверка живости была `os.kill(pid, 0)` по **локальной** таблице процессов — бессмысленно для pid чужой машины), водяной знак сканирования Codex теперь отдельный на каждый хост (один общий нижний порог означал, что хост, отработавший последним, сдвигал его за стенограммы, которые другой ещё не прочитал, — они не импортировались уже никогда), и `doctor --fix` вообще не трогает pidfile чужого хоста.

**Новое: `tesserae engine --harvest-only`.** Один хост компилирует; каждый другой только вычитывает доступные ему стенограммы и никогда не берёт блокировку компиляции. Это убирает конкуренцию, а не разруливает её.

## Фоновый движок больше вас не блокирует

`compile` и `refresh` принимают `--wait [SECONDS]`: вместо выхода с кодом 2 команда встаёт в очередь за блокировкой компиляции проекта, отчитывается каждые пять секунд и называет машину, которая эту блокировку держит. Фоновый демон теперь откладывает работу с экспоненциальной выдержкой, ограниченной 60 секундами, вместо того чтобы терять свой триггер.

`--wait` — явный флаг, а не поведение, выведенное из того, является ли stderr терминалом: одна и та же команда не должна вести себя иначе под `tee`, при захвате в tmux или в CI. Ожидание ограничено по времени, потому что `flock` не даёт никакой справедливости и, следовательно, никакой границы на голодание.

## `compile --all` / `refresh --all`

Одна команда по всем зарегистрированным проектам, с изоляцией отказов по проектам — падение одного проекта не останавливает остальные. Проект, чья блокировка компиляции занята, отчитывается как **locked**, а не **failed**, и получает собственный код выхода: в парке машин это нормальное состояние, а если дать ему тот же код, что и трейсбеку, люди научатся игнорировать код выхода. `--jobs` по умолчанию равен 1, потому что компиляция тяжела по LLM.

## Конфигурация LLM уровня проекта наконец доходит до клиента

`ProjectWiki._build_json_client` разрешал конфигурацию проекта, а затем вызывал фабрику клиента **без неё**, поэтому фабрика заново разрешала настройки только по переменным окружения и глобальной конфигурации и отбрасывала любые `llm_model`, `llm_base_url` и `llm_api_key` уровня проекта. Собственный endpoint, прописанный в `.tesserae/config.json`, никогда не доходил до клиента, и компиляция молча шла на бэкенде по умолчанию.

Документация уже описывала правильное поведение — не соглашался с ней только код, и это худшая форма, которую может принять ошибка, потому что она не даёт вам ни одной причины заподозрить инструмент.

Повторённый `--claude-config-dir` тоже схлопывался до первого аккаунта, поскольку `CLAUDE_CONFIG_DIR` — скаляр. Теперь полный упорядоченный список едет в `TESSERAE_CLAUDE_CONFIG_DIRS`.

## Честная отчётность

`tesserae init` теперь регистрирует проект. Без этого прохождение быстрого старта из README давало `ask`, который не мог разрешить алиас рабочего каталога, откатывался к федеративной области и отвечал на вопрос о проекте из трёх файлов, опираясь на 19,744 узла из посторонних репозиториев, — тогда как `--scope current` выходил с кодом 2 и сообщением «not inside a registered project», находясь внутри зарегистрированного проекта.

`compile` теперь выходит с кодом 1, когда **каждый** документ откатился на детерминированное извлечение. Раньше он печатал сводку и выходил с кодом 0, поэтому граф без концептуального слоя читался как успех, а `query` затем не находил ничего.

`doctor` больше не сообщает `credentialed LLM CLI` на основании файлов, которые доказывают лишь то, что CLI когда-то использовали, — он печатал зелёную галочку в ту же секунду, когда `compile` падал на аутентификации. **Это понижение уверенности, а не повышение возможностей**: проверка учётных данных стоит настоящего вызова LLM, поэтому проверка теперь заявляет только то, что она действительно проверила.

Новая проверка `filesystem_locking`, только для отчёта. Все гарантии параллелизма здесь держатся на том, что `flock(2)` обеспечивается файловой системой, на которой лежит `.tesserae/`, а поверх NFS или SMB это зависит от конфигурации: без работающего lock-демона `flock` может молча выродиться в no-op. Проверка предупреждает на сетевой файловой системе и прямо заявляет, что один хост **не может** доказать соблюдение блокировок между хостами. Если вы запускаете Tesserae с нескольких машин поверх общего хранилища, проверьте это напрямую.

## Параллельная запись

Пять писателей артефактов публиковались через один фиксированный временный путь — заметьте, что `with_suffix` *заменяет* суффикс, поэтому `graph.json` публиковался через `.tesserae/graph.tmp`. Двое публикующих переплетались в этом одном файле, и получившаяся смесь переименовывалась на место. Больше всего значил случай с манифестом: `_load_manifest` вызывает `json.loads` без защиты, поэтому переплетённый манифест валил каждую последующую компиляцию на каждом хосте.

`TESSERAE_REGISTRY` теперь учитывается каждой командой, а не только режимом парка у движка.

## Обновление

Делать ничего не нужно. Установки на одной машине ведут себя ровно так же, как раньше; поле хоста добавочное, и запись без него никто не трогает, пока вы не передадите `--adopt-unowned`.

Две вещи стоит выполнить один раз:

```bash
tesserae sessions prune-internal --dry-run   # see how much of your store is noise
tesserae sessions prune-internal             # then clean it
tesserae compile                             # and rebuild on what is left
```
