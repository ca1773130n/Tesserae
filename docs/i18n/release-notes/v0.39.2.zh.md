发布于 **2026-09-08** · [PyPI](https://pypi.org/project/tesserae/0.39.2/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.2) · `pip install --upgrade tesserae==0.39.2`

同一处的两个缺口：没有任何东西告诉你 LLM 后端是否真的能用，而 `doctor --fix` 不会把开始的事做完。

## 发生了什么

`doctor --fix` 按注册表顺序对每项修复只应用一次。让先前检查失效的修复，会把这份工作留给没人知道要运行的第二次调用：修复 lint 会重写 `graph.json`，从而让站点变旧，而站点检查早已过去。修复运行还打印与只读运行相同的表格，因此要弄清哪些警告是有意为之，就得比对两屏内容。与此同时，唯一接触后端的只有 `config status --ping`，它在打印配置时顺带发一次调用。

## 变更内容

- **`doctor --fix` 会收敛。** 修复反复执行，直到某一轮不再改变任何东西，上限三轮；每轮之间重建项目上下文，因此那些创建了后续检查所读之物的修复也会被看到。
- **它拒绝做的每件事都会被点名。** 仍然出错的内容会出现在 **Still open** 之下，连同命令和原因。原因对产生它的那次运行是诚实的：只读运行会说该发现可由 `--fix` 修复，而不会说修复运行过却失败了。四条常设原因覆盖所有只报告的检查——spend、install、authenticate、destroy——若新增检查却不给出原因，测试就会失败。
- **又有三项检查能自行修复。** `config_valid` 用 `init` 会写入的值原子地补齐缺失的必需键；无法解析的配置只报告，绝不重写。`--fix --deep` 追加缓慢的本地修复，从会话分块回填开始。任何层级的修复都不会运行编译。
- **`tesserae test` 证明后端在应答。** 它按编译的方式解析设置、构建同一个客户端，然后花掉一次 JSON 调用和一次散文调用，因为网关可能服务前者而拒绝后者。两者都不缓存。只有两次都返回才以 0 退出。

## 用法

```bash
tesserae test                 # resolve, build, one JSON call, one prose call
tesserae doctor --fix         # repeats until a pass changes nothing
tesserae doctor --fix --deep  # + the slow local repairs
```

## 升级

无需迁移。`doctor --fix` 仍然遵守旧承诺——只做安全修复，绝不编译，绝不杀进程——只是现在会重复执行并报告它留下了什么。没有 `--fix` 的 `--deep` 以 2 退出。
