공개일 **2026-09-06** · [PyPI](https://pypi.org/project/tesserae/0.39.0/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.0) · `pip install --upgrade tesserae==0.39.0`

`tesserae compile`은 항상 설정된 LLM을 통해 개념 및 클레임 레이어를 구축했다.
다른 모든 컴파일 경로는 그렇지 않았다: `refresh`, 엔진 데몬, MCP `materialize` 경로, 그리고 `deploy --build`는
모두 추출기를 명명하지 않고 컴파일을 요청했으며, "none"은 결정론적인 것을 의미했다.

## 무슨 일이 있었나

`tesserae refresh` 한 번이 실제 프로젝트에서 LLM 없이 전체 문서 레이어를 다시 구축했다.
모든 파일은 여전히 그래프된 것으로 표시되었고, 어떤 문서도 폴백으로 표시되지 않았으며,
그래프는 개념, 기능, 모델, 주제가 없이 돌아왔다 — 466개의 개념이 0이 되었다.
새로고침 루프의 데몬은 첫 번째 재컴파일에서 동일하게 했을 것이다.
수정은 먼저 픽스처로 고정되었다: 증분 differ는 손대지 않은 파일의 LLM 유형 노드를 유지한다;
진입점이 구멍이었다.

## 무엇이 바뀌었나

- **추출기를 명명하지 않은 컴파일은 이제 설정된 LLM을 구축한다**, `tesserae compile`이 구축하는
  것과 같은 형태로, 결정론적 추출기가 문서당 폴백이다. 사용할 수 있는 백엔드가 없으면 경고와 함께 구조 그래프로
  저하되고, 절대 조용히 진행되지 않는다. `compile --extractor deterministic`은 명시적 거부로 남아 있다.
- **컨텍스트 번들은 엔티티를 풀어 설명하는 문서를 인용하고 패킹한다.**
  v0.38.0은 문서당 언급 밀도를 저장했다; 아무것도 그것을 읽지 않았다. 엔티티에 대한 번들의 섹션은 이제 그 문서의 산문을 패킹하고 그것을 인용 이름으로 하며,
  신선한 SQLite 미러가 없을 때 처음 본 경로로 폴백한다.
  `node_context`는 가산 `documents` 리스트를 얻으며, 순위가 정해진다. 두 코퍼스에서 측정했을 때, 처음 본 것은 대략 절반 정도의 확률로 소유 논문을 이름 붙이고;
  가장 많이 언급한 문서는 10번 중 9번이다.
- **`verify_attribution`**, MCP 도구이자 `verify-attribution` CLI 동사로. 커버리지 검사는 이웃의 테이블 행에서 들어올린 실수 숫자를 통과하는데, 왜냐하면 모든 토큰이 증거에 있기 때문이다. 이것은 대신 소유권을 검사한다: 그 그림이 어느 레코드에 있는지, 그리고 그 문서가 벤치마크를 이름 붙이는지 여부.
  결정론적이고, 그래프 없고, LLM 없음; 33개의 참 응답 중 4개의 거짓 양성으로 15개 중 14개의 오귀인을 포착했다고 감사를 받았다.
- **신용이 부족한 codex 계정은 고갈이지 전송 오류가 아니다.** 한 번의 호출에서 판정 `exhausted`로 표시되고 실행 동안 기억된다 — 제공자 체인은
  호출 시점에 로그인한 Claude CLI로 폴백하고, 그것의 docstring이 항상 약속했던 대로다. 이전에는 모든 호출이 약 55초를 들여 네 개의 홈을 재시도하고 아무것도 반환하지 않았다.

## 업그레이드

daemon을 실행하거나 `refresh` 루프를 실행한다면, 이제부터 변경된 문서에서 LLM 호출을 쓸 것으로 예상하라;
변경되지 않은 문서는 프롬프트-주소 지정된 캐시를 사용한다. 이전 버전 아래 `refresh`로 컴파일한 그래프는 구조만 있고 —
한 번의 완전한 `tesserae compile`이 LLM 레이어를 복원한다. 마이그레이션할 것은 없다.
