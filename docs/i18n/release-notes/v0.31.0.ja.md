リリース **2026-08-10** · [PyPI](https://pypi.org/project/tesserae/0.31.0/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.31.0) · `pip install --upgrade tesserae==0.31.0`

セッションのトランスクリプトは、コマンドが実行されたことを記録します。これまで
グラフが保持していたのはそれだけでした — 呼び出しがあったという事実だけで、その
結果は決して残りませんでした。自分の履歴を読むエージェントは `pytest` を走らせた
ことは分かっても、スイートが通ったかは分かりません。それがログと記憶の違いであり、
このリリースが埋めるところです。

## ツールの結果はひとつのターン

終了コードとエラーフラグが取り込みを生き延び、そのターンの `Event` ノードに刻まれ
るようになりました。グラフは**失敗した**コマンドと、単に実行されただけのコマンドを
区別できます。

そのノードを生成する `Event` パスは、LLM を使わず例外も投げない性質を保ちます:
有意な遷移ごとにノード一つ、連続するイベント間の `precedes` エッジ、そしてすべての
id・本文・日付が内容由来。再実行すればバイト単位で同一の出力になります — 481
セッションのコーパスで検証し、さらに「あらゆる属性アクセスで例外を投げる」
クライアントを渡して再検証しました。このパスはセッションを持つプロジェクトで
既定オンであり、その安全性は経路にモデルがないことだけに依っているからです。

ターンのテキストはノード名と説明にコピーされ、それらは `graph.json` とあらゆる投影に
シリアライズされるため、**ホームディレクトリは入口で伏せられます**。
`/Users/<name>` と `/home/<name>` がグラフに届くことはありません — パスは、誰も
意図しないのにほぼすべてのトランスクリプトに現れる個人データだからです。

## `recovers` エッジ

Tesserae はひとつのセッション内の**観測された**二つの結果から、因果エッジを一本
導くようになりました: 失敗を報告したツール呼び出しと、その後の呼び出し — 同じ
ツール、同じプログラム系統、同じ作業ディレクトリ、同じオペランドで、その間にその
オペランドでの成功が観測されていないもの — が成功を報告した場合です。成功した
`Event` がソース、失敗した側がターゲットで、両方のターン id が証拠に記され、
`metadata["basis"]` は二つの呼び出しが一致していなければならなかったすべての次元を
名指しします。

`CAUSAL_EDGE_TYPES` の要素はちょうど一つで、これからもそうです。主要なエージェント
メモリシステム四つを調べたところ、因果エッジを導出しているものは一つもありません
でした: 二つは最も強いリンクを共起から推論し、一つは検証なしに開いた語彙の関係
ラベルを LLM の言い分のまま受け取り、一つはエッジそのものがありません。この狭さが
避けようとしている失敗は、実際には `happened_near` でしかない `caused_by` を出荷
することです — グラフの中で両者は区別できず、間違ったほうが証拠として読まれます。

アンカーはコマンドではなく**オペランド**です。コマンドは重要でないところ（フラグ、
順序）で変わりますが、作用の対象こそが再試行が実際にやり直しているものだからです。
この選択は、実際のトランスクリプト 103 件、ツール結果 2,330 件、生の失敗 94 件を
四つの候補アンカーキーで再解析し、全区間を手で検証して得られました。

## 来歴によって獲得される、予約された手続き的枠

`tesserae context` は手続き的プールごとに枠を一つ予約するようになりました —
`Runbook`, `Gotcha`, `Event`, `DistilledNote`, `ExpertiseProfile` — エージェントが
実際に何を実行し、どうなったかが、厳しい予算ウォークの先頭に届くようにするためです。

その枠は**与えられるのではなく獲得されます**。この五つの型名は文書抽出でも生成でき
るため、投稿募集を読んだ LLM が「CVPR 2026」という `Event` を正当に作ります。予約は
加算的で、近傍のどこにあってもノードを予算の先頭へ引き上げるので、型だけで予約すると
学会の締切がその枠を獲得したセッションの発見を追い出しかねません。両者を分けるのが
`has_producer_provenance` であり、予約は枠への主張であって証明ではありません:
`delivered` は予算ウォークのあとで確定するので、呼び出し側は「手続き的記憶が予約
された」と「手続き的記憶が届いた」を区別できます。新しい `PROCEDURAL_POOLS` lint
コードがその差を報告します。

## ノードは、そのソースが入ってきた場所から日付を得る

`first_seen_at` は、コンパイル時の壁時計ではなく、ノードのソースが取り込まれたパスから
導かれるようになりました。時計を読めば再実行のたびに差分が出て、バイト冪等性が拠って
立つ内容ハッシュのスキップが崩れます。同じ規則が `Event` パスを再現可能に保ちます。

## ドキュメント

ドキュメントはコードより丸一サイクル遅れており、このリリースが八言語すべてでそれを
正します。ユーザー向けドキュメントが皆無だった五つのサブシステム — 憲章、lint コード
の語彙、ツール結果、`recovers` エッジ、手続き的枠 — に説明がつき、提供されていながら
一覧になかった MCP ツール九つが文書化されました。おかげでエージェントは自分のために
書かれたツールを見つけられます。提供中の 35 ツールすべてが全言語でカバーされています。

古い不具合も二つ片付きました: `docs/i18n/` 内の壊れたリンク 70 本（翻訳ページが、その
場所には存在しない英語ファイル名を指していました）と、v0.10.0 で入ったのに一度も翻訳
されていなかったアーキテクチャ文書の `OKF v0.2 エクスポート / インポート` 節です。

## アップグレード

```bash
pip install --upgrade tesserae==0.31.0
```

移行が必要なものはありません。`Event` パスと `recovers` 検出器は、セッションを持つ
プロジェクトの次回コンパイルで動きます。既存のグラフは再構築を強制されることなく新しい
ノードとエッジを得ます。このリリース以前に取り込まれたセッションに終了コードはありま
せん。その情報は取り込み時に捨てられ、正規化済みレコードからは復元できないからです —
結果を付けたい場合は、それらのトランスクリプトを取り込み直してください。
