公開日 **2026-09-04** · [PyPI](https://pypi.org/project/tesserae/0.38.0/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.38.0) · `pip install --upgrade tesserae==0.38.0`

`node_provenance` はどの文書がそのエンティティに言及しているかまでを答えて、そこで
止まる。30 本の論文で見つかったノードは、見分けのつかない 30 件の文書を返し、その
エンティティを実際に詳述している一本はそのどこかにある。

## 何が起きたか

2026-09-02 に二つのコーパスで測定した。provenance の集合は 55-64% の割合で詳述して
いる文書を含んでいるが、その集合を並べ替えてその一本を上に出せるのは 10-15% にすぎ
ない。集合は正しく、順序はコイン投げである。サイドカーから見ると、その中の文書は
どれも同じに見えるからだ。

## 何が変わったか

- **派生サイドカー `node_mentions`** — `(node_id, source_path, mentions)`。コンパイル
  時のパスが、各ノードの名前とその別名を、単語境界を守って、その provenance が指す
  すべての文書の中で数える。
- **`SqliteGraphStore.node_documents` は、それらの文書を言及数の
  多い順に返す。** 読み
  出しは `node_provenance` が主導し、カウントを LEFT JOIN するので、二つのサイドカー
  が互いにずれることはない。カウントのない文書も 0 として現れる。
- **列ではなく別テーブルである。** 既存の `sqlite.db` に移行は要らず、provenance の
  バイト安定性にも手を触れない。
- **名前と別名の重なる範囲は統合される**ので、`BERT-base` は 2 回ではなく 1 回として
  数えられる。
- **このカウントはコーパス本文が手元にあるときにしか取れない**。だからコンパイル時に
  行う。下流の何もこれをグラフから復元できない。

測定したコスト: 全文論文 148 本の 43,151 ペアで 31.5 秒、抄録 1,552 本の 27,669
ペアで 5.2 秒。時間単位で測られるコンパイルに対しての話である。

## まだやっていないこと

出荷済みの検索経路に、このカウントで順位を付ける箇所はない。`node_documents` は呼び
出せる API であり、パッカーは今も、そのノードが最初に見つかった場所を基準に文書を
並べている。この作業のきっかけとなったベンチマークでは、mention density が二つの
コーパスでそれぞれ 0.92 と 0.85 の割合で所有文書を選び、出荷済みの規則は 0.52 と
0.55 だった。組み込むのは後のリリースであって、今回ではない。

## アップグレード

移行するものはない。テーブルは次の `tesserae compile` で現れ、カウントも一緒に現れ
る。再コンパイルするまで、`node_documents` は provenance の集合をパス順に、カウント
はすべて 0 で返す。これまでと同じ文書であり、悪くなることはない。
