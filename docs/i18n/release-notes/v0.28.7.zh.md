Released **2026-08-05** · [PyPI](https://pypi.org/project/tesserae/0.28.7/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.7) · `pip install --upgrade tesserae==0.28.7`

**如果有其他工具将会话记录写入您的 Tesserae 存储库，请升级。**
[#104](https://github.com/ca1773130n/Tesserae/issues/104) 在 0.28.5 和 0.28.6 中修复了两次，但两次都仍然丢失了这些记录。此版本在实际区分一个生产者和另一个生产者的轴上修复了它。

## 之前两个修复遗漏的内容

两者都根据扫描查看的*位置*确定了删除范围：发现只能删除其脚本存在于它已遍历的 harness 根目录下的记录。这个推理仅在不同生产者读取不同目录时成立。

但他们不会。描述 Tesserae 本地扫描所读的**相同** `~/.claude` 脚本的 orchestrator 导出自己的代理会话 — 只是携带扫描无法推断的代理身份。按构造，其记录位于范围内。

在针对真实 375 记录存储的 0.28.6 上测量，两种丢失形式幸存了下来：

- **已删除。** 扫描不再找到其脚本的记录被修剪。原始错误，未改变。
- **默默被覆盖。** 扫描*确实*找到其脚本的记录被扫描的更简单版本替换 — 代理身份和元数据消失。两个编写器从会话 id 派生相同的文件名，因此一个落在另一个之上。什么都没被删除，所以删除计数保持为 0，运行报告成功。

第二种形式根本不是修剪问题，这就是为什么范围的任何精化都无法到达它。

## 来源

每条记录现在都有一个 **`producer`** — 写入它的导入器。
`sessions discover --import` 戳上 `tesserae:discover`；`sessions import <path>` 戳上 `tesserae:import`。编写器只能触及它生产的记录：

- 仅修剪自己的记录；
- 它**不会**覆盖同一会话的另一生产者的记录。传入的写入被跳过并报告为
  `Left alone (written by another producer)`。

如果您从自己的工具写入此存储库，请使用 `tesserae sessions import <file>`，您的记录从该点起受到保护。无需其他任何内容。

根和 harness 范围设置仍作为第二道关卡，但它们不再是保护记录安全的内容。

## 升级

**在此版本之前写入的记录不携带生产者。** 它们不归属，因此没有导入器修剪或覆盖它们 — 升级无法丢失您已拥有的内容，包括其他工具写入的记录。

该选择的代价：发现也不会刷新旧版记录。如果 Tesserae 自己的扫描是写入您的存储库的唯一内容，请运行

```bash
tesserae sessions discover --import --adopt-unowned
```

一次以将这些记录交付给发现。**如果其他工具写入同一存储库，请不要运行它** — 它确实做了标志所说的事情。

无损是正确的默认值。正在修复的错误是无声的数据丢失，而另一个默认值会在应该保护它们的升级中最后一次销毁报告项目的记录。

## 致谢

由在 [Agented](https://github.com/ca1773130n/Agented) 项目上工作的代理报告、再现和诊断，该项目通过 CLI 使用 Tesserae。他们针对真实存储库而不是固定装置进行了测量，这就是他们发现两轮修复和五个审查者的代码审查所遗漏的原因 — 这里编写的每个测试都使"另一个生产者"意味着"另一个目录"，所以测试确认了假设而不是检查它。他们还提议了来源，这是 #104 从一开始就建议的方向。
