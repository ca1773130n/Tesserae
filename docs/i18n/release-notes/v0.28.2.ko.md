Released **2026-07-27** · [PyPI](https://pypi.org/project/tesserae/0.28.2/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.2) · `pip install --upgrade tesserae==0.28.2`

두 항목 모두 다른 코드베이스에서 `verify_claim`을 사용해 개발하던 팀이 제보한
것입니다. 둘 다 직접 소비자가 되어 보지 않으면 발견할 수 없는 종류의 문제입니다.

## `tesserae verify-claim`

`verify_claim`은 MCP 도구일 뿐 그 이상이 아니었습니다. 즉 Tesserae를 임포트하지
않고 서브프로세스로 호출하는 쪽에서는 아예 닿을 수 없었습니다. 그렇다고 임포트가
공짜인 것도 아닙니다. 트리 전체가 가상환경으로 딸려 들어오고, 그쪽 프로젝트의
버전이 우리 버전에 묶여 버립니다.

v0.25에서 `graph-map`이 메운 것과 같은 공백이고, 같은 해법입니다.

```sh
tesserae verify-claim -s 'Flash Attention' -p uses -o 'Tiling'
# -> {verdict, reason, triple, citation, provenance, advisory}
```

엔드포인트는 정확한 노드 id, 대소문자를 접은 고유 이름, 또는 고유 별칭으로만
해석됩니다. 자연어 입력은 설계상 존재하지 않습니다. 그 외의 것은 추측하지 않고
`NOT_RESOLVABLE`을 냅니다.

종료 코드는 **답이 되는 모든 판정에 대해 0**이며, 여기에는 `ABSENT`도
포함됩니다("이 그래프는 그것을 주장하지 않는다"는 오류가 아니라 진짜 답입니다).
그리고 **`NOT_RESOLVABLE`에는 2**를 주어, 스크립트가 *확인할 수 없었음*과
*확인했고 결과는 이것임*을 구분할 수 있게 했습니다. 분기는 `verdict`와
`provenance.class`를 함께 보고 하십시오. `reason`으로는 절대 하지 마십시오.

## 재접지(re-grounding)는 판정을 바꿉니다. 문서는 절대 그럴 수 없다고 했습니다.

`reground` 파라미터의 문서는 이것이 "advisory only"이며 "판정을 절대 바꿀 수
없다"고 약속했습니다. 구현은 작성된 시점부터 그와 달랐습니다. `document_backed`는
`regrounded is not False`를 요구합니다.

옳았던 쪽은 **구현**입니다. `SUPPORTED`는 주장의 근거가 실제 문서의 축자적
스팬이라고 단언하는데, 실제 15,284개 엣지 그래프에서 **2,088개 `SUPPORTED` 판정
중 198개가 해당 파일에 명백히 존재하지 않는 텍스트를 인용**하고 있었습니다.
추출기가 제목 경계를 넘어 조각을 이어 붙인 것입니다. 클래스만으로는 이것을 볼 수
없습니다. 클래스는 메타데이터에서 나오고, 디스크를 읽는 것은 재접지뿐이기
때문입니다.

그래서 게이트가 아니라 문서를 고쳤습니다.

- `regrounded: false` — 파일을 읽었고 스팬이 **없었습니다**. 반증된 근거는
  `SUPPORTED`일 수 없으므로 판정은 `PRESENT_UNEVIDENCED`로 강등됩니다.
- `regrounded: null` — 확인하지 않음(`--no-reground`이거나 읽을 수 있는
  `source_path`가 없음). 아무것도 강등하지 않습니다. 가정하지 말고 반증하십시오.

판정은 여전히 *고정된 `reground`에 대해서는* 그래프 바이트의 순수 함수입니다.
재접지는 같은 그래프가 다르게 답할 수 있는 유일한 축인데, 그것이 그래프가
소유하지 않은 파일을 읽는 유일한 축이기 때문입니다. 그리고 판정을 **아래로만**
움직일 수 있습니다.

**`verify_claim`을 소비한다면 무엇을 읽어야 하는지가 달라집니다.** `verdict`를
기준으로 삼은 것은 언제나 옳았습니다. 하지만 `regrounded`를 무시해도 되는
장식으로 취급한 것은 옳지 않았습니다. 그것은 `verdict`의 입력이지 위에 얹힌
꾸밈이 아닙니다.

## 그 밖에

CLI 동사가 이제 MCP 도구와 동일한 경로로 그래프를 적재하므로, 연결 발견
오버레이가 양쪽 모두에 적용됩니다. `verify_claim`은 쌍-국소적이어서, 검사 대상인
두 엔드포인트 사이에 발견된 엣지가 있으면 한쪽 표면의 엣지 집합에만 들어가고
다른 쪽에는 들어가지 않았을 것입니다. 같은 트리플이 호출 방식에 따라 다르게
답하는 셈입니다.

`tesserae --help`가 `verify-claim`을 두 번 출력하고 있었습니다.
