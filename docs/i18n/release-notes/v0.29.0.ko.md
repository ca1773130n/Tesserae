Released **2026-08-07** · [PyPI](https://pypi.org/project/tesserae/0.29.0/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.29.0) · `pip install --upgrade tesserae==0.29.0`

이번 릴리스는 여러 대의 머신이 디스크 하나를 공유하는 상황에서도 Tesserae를 쓸 수
있게 만들고, 겉보기와 달리 출력물을 조용히 더 나쁘게 만들고 있던 두 가지를
고칩니다.

## Tesserae는 자기 자신의 LLM 호출을 당신의 세션으로 인제스트하고 있었습니다

컴파일할 때마다 문서마다 한 번, 세션마다 한 번씩 `claude` CLI가 실행됩니다. 그
호출 하나하나가 `~/.claude/projects`에 트랜스크립트를 남기고, 세션 discovery는
그것들을 당신의 코딩 작업인 양 수집했습니다. 메인테이너 본인의 프로젝트에서는:

| | |
|---|---|
| 저장된 세션 레코드 | 14,605 |
| Tesserae 자신의 추출 호출 | **14,377 (98.4%)** |
| 진짜 사용자 세션 | 228 |

그중 10,666개는 제목이 하나로 똑같았습니다 — 추출 프롬프트입니다.

이를 걸러내는 필터는 이미 있었고, 그 필터를 빠짐없이 유지하는 것만이 존재
이유인 테스트도 있었습니다. 그 테스트는 소스를 훑어
`You (?:are|distill|write|decide|arbitrate|split)`에 매칭되는 프롬프트를
찾았습니다 — 손으로 관리하는 시작 **동사** 허용 목록이었습니다. 추출 프롬프트는
"You extract"로 시작하므로, 시스템에서 가장 많은 양을 차지하는 프롬프트가 하필
가드가 볼 수 없는 그 한 프롬프트였습니다.

이제 가드는 AST에서 `system=` 인자를 열거하고 모듈 수준 상수를 해석합니다.
프롬프트는 어떤 문구로 쓰였는지가 아니라 **어떻게 전달되는지**로 식별되기
때문입니다. 이 변경으로 커버되지 않던 호출 다섯 개가 즉시 드러났습니다: liveness
probe, activity summary(문구 두 가지), decision extractor, claim judge, scope
router.

`tesserae sessions prune-internal`은 이제 sqlite뿐 아니라 **파일 스토어**도
정리합니다 — 이전에는 sqlite만 정리했고, `compile`이 읽는 쪽은 파일 스토어이므로
정리해도 아무 일도 일어나지 않는 것처럼 보였습니다. `--dry-run`을 받습니다.

Tesserae를 한동안 돌려 왔다면 실행하세요. 그런 다음 다시 컴파일하세요. 지금까지의
노드 수는 노이즈를 센 것입니다.

## 여러 대의 머신이 프로젝트 디렉토리 하나를 공유할 때

Tesserae 안 어디에도 머신 신원이 없었기 때문에, 공유된 `.tesserae/`에 사는
머신별 상태는 전부 머신이 하나뿐인 것처럼 모든 호스트가 읽고 썼습니다.

**세션 레코드는 그것을 본 적 없는 호스트에 의해 삭제될 수 있었습니다.**
`producer`는 두 머신을 갈라놓지 못합니다: 모든 호스트의 스캔이 같은 상수를 찍고,
각자의 `~/.claude` 루트도 같은 문자열로 해석됩니다. 그래서 트랜스크립트를 본 적
없는 호스트에서도 기존 안전 게이트 두 개가 모두 통과했고 — 다른 머신의 레코드를
삭제하면서 성공을 보고했습니다. 이제 레코드는 자신을 수집한 호스트를 담고,
호스트는 자신이 수집한 것만 제거합니다.

호스트 id는 호스트명에서 유도하지 않고 `~/.tesserae/host_id`에
저장합니다(`TESSERAE_HOST_ID`로 재정의). 이미지 하나로 찍어낸 플릿은 호스트명을
재사용하고, 충돌이 나면 한 머신의 레코드가 다른 머신에게 넘어가기 때문입니다.

충돌 세 가지가 더 수정됐습니다: 엔진 pidfile은 이제 `daemon.<host>.pid`이고(생존
확인이 **로컬** 프로세스 테이블을 상대로 하는 `os.kill(pid, 0)`이었는데, 다른
머신의 pid에는 아무 의미가 없습니다), Codex 스캔 워터마크는 호스트별이며(공유
하한선 하나로는 마지막에 실행된 호스트가 다른 호스트가 아직 읽지 않은 트랜스크립트
너머로 워터마크를 밀어버렸고 — 그것들은 끝내 임포트되지 않았습니다),
`doctor --fix`는 다른 호스트의 pidfile을 아예 건드리지 않습니다.

**신규: `tesserae engine --harvest-only`.** 호스트 하나가 컴파일하고, 나머지
호스트는 자기가 볼 수 있는 트랜스크립트만 따라가며 컴파일 락을 절대 잡지 않습니다.
경합을 중재하는 대신 없애는 쪽입니다.

## 백그라운드 엔진이 더 이상 당신을 막지 않습니다

`compile`과 `refresh`는 `--wait [SECONDS]`를 받습니다. 종료 코드 2로 빠지는 대신
프로젝트의 컴파일 락을 기다리는 큐에 서고, 5초마다 상태를 보고하며 락을 쥔 머신을
알려줍니다. 백그라운드 데몬은 이제 트리거를 버리는 대신 최대 60초의 지수 백오프로
미룹니다.

`--wait`는 stderr가 터미널인지로 추론하는 대신 명시적 플래그로 뒀습니다: 같은
명령이 `tee` 아래에서든, tmux 캡처에서든, CI에서든 동작이 달라져서는 안 됩니다.
`flock`은 공정성을 제공하지 않고 따라서 기아 상태의 상한도 없으므로, 대기에는
한계 시간이 있습니다.

## `compile --all` / `refresh --all`

등록된 모든 프로젝트에 대해 명령 하나이며, 프로젝트별로 실패가 격리됩니다 — 한
프로젝트가 실패해도 나머지는 멈추지 않습니다. 컴파일 락이 잡혀 있는 프로젝트는
**failed**가 아니라 **locked**로 보고되고 자기만의 종료 코드를 받습니다: 플릿에서
그것은 정상 상태이고, 트레이스백과 같은 코드를 주는 것은 사람들에게 종료 코드를
무시하라고 가르치는 셈입니다. 컴파일은 LLM을 많이 쓰므로 `--jobs`의 기본값은
1입니다.

## 프로젝트 수준 LLM 설정이 이제 실제로 클라이언트에 도달합니다

`ProjectWiki._build_json_client`는 프로젝트 설정을 해석한 다음 클라이언트 팩토리를
**그 설정 없이** 호출했습니다. 그래서 팩토리는 환경 변수와 글로벌 설정만으로 다시
해석했고, 프로젝트 수준의 `llm_model`, `llm_base_url`, `llm_api_key`는 전부
버려졌습니다. `.tesserae/config.json`에 적어 둔 커스텀 엔드포인트는 클라이언트에
한 번도 닿지 않았고, 컴파일은 조용히 기본 백엔드에서 돌았습니다.

문서는 이미 올바른 동작을 설명하고 있었습니다 — 코드만 거기에 동의하지 않았을
뿐이며, 이것은 버그가 취할 수 있는 최악의 형태입니다. 도구를 의심할 이유를 전혀
주지 않기 때문입니다.

`--claude-config-dir`을 반복해서 넘겨도 `CLAUDE_CONFIG_DIR`이 스칼라라서 첫 번째
계정으로 뭉개졌습니다. 이제 순서가 유지된 전체 목록이
`TESSERAE_CLAUDE_CONFIG_DIRS`로 전달됩니다.

## 정직한 보고

`tesserae init`이 이제 프로젝트를 등록합니다. 그러지 않으면 README 퀵스타트를
그대로 따라갔을 때 `ask`가 cwd 별칭을 해석하지 못해 federated 스코프로 폴백했고,
파일 세 개짜리 프로젝트에 대한 질문에 무관한 저장소들에 속한 19,744개 노드를
근거로 답했습니다 — 그러면서 `--scope current`는 등록된 프로젝트 안에서
"not inside a registered project"라며 2로 종료했습니다.

`compile`은 이제 **모든** 문서가 결정론적 추출로 폴백한 경우 1로 종료합니다.
이전에는 요약을 출력하고 0으로 종료했기 때문에, 개념 레이어가 없는 그래프가
성공으로 읽혔고 그다음 `query`는 아무것도 매칭하지 못했습니다.

`doctor`는 더 이상 CLI가 한때 사용됐다는 사실만 증명하는 파일들을 근거로
`credentialed LLM CLI`를 보고하지 않습니다 — `compile`이 인증 때문에 실패하는 바로
그 순간에 초록색 체크를 찍고 있었습니다. **이것은 능력의 향상이 아니라 확신의
하향 조정입니다**: 자격 증명을 검증하려면 실제 LLM 호출 비용이 들기 때문에, 이제
이 검사는 자신이 실제로 검증한 것만 진술합니다.

새로 추가된 보고 전용 `filesystem_locking` 검사. 여기 있는 모든 동시성 보장은
`.tesserae/`를 담고 있는 파일시스템이 `flock(2)`를 강제한다는 전제 위에 서 있는데,
NFS나 SMB에서는 그것이 설정에 따라 달라집니다 — 락 데몬이 동작하지 않으면
`flock`은 조용히 no-op으로 격하될 수 있습니다. 이 검사는 네트워크 파일시스템에서
경고하며, 호스트 하나로는 호스트 간 강제를 증명할 **수 없다**는 점을 분명히
말합니다. 여러 머신에서 공유 스토리지를 상대로 Tesserae를 돌린다면, 그것은 직접
시험해 보세요.

## 동시 쓰기

아티팩트 라이터 다섯 개가 고정된 임시 경로 하나를 통해 발행하고 있었습니다 —
`with_suffix`는 접미사를 *교체*하므로 `graph.json`은 `.tesserae/graph.tmp`를 거쳐
발행됐습니다. 발행자 둘이 그 파일 하나에 뒤섞여 쓰고, 섞인 결과를 제자리로
rename했습니다. 그중 매니페스트가 가장 큰 문제였습니다: `_load_manifest`는
`json.loads`를 아무 방어 없이 호출하므로, 뒤섞인 매니페스트는 모든 호스트의 이후
모든 컴파일에서 예외를 던졌습니다.

`TESSERAE_REGISTRY`는 이제 엔진의 플릿 모드에서만이 아니라 모든 명령에서
존중됩니다.

## 업그레이드

할 일 없습니다. 단일 머신 설치는 이전과 정확히 동일하게 동작하며, 호스트 필드는
추가되기만 할 뿐이고 호스트 필드가 없는 레코드는 `--adopt-unowned`를 넘기기
전까지 건드리지 않습니다.

한 번쯤 실행해 볼 만한 것 두 가지:

```bash
tesserae sessions prune-internal --dry-run   # see how much of your store is noise
tesserae sessions prune-internal             # then clean it
tesserae compile                             # and rebuild on what is left
```
