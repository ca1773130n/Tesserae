공개일 **2026-09-08** · [PyPI](https://pypi.org/project/tesserae/0.39.2/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.2) · `pip install --upgrade tesserae==0.39.2`

같은 자리에 두 개의 구멍이 있었다. LLM 백엔드가 실제로 동작하는지 아무것도 알려주지 않았고, `doctor --fix`는 시작한 일을 끝내지 않았다.

## 무슨 일이 있었나

`doctor --fix`는 각 수리를 레지스트리 순서대로 한 번씩만 적용했다. 앞선 검사를 무효화하는 수리는 아무도 실행할 줄 모르는 두 번째 호출에 그 일을 남겼다: lint를 고치면 `graph.json`이 다시 쓰이고 그래서 사이트가 낡는데, 사이트 검사는 이미 지나간 뒤였다. 게다가 수리 실행은 읽기 전용 실행과 같은 표를 출력해서, 어떤 경고가 의도된 것인지 알려면 두 화면을 비교해야 했다. 한편 백엔드를 건드리는 유일한 것은 설정을 출력하는 부수 효과로 한 번 호출하는 `config status --ping`뿐이었다.

## 무엇이 바뀌었나

- **`doctor --fix`가 수렴한다.** 한 패스가 아무것도 바꾸지 않을 때까지 수리를 반복하며, 최대 세 번이다. 패스 사이에 프로젝트 컨텍스트를 다시 만들어, 뒤의 검사가 읽는 것을 만들어내는 수리도 반영된다.
- **거절한 것은 모두 이름이 붙는다.** 아직 잘못된 것은 **Still open** 아래에 명령과 이유와 함께 나온다. 이유는 그것을 낳은 실행에 대해 정직하다: 읽기 전용 실행은 그 발견이 `--fix`로 고칠 수 있다고 말하지, 수리가 실행됐는데 실패했다고 말하지 않는다. 네 가지 상시 이유가 모든 보고 전용 검사를 덮으며 — spend, install, authenticate, destroy — 이유 없이 검사를 추가하면 테스트가 실패한다.
- **세 개의 검사가 더 스스로를 고친다.** `config_valid`는 `init`이 쓰는 값으로 빠진 필수 키를 원자적으로 채운다. 파싱되지 않는 설정은 보고만 하고 절대 다시 쓰지 않는다. `--fix --deep`은 느린 로컬 수리를 추가하며 세션 청크 백필부터 시작한다. 어느 단계의 수리도 컴파일을 실행하지 않는다.
- **`tesserae test`가 백엔드의 응답을 증명한다.** 컴파일과 같은 방식으로 설정을 해석하고 같은 클라이언트를 만든 뒤, JSON 호출 하나와 산문 호출 하나를 쓴다. 게이트웨이는 앞의 것만 제공하고 뒤의 것은 거부할 수 있기 때문이다. 둘 다 캐시하지 않는다. 둘 다 돌아올 때만 0으로 끝난다.

## 사용법

```bash
tesserae test                 # resolve, build, one JSON call, one prose call
tesserae doctor --fix         # repeats until a pass changes nothing
tesserae doctor --fix --deep  # + the slow local repairs
```

## 업그레이드

마이그레이션할 것은 없다. `doctor --fix`는 예전 약속을 그대로 지킨다 — 안전한 수리만, 컴파일은 절대, 프로세스 종료도 절대 — 다만 이제 반복하고 무엇을 남겼는지 보고한다. `--fix` 없는 `--deep`은 2로 끝난다.
