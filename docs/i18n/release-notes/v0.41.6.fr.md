Publié le **2026-09-18** · [PyPI](https://pypi.org/project/tesserae/0.41.6/) · [Version GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.6) · `pip install --upgrade tesserae==0.41.6`

Une compilation tourne sur le thread de la boucle d'événements du moteur, et les signaux d'arrêt passaient
par cette boucle : Ctrl-C ou SIGTERM restaient donc sans réponse jusqu'à la fin de la compilation. L'arrêt
lançait ensuite une compilation de plus pour ce qui s'était accumulé. Le journal du moteur de ce projet le
montre : deux signaux, puis une compilation finale sur 4,740 chemins.

## Ce qui a changé

- **Un second signal arrête le moteur.** Le premier termine toujours le travail en cours, et le dit
  désormais : `signal again to stop now`. Le second lève dans le thread principal, quoi qu'il soit en
  train de faire, si bien que le moteur sort même au milieu d'une compilation, son pidfile supprimé et
  avec le code de sortie conventionnel. Rien n'est perdu : la compilation du démarrage suivant retrouve
  les sources modifiées via les différences du manifeste.
- **Un arrêt n'abandonne plus le LLM.** L'agent CLI tourne dans sa propre session, donc le Ctrl-C du
  terminal ne l'atteint jamais, et seul un dépassement de délai le tuait. Toute autre sortie de l'attente
  laissait `claude -p` tourner, et facturer, après la disparition du processus qui l'avait demandé. Son
  groupe de processus est maintenant tué quelle que soit la façon dont l'attente se termine. Cela vaut
  aussi pour le Ctrl-C pendant un simple `tesserae compile`.

## Mise à niveau

Rien à migrer. Redémarrez un moteur en cours d'exécution pour en profiter. Le mode flotte
(`engine --all`) garde le comportement à un seul signal.
