공개일 **2026-09-12** · [PyPI](https://pypi.org/project/tesserae/0.41.0/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.0) · `pip install --upgrade tesserae==0.41.0`

Tesserae는 자신을 지시받기를 기다리지 않고 스스로 지식을 끌어오는 엔진이라고 설명한다.
이 릴리스까지 그것은 아무것도 끌어온 적이 없었다.
데몬이 가진 모든 트리거 소스는 로컬 파일이 변경될 때까지 기다렸다: 파일시스템 감시자, 금고 감시자, 세션 추적자, 그리고 v0.40.0에서 추가된 사이트 서버.
그들은 이미 디스크에 있는 것을 재구성할 뿐이다.

## 무엇이 바뀌었나

- **`tesserae engine --proactive`가 페칭한다.** 프로젝트의 `proactive_sources`에 나열된 피드를 폴링하고, 이전에 본 적 없는 문서를 끌어오고, 다른 새 파일과 동일한 디바운스 및 컴파일 경로로 넘긴다. RSS와 Atom 모두 작동하며, 피드가 아닌 URL은 문서 자체로 취급되어 한 번 수집된다.
- **기본적으로 꺼져 있고 비용 효율적이다.** 이것은 Tesserae에서 키보드에 사람이 없이 비용을 소비하는 첫 번째 것이므로, `--proactive`는 옵트인이고, `--once`, `--harvest-only` 및 `--all`과 함께 사용할 수 없으며, 폴당 5개의 새 문서로 제한된다. 폴러는 첫 틱 전에 대기하므로, 실행할 작업을 설명하는 로그 라인이 먼저 나타난다.
- **아무것도 두 번 페칭하지 않는다.** 그래프 옆의 원장이 모든 URL을 기록한다. Tesserae가 읽을 수 없는 것(예: PDF 전용 링크)은 다시 시도되지 않으며 거부된 것으로 기록된다. 타임아웃은 문서에 대한 결정이 아니므로 절대 기록되지 않으므로, 전송 오류는 재시도된다.
- **피드는 방어적으로 파싱된다.** 이것은 Tesserae가 외부에서 제어하는 URL에서 XML을 파싱하는 유일한 곳이므로, DTD를 선언하는 피드는 완전히 거부된다. 이는 엔티티 확장 및 외부 엔티티 공격을 동시에 방지하고, 실제 피드는 이를 필요로 하지 않는다.
- **`tesserae sources add <url>`**은 피드를 추가하며, 디렉토리를 추가할 때와 같은 동사를 사용한다. 그래프의 지식이 어디서 오는지는 하나의 질문이므로, 하나의 명령으로 관리한다. `sources list`는 각 항목에 레이블을 표시한다.
- **`tesserae completion bash|zsh|fish`**는 셸 완료 스크립트를 출력하며, 실제 명령 트리에서 생성되므로 CLI와 동기화가 유지된다. 생성기는 즉시 `sessions`의 5개 하위 명령 중 3개를 나열했던 도움말의 오래된 줄을 발견했다.
- **잘못 입력된 명령이 올바른 명령을 제안한다.** `tesserae complie`은 `compile`을 가리키고, 그룹 없이 입력된 하위 명령(예: `sync`)은 그 명령을 포함하는 모든 그룹을 이름으로 표시한다. `tesserae vault`와 같은 그룹 이름만 입력하면 이제 누락된 인수 오류 대신 그룹의 도움말을 출력한다.
- **`write_sessions`은 저장소 소유자를 추론하지 않는다.** 그 `producer` 인수는 기본적으로 빈 값이었으므로 전체 저장소 권한을 의미했고, 결과적으로 아무것도 전달하지 않으면 파괴적 읽기를 수행했다. 이제는 필수이다. 전체 저장소 권한은 여전히 가능하지만 `producer=""`로 명시적으로 전달해야 하므로, 생략이 아닌 의도적 선택이 된다.

## 업그레이드

마이그레이션할 것이 없다. 사전 대기 수집은 피드를 추가하고 `--proactive`를 전달할 때까지 아무것도 하지 않으며, 다른 모든 변경은 추가적이다. 유일한 주요 변경은 `write_sessions`을 직접 호출하는 코드: `producer=`을 전달해야 한다. Tesserae 내의 모든 호출자는 이미 이를 수행한다.
