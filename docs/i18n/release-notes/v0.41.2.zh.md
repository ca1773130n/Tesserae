发布于 **2026-09-12** · [PyPI](https://pypi.org/project/tesserae/0.41.2/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.2) · `pip install --upgrade tesserae==0.41.2`

每个命令都通过运行进行了审计。在 42 个候选缺陷中，31 个在复现和对抗性第二意见中幸存下来。这个版本修复了其中最严重的十二个：五个报告成功完成了他们没有做过的工作，五个破坏了数据，一个被忽略的标志，以及一个有意留下的。

## 报告成功但未完成的工作

- **对不包含 markdown 的路径进行编译被拒绝。** `tesserae compile README.txt` — 一个扩展名错误的真实文件 — 从零重建了图谱，用一个空图谱替换它，并以 0 退出。拒绝发生在任何写入之前，所以当你读取它时图谱仍然存在。路径现在对 `--project` 进行解析，而不是对工作目录。
- **`code ingest` 拒绝不存在的路径**，而不是在真实图谱上写入空代码图谱并报告成功。
- **对不是项目的内容进行 `query` 是一个错误。** 它以 0 退出码回答"无匹配"，这看起来像是真实搜索没有找到任何东西，所以 `--project` 中的一个打字错误会被误读为空语料库。
- **`lint` 在无法读取图谱时说明情况。** 它吞下了解析错误，在空图谱上运行了每项检查，并针对根本无法解析的 `graph.json` 以 0 退出码报告"无发现。Wiki 是干净的。"
- **当编译失败时 `engine --once` 以非零状态退出。** 它无论发生什么都返回 0，所以连续集成看到了一个异常的管道的绿色状态。相同的 bug 也导致一个集群为某个项目失败的批次打印 `2/2 units ok`：它读取每个单元的退出码。

## 破坏的数据

- **无法解析的机器范围配置不再被替换。** 每个写入程序在文件无法读取时合并到空字典，然后写入结果，所以一个随意的逗号成本了存储的 clip token 和每个保存的密钥。过去读取一个损坏的文件是可以的；写入一个则不是。
- **`projects register` 不再重新初始化从未编译过的项目**，这会替换其配置并丢失其源、名称和提供程序。守护语句自己的注释已经许诺了这一点；它测试的是错误的文件。
- **`sessions discover --import` 保留来自无法读取的根的记录。** 一个不在磁盘上的 `--root` 仍然被交给修剪范围，所以导入删除了从它收集的所有内容，同时对它一无所知。一个未挂载的磁盘就足够了。
- **`vault sync` 保存它声称应用的覆盖。** 它报告了编辑，仅写入了 vault，下一次运行会把你的更改恢复到原样。
- **`vault export` 保留了一个孤立页面，里面是你的笔记** — 这正是 `vault prune` 已经拒绝删除的。这两个不一致，无声的运行了每次导出。

## 被忽略

- **`engine --all --harvest-only` 不再编译。** 该标志到达了一个单一项目，在集群模式中被丢弃，这就是它被编写的样子：几台机器共享一个目录，每台读取只有它能看到的东西，其中一台编译。

## 有意留下

`lint --fix-trivial` 列出了它刚刚修复的发现。这读起来像"这是我修复的内容"，一个测试将其固定，它不是一个缺陷。它在这里被命名是因为审计提出了它，答案是否定的。

## 升级

没有什么需要迁移。曾经以 0 退出而什么都没有做的命令现在以 2 退出并说明原因，所以依赖于沉默的脚本将开始报告它已经发生的失败。
