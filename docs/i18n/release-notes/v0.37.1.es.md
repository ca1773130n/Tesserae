Publicado el **2026-08-31** · [PyPI](https://pypi.org/project/tesserae/0.37.1/) · [Versión en GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.1) · `pip install --upgrade tesserae==0.37.1`

Configurar un proveedor LLM personalizado no podría funcionar, por tres razones independientes, y el síntoma cada vez era un error sobre un modelo que nunca configuraste. Una auditoría del código del proveedor confirmó 23 defectos; esta versión los corrige.

## El protocolo de línea nunca fue modelado

`llm_provider` confundía *qué backend* con *qué dialecto HTTP*, y `custom` siempre creaba el cliente de Anthropic, que envía POST a `{base}/v1/messages`. Cada servidor compatible con OpenAI — vLLM, LiteLLM, OpenRouter, Together, Ollama, LM Studio — responde 404 a eso. La única clase que habla `chat/completions` no fue creada por ninguna ruta de código e hizo codificación fija de `api.openai.com`, por lo que tampoco podría haber servido tu punto final.

`llm_api_style` ahora nombra la línea y es la única cosa que elige el cliente. Si no se establece, permanece `anthropic` para `custom`, por lo que una configuración personalizada existente se comporta exactamente como antes.

```bash
# un punto final compatible con OpenAI (vLLM, LiteLLM, OpenRouter, Ollama, LM Studio)
tesserae config llm --llm-provider custom --llm-api-style openai \
  --llm-base-url https://gw.example/v1 --llm-model qwen3-coder --llm-auth-token sk-…

# un punto final compatible con Anthropic — sin /v1, el SDK lo añade
tesserae config llm --llm-provider custom --llm-api-style anthropic \
  --llm-base-url https://gw.example --llm-model my-model --llm-api-key sk-…

tesserae config status --project .
```

## El modelo fue descartado, y algo más respondió

El `llm_model` configurado estaba limitado al *nivel* de configuración que proporcionar `llm_provider` — establece el proveedor por bandera y el modelo en un archivo de configuración y tu modelo fue descartado para un valor predeterminado codificado. El punto final personalizado luego cayó a través del CLI de Claude, que fue desencadenado con `--model sonnet` contra tu propia URL base e informó de un modelo no compatible. Nada nombró la causa real.

Un proveedor de **punto final** explícitamente configurado (`anthropic`, `openai`, `custom`) ahora es un contrato: se construye solo, y una falla genera un error que nombra el proveedor, la línea, la URL base, el modelo y qué tipo de credencial se utilizó. `llm_allow_fallback: true` restaura el encadenamiento anterior. Los dos CLI de OAuth aún se reparten entre sí, ya que ninguno lleva un punto final tuyo.

## No había una credencial portadora

Un `llm_api_key` fue enviado como `X-Api-Key` por el SDK y como un token portador por el CLI, y pasarlo al SDK suprimió la resolución de auth-token del propio SDK — por lo que una puerta de enlace que quería `Authorization: Bearer` era inalcanzable. `llm_auth_token` es la credencial portadora, en ambas líneas.

## Configuración que puedes ver

Una precedencia para cada clave: `TESSERAE_LLM_*` environment → `.tesserae/config.json` del proyecto → `~/.tesserae/config.json` → predeterminado, con las variables heredadas `ANTHROPIC_*` un escalón más bajo. El resolvedor registra qué capa ganó cada clave y `tesserae config status` imprime eso — solía adivinar, y acreditaba una variable de entorno que el resolvedor deliberadamente ignora. Status también muestra la línea, el tipo de credencial y el cliente que sirvió su sonda.

`ask`, `query`, lint, los resúmenes de MCP y el demonio del motor se resolvieron solo contra el entorno y la configuración global, por lo que un punto final a nivel de proyecto fue respetado por `compile` e ignorado silenciosamente en cualquier otro lugar. Ahora todos leen el proyecto.

## Además

- Un `llm_provider` inválido se reporta en lugar de convertirse silenciosamente en `claude`.
- Las URL base de Anthropic se normalizan, corrigiendo el `/v1/v1/messages` duplicado que la guía de inicio rápido de este proyecto documentaba.
- `401`/`403` se clasifican como fallos de autenticación y `404`/no encontrado como fallos de punto final, en lugar de informarse todos como "no disponibles".
- `init` y `setup` persisten las nuevas claves; antes las aceptaban y descartaban.

## Actualización

Nada que migrar. Dos cambios visibles: un proveedor de punto final explícito ya no se reparte a un backend diferente, y `config status` imprime el *tipo* de credencial en lugar de `set`/`unset`.
