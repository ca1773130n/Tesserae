공개일 **2026-10-06** · [PyPI](https://pypi.org/project/tesserae/0.42.0/) · [GitHub 릴리스](https://github.com/ca1773130n/Tesserae/releases/tag/v0.42.0) · `pip install --upgrade tesserae==0.42.0`

노드와 엣지 어휘는 닫혀 있었습니다. 새 관계 타입 하나에 새 릴리스가 필요했고, 그 타입을 쓴 그래프는
이전 설치본에서 읽을 수 없었습니다. 매주 자기 온톨로지를 키우는 호스트는 이렇게 일할 수 없습니다. 이번
릴리스에서 호스트는 실행 중에 타입을 등록할 수 있고, 각 타입은 코어 부모 아래에 놓입니다. 호스트가 쓰는
모든 파일은 0.41에서도 그대로 읽힙니다.

## 바뀐 점

- **타입 레지스트리.** `tesserae.type_registry`는 코드, JSON 파일, 또는 `TESSERAE_TYPE_REGISTRY`에서
  등록한 `TypeSpec` 행을 담습니다. 모든 타입은 `core_parent`를 지정합니다. 노드는 코어 타입을 그대로
  유지하고 더 세밀한 종류는 `metadata.subtype`에 담습니다. 활성 레지스트리 엣지 타입은 메모리에서
  허용됩니다.
- **관대한 로드.** `TESSERAE_TYPE_MODE=lenient`는 읽는 쪽이 모르는 타입을 레지스트리 부모로, 없으면
  `Concept` 또는 `references`로 매핑합니다. 원래 타입은 `metadata.raw_type`에 남기고 `load_stats`에서
  셉니다. 기본값은 여전히 `strict`이며 예전과 똑같이 예외를 던집니다.
- **레지스트리에서 오는 뷰.** 레지스트리 타입은 선언한 뷰에, 없으면 부모의 뷰에 들어갑니다. 새
  `crossdomain` 뷰는 `transfers_to`, `inspired_by` 같은 분야 간 관계를 담습니다. 호스트가 이 타입들을
  등록하기 전까지는 비어 있습니다.
- **엣지 신뢰도와 상태.** 엣지는 선택적으로 `confidence`, `status`, `asserted_by`, `valid_from`,
  `invalid_at`, `provenance`를 가집니다. PPR은 타입 가중치에 `confidence`를 곱하고, 요청이 없으면
  `candidate`, `refuted`, `retracted` 엣지를 건너뜁니다. 반박된 `supersedes` 엣지는 더 이상 대상을
  숨기지 않습니다.
- **콘텐츠 리졸버.** `compile_context(content_resolver=...)`는 노드의 콘텐츠를 먼저 호스트에게, 가장
  저렴한 뷰부터 요청하고, 그다음 위키 페이지와 설명으로 물러납니다. 인용에는 실제로 쓴 참조가
  기록됩니다.
- **개념 정체성.** 연합은 `metadata.concept_id`, Wikidata QID, 또는 MSC2020 분류를 공유하는 노드를
  합칩니다. `federate_graphs(identity_resolver=...)`로 호스트는 어떤 `graph.json`도 고치지 않고 자기
  테이블에서 정체성을 공급할 수 있습니다.
- **스키마 드리프트.** `analyze_schema_drift(kind="edge")`는 하위 관계를 제안하고, `embedder`가 이름
  토큰 Jaccard를 대신하며, 원장 레코드에는 게이트 지표가 붙고, `apply_ledger_to_registry`는 승인된
  제안을 레지스트리 파일에 씁니다. 노드의 타입은 절대 바꾸지 않습니다.
- **상한이 있는 이웃 조회.** `store_neighbors`와 `store_iterate_edges`는 저장소에 자체 `neighbors` /
  `iterate_edges`가 있으면 그것을 쓰고, 없으면 대체 경로로 동작합니다. `GraphStore` 자체는 바뀌지
  않았습니다.
- **생산자 전용 엣지.** `transfers_to`, `candidate_transfer`, `analogous_to`, `merged_into`는 LLM이
  추출할 수 없고 에이전트가 쓸 수도 없습니다. 엣지 타입으로도, 그 아래의 레지스트리
  타입으로도, 코어 엣지의 `metadata.relation`으로도 안 됩니다. 브리지가 바로 이 마지막
  형태로 저장되기 때문입니다. 쓸 수 있는 건 생산자 자신인 호스트 코드뿐이고,
  `record_agent_write`에 `allow_producer_only=True`를 넘깁니다. MCP `graph_write` 도구는
  클라이언트가 어떤 `agent`를 내세워도 이 값을 넘기지 않습니다.
- **에이전트 쓰기.** `graph_write`는 레지스트리 타입을 기록하기 전에 코어 부모로 매핑하고
  `metadata.subtype` 또는 `metadata.relation`을 붙입니다. 엣지는 `metadata`를 가질 수 있습니다.

## 호환성

0.41의 `graph.json`은 strict 모드에서 노드, 엣지, 타입 수가 같은 채로 로드됩니다. 새 필드가 없는 그래프는
예전과 바이트 단위로 똑같이 직렬화됩니다. 이번 릴리스가 `graph.json`이나 `agent-writes.jsonl`에 쓰는 것은
어떤 레지스트리 타입도 쓰지 않으므로, 0.41로 되돌아가는 것도 안전합니다.

## 업그레이드

마이그레이션할 것은 없습니다. 레지스트리가 없으면 모든 기본값이 0.41의 동작과 같습니다.
