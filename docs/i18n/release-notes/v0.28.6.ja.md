Released **2026-08-04** · [PyPI](https://pypi.org/project/tesserae/0.28.6/) · [GitHub release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.28.6) · `pip install --upgrade tesserae==0.28.6`

ローカルのハーネス慣例外から Tesserae にセッションを書き込むものがあるなら、
アップグレードしておくこと。0.28.5 まで、`tesserae sessions discover --import`
がそれらのレコードを黙って削除していた。プラグインの `SessionEnd` フックは
セッション終了時に毎回ディスカバリーを実行する。

## ストアが成長を報告しているはずの行で縮んでいた

[#104](https://github.com/ca1773130n/Tesserae/issues/104) で報告されたもので、
0.28.2 で報告され、0.28.5 でもまだ生きていた。あるプロジェクトには外部プロデューサー
から取り込まれたセッションが 1 つあった — 自らのエージェントセッションを
`HarnessSession` JSON に正規化し、`tesserae sessions import <file>` を呼ぶアプリだ。
ローカルの Claude Code と Codex 履歴を追加するため `sessions discover --import` を
実行すると、マニフェストが 1 から 377 セッションになり、存在していたレコードは
消えていた。マニフェストから削除されたのではなく、ストアから削除されたのだ。
出力された行は `Imported harness sessions: 377` だけだった。

空のスキャンガード（スキャンで何も見つからなければマージするガード）は既に正しかった。
「権威がある」がどこまで到達するかが間違っていたのだ。ディスカバリーはローカルの
Claude Code と Codex トランスクリプトをスキャンし、他のプロデューサーからのレコードは
構造的には見えない。古いわけではない。範囲外なのだ。それでも削除されていた。

## 修正と最初の試みを越える 3 つの方法

最初の修正はスキャンが実際に歩んだハーネスルートに削除の対象を絞った。その修正を
レビューすると、その対象範囲を越える 3 つの方法が見つかり、それぞれ実行の権限がない
レコードを削除していた：

- **`--harness` がスキャンを絞っても対象範囲は絞らなかった。** ルートはフィルターが
  適用される前に発見されるため、`sessions discover --harness codex --import` でも
  `~/.claude` をその削除対象に入れながら、そこからは何一つ書き直さず、保存された
  すべての Claude Code レコードを削除していた。CLI の `--help` テキストの例がこれだ。
- **パースできないレコードは誰にも属さないものとして扱われていた**。しかし
  これはプロデューサーが書き込み中か、ファイルが破損している — どちらにせよ所有者は
  *未知*で、未知で削除することがまさに最初のバグの仕組みだった。
- **`Path.resolve()` が保護なしで実行されていた。** シンボリックリンクループが
  `RuntimeError` を出し、埋め込まれた NUL が `ValueError` を出すが、どちらも
  キャッチされず — 新しいファイルが着地した後、マニフェストが再構築される前に
  書き込みを中止し、ストアとマニフェストの一致を失わせていた。

3 つすべてが同じ質問に同じ間違った方法で答えることから来ていた。コードに書き込まれた
ルールは今：**不確実なケースはすべて「これは削除する権限がない」と答える。**
削除は破壊的で、スキャンの権限は狭い。だから「このレコードが自分のものだと示せない」は
「手をつけずにいる」を意味する必要がある。

具体的には、保存されたレコードは、そのトランスクリプトがこの実行がスキャンした
ルートの下に**あり**、そのハーネスがこの実行がスキャンしたもの**である**場合に限り
削除される。両方の半分が独立して範囲を狭める。`.md` ページで背後にレコードがなければ
まだスイープされる — それは本物の孤児で、スイープはその孤児のためにあるのだ。

2 つの小さなことが生まれ出る：レコードを削除するスイープが取り込み数の隣に数を
出力するようになったため、縮小がもう成長を報告している行の内側に隠れることはできない。
`write_sessions` は `replace=True` で対象範囲を省略すると依然ストア全体をワイプすること
を文書化するようになったが、これは古い挙動で、依然到達可能で、Tesserae の呼び出し元は
これを望まない。

## 契約が書き込まれた

バグは部分的には、2 つのエントリーポイントがどう異なるか何も言わないことで
可能だった。正規化された `HarnessSession` JSON を作るツールが `sessions import` を
呼び出すことができ、後のディスカバリーが書き込んだものを削除することを学ぶ方法が
なかった。
[`docs/session-history.md`](../session-history.md) はいま **How the store is written**
セクションを持ち、状態を述べている：インポートはマージし、ディスカバリーはスキャンした
範囲内だけを置き換え、その他すべて生き残る。

## このリリースの他の部分

開発者向けで、ランタイムの挙動を変えないグラフ成長評価の作業。全デモコーパスをスライス
するようになった — 50 のペーパーではなく 73 のドキュメント、リポ、ダイジェスト、
総合と開放質問で、それらが既に宣言するものではなくコーパスに書き込まれた日付からの
ものだ。アンカー解決はリテラルフレーズではなくラベルトークンと照合する。

それを実行した正直な結果：15/15 の質問に答え可能で、その数は置き換えた 14/15 より
少ない意味を持つ。より大きなグラフで、15 のうち 14 の質問は既に*シングル*ホップで
答え、任意のアンカーペアの 87% は 3 ホップ以内でつながっている。アンカー解決が
セット基盤であるため、回答可能性はコーパスサイズとともにインフレする。
`evals/growth/probe_anchors.py` がこれを正確に測定し、結果は平滑化ではなく記録される
— 評価の弁別力、スコアではなく、が開放問題だ。
