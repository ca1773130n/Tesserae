发布于 **2026-09-06** · [PyPI](https://pypi.org/project/tesserae/0.39.0/) · [GitHub 发布](https://github.com/ca1773130n/Tesserae/releases/tag/v0.39.0) · `pip install --upgrade tesserae==0.39.0`

`tesserae compile` 总是通过你配置的 LLM 来构建概念和声明层。其他所有进入编译的方式都没有这么做：
`refresh`、引擎守护进程、MCP `materialize` 路径和 `deploy --build` 都会请求编译而不指定提取器，而"none"
的意思是用确定性那个。

## 发生了什么

在一个真实项目上运行一次 `tesserae refresh` 会不用 LLM 重建整个文档层。每个文件仍然标记为已图表化，
没有文档被标记为回退，而图谱回来时已经失去了概念、能力、模型和主题——466 个概念变成了 0。在刷新循环上
运行的守护进程会在它的第一次重新编译时做同样的事。修复先用一个装置钉住了：增量差异器保留未触及文件的
LLM 类型节点；入口点是那个漏洞。

## 改了什么

- **不指定提取器的编译现在构建配置的 LLM 那个**，与 `tesserae compile` 构建的形状相同，确定性提取器作为
  每个文档的回退。没有可用的后端退化到结构图并发出警告，从不静默。`compile --extractor deterministic`
  仍然是明确的退出。
- **上下文包引用并打包阐述一个实体的文档。** v0.38.0 存储了每个文档的提及密度；没有东西读它。一个实体的
  包部分现在打包那个文档的正文并用其引文命名它，当没有新鲜 SQLite 镜像时回退到首次看到的路径。
  `node_context` 获得了一个累加的 `documents` 列表，已排序。在两个语料库上测量，首次看到的大约半数时间命名
  拥有的论文；最常提及的文档，十次中九次。
- **`verify_attribution`**，作为一个 MCP 工具和 `verify-attribution` CLI 动词。覆盖率检查从邻近的表格行
  提取一个真实的数字能通过，因为每个标记都在证据中。这改为检查所有权：该数字在谁的记录中，以及该文档是否
  命名了基准。确定性，无图，无 LLM；在 15 个错误属性中捕获了 14 个，33 个真正的答案中有 4 次误警。
- **一个信用不足的 codex 账户是耗尽，而不是传输故障。** 一次生成，判决 `exhausted`，在运行中记住——提供者
  链在调用时落回到登录的 Claude CLI，正如其文档字符串一直承诺的那样。在此之前，每个调用花费约 55 秒去重试
  四个位置，最后什么都没返回。

## 升级

如果你运行一个守护进程或一个 `refresh` 循环，从现在起期望它在改变的文档上花费 LLM 调用；未改变的文档会
击中以 `prompt` 为键的缓存。在早期版本中通过 `refresh` 编译的图表是纯结构的——一个完整的 `tesserae compile`
恢复 LLM 层。没有其他东西需要迁移。
