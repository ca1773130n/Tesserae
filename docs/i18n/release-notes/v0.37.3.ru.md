Выпущено **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [Релиз на GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1 и v0.37.2 сделали локальный OpenAI-совместимый сервер достижимым. Запуск
такого сервера показал следующее: пул извлечения рассчитан на облачный API с
ограничением частоты запросов, а сервер модели на этой машине обслуживает один
запрос за раз.

## Что произошло

`TESSERAE_EXTRACT_CONCURRENCY` по умолчанию равен 4. Ollama, llama.cpp и LM Studio
обслуживают один запрос за раз, поэтому за каждым вызовом в очереди стояли три
запроса, а запрос из очереди, который сервер отбросил, блокировал свой воркер на
весь `TESSERAE_EXTRACT_TIMEOUT`. Снаружи это выглядит в точности как проблема с
памятью, и на правильное прочтение ушли часы.

## Что изменилось

- **Если значение не задано, оно следует за эндпоинтом.** Loopback-адрес в
  `llm_base_url` (`localhost`, `127.0.0.1`, `::1`) означает один документ за
  раз, а заметка в stderr называет эндпоинт и способ переопределения.
- **Пакетный раннер спрашивает у экстрактора, куда идут его запросы.**
  `LLMResearchExtractor` открывает `base_url` своего клиента, а выборочный
  маршрутизатор отвечает за свою LLM-половину, так что ничего не пришлось
  прокладывать через четыре места вызова. У детерминированного экстрактора
  нет эндпоинта, и он сохраняет 4.
- **Явное значение всегда побеждает.** Loopback-прокси, раздающий запросы в
  облачный API (LiteLLM, vLLM с батчингом), выдерживает больше: задайте его.

`docs/tuning.md` описывает новое значение по умолчанию.

## Обновление

Мигрировать нечего. Если компиляция с локальной моделью выглядела зависшей или
упёршейся в память, скорее всего дело было в этом. Добавленный как обходной путь
`TESSERAE_EXTRACT_CONCURRENCY=1` можно оставить или убрать; результат тот же.
