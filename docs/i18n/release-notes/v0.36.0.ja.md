公開日 **2026-08-30** · [PyPI](https://pypi.org/project/tesserae/0.36.0/) · [GitHub リリース](https://github.com/ca1773130n/Tesserae/releases/tag/v0.36.0) · `pip install --upgrade tesserae==0.36.0`

このリリースは、コンパイル済みグラフを二日間測った結果である。数字はすべてここにあり、それぞれを生んだハーネスはリポジトリにある。

## 文書ごとにアンカーは一つ

チャンク抽出はチャンクごとに文書アンカーを作っていた — 論文一本に 9.4 個 — そしてリトリーバはアンカーごとに原文全体を与えるので、一本の論文が top-k の十席を独占できた。いまは各断片のアンカーがマージ前に最初の断片のアンカーへ向け直され、先に現れた被引用文書を文書と取り違えることもない。同じ 148 本の論文を同じキャッシュヒットで再コンパイルすると、文書 recall@10 は **0.550 → 0.652** になった。

同じ根の二つ目の欠陥: グラフはセッションごとにアンカーノードを二つ持ち、文書優先検索の十席は四セッションしか含まなかった。いまは文書ごとに一つのアンカーを並べ、残りの席を埋める — LongMemEval recall@10 **0.867 → 0.891**。

## 一つの名前は一つのエンティティ、事実はノード越しにも読める

`PDB` はある論文では Benchmark、別の論文では Dataset で、名前で解決する消費者はみなその曖昧さを拒んだ。三つのマージパスがすべて見逃していた。いまは研究エンティティ型をまたいで、同じ名前は文書を越えて統合される。そして `verify_claim` は、抽出器が Result ノードを通して書いた事実 — `S reports_result R, R evaluated_on D` — を読む。述べられた関係 426 のうち正解 **117 → 167**、負例 426 で捏造された SUPPORTED は **0**。

## レビュー印は既定で正確

無料の検査だけではモデルより不正確で（0.872 対 0.928）、モデルなしの変種はどれも差を埋めなかった — それぞれ測った。カスケードは埋める: 不確かな帯だけを委ね、呼び出しの 40% で **0.935**。`ask` の内側では既定でオンになった; `TESSERAE_VERIFY_BAND=off` で無料の印に戻る。

| 会話メモリの検索 | 以前 | 以後 |
|---|---|---|
| LoCoMo、9 会話、recall@10 | 0.878 | **0.930** |
| LongMemEval、グループ 0、recall@10 | 0.867 | **0.891** |

## そのほか

- `tesserae graph-repair` は、すでにディスクにあるグラフに後処理パスを適用する — モデルもネットワークもなく数秒 — そして修復したグラフは再コンパイルしたグラフと一致する
- 会話メモリ向けの文書優先ランキング（`document_first`）は LoCoMo と LongMemEval のアームが選ぶ; 論文コーパスでは悪化するため既定ではない

## アップグレード

既存のグラフには再コンパイルではなく `tesserae graph-repair` を実行する。`ask` は既定でレビューカスケードにトークンを使うようになった; 以前の挙動は `TESSERAE_VERIFY_BAND=off`。
