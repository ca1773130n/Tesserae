Veröffentlicht am **2026-09-12** · [PyPI](https://pypi.org/project/tesserae/0.41.0/) · [GitHub-Release](https://github.com/ca1773130n/Tesserae/releases/tag/v0.41.0) · `pip install --upgrade tesserae==0.41.0`

Tesserae beschreibt sich selbst als eine Engine, die Wissen eigenständig einzieht, anstatt darauf zu warten, dass es ihr mitgeteilt wird. Bis zu diesem Release zog sie niemals etwas ein. Jede Trigger-Quelle, auf die der Daemon wartete, war eine lokale Dateiänderung: der Dateisystem-Watcher, der Vault-Watcher, der Session-Tailer und der in v0.40.0 hinzugefügte Site-Server. Sie rekonstruieren, was Sie bereits auf die Festplatte geschrieben haben.

## Was sich geändert hat

- **`tesserae engine --proactive` ruft Daten ab.** Es fragt die in der `proactive_sources` eines Projekts aufgelisteten Feeds ab, zieht Dokumente ein, die es noch nie gesehen hat, und übergibt sie dem gleichen Debounce- und Compile-Pfad wie jede andere neue Datei. RSS und Atom funktionieren beide, und eine URL, die kein Feed ist, wird als das Dokument selbst behandelt und einmal aufgenommen.
- **Es ist standardmäßig ausgeschaltet und bleibt günstig.** Dies ist das erste, das in Tesserae ohne einen Menschen an der Tastatur ausgibt, also ist `--proactive` opt-in, wird zusammen mit `--once`, `--harvest-only` und `--all` abgelehnt und ist auf fünf neue Dokumente pro Abfrage budgetiert. Der Poller wartet vor seinem ersten Tick, also kommt die Protokollzeile, die sagt, was er tun wird, zuerst.
- **Nichts wird zweimal abgerufen.** Ein Ledger neben dem Graph zeichnet jede URL auf. Eine, die Tesserae nicht lesen kann, wie ein reiner PDF-Link, wird als verweigert aufgezeichnet, nicht jede Stunde erneut versucht, vor Einträgen, die funktioniert hätten. Ein Timeout ist keine Aussage über ein Dokument und wird nie aufgezeichnet, daher werden Transportfehler erneut versucht.
- **Feeds werden defensiv geparst.** Dies ist der einzige Ort, an dem Tesserae XML von einer URL analysiert, die jemand anderes kontrolliert, also wird ein Feed, der eine DTD deklariert, komplett abgelehnt. Das beseitigt Entity-Expansion- und External-Entity-Angriffe zusammen, und ein echter Feed hat keinen Nutzen für einen.
- **`tesserae sources add <url>`** fügt einen Feed hinzu, dasselbe Verb, das ein Verzeichnis hinzufügt. Woher das Wissen eines Graphen kommt, ist eine Frage, also ist es ein Befehl; `sources list` beschriftet jeden Eintrag.
- **`tesserae completion bash|zsh|fish`** gibt ein Shell-Completion-Skript aus, das aus der echten Befehlsstruktur generiert wird, damit es nicht von der CLI abweichen kann. Der Generator hat sofort eine veraltete Zeile in der Hilfe gefunden, die drei von `sessions`' fünf Unterbefehlen beworben hatte.
- **Ein falsch geschriebener Befehl schlägt den richtigen vor.** `tesserae complie` weist auf `compile` hin, und ein Unterbefehl, der ohne seine Gruppe eingegeben wird, wie `sync`, nennt beide Gruppen, die einen haben. Ein bloßer Gruppenname wie `tesserae vault` gibt jetzt die Hilfe dieser Gruppe aus, anstatt einen Argparse-Fehler über ein fehlendes Argument.
- **`write_sessions` wird nicht ableiten, wer einen Store besitzt.** Sein `producer`-Argument war standardmäßig leer, was ganze Store-Autorität bedeutet, daher war die destruktive Lesestelle die, die Sie durch das Nichtübergeben von irgendetwas erhalten haben. Es ist jetzt erforderlich. Ganze Store-Autorität ist immer noch verfügbar und ist als `producer=""` geschrieben, was als Entscheidung statt als Unterlassung gelesen wird.

## Upgrade

Nichts zu migrieren. Proaktive Aufnahme macht nichts, bis Sie einen Feed hinzufügen und `--proactive` übergeben, und jede andere Änderung ist zusätzlich. Die einzige Breaking Change ist für Code, der `write_sessions` direkt aufruft: übergeben Sie `producer=`. Jeder Aufrufer innerhalb von Tesserae tat das bereits.
