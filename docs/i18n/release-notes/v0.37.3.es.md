Publicado el **2026-09-02** · [PyPI](https://pypi.org/project/tesserae/0.37.3/) · [Release en GitHub](https://github.com/ca1773130n/Tesserae/releases/tag/v0.37.3) · `pip install --upgrade tesserae==0.37.3`

v0.37.1 y v0.37.2 hicieron alcanzable un servidor local compatible con OpenAI.
Ejecutar uno expuso lo siguiente: el pool de extracción está dimensionado para
una API en la nube con límite de peticiones, y un servidor de modelos en esta
máquina sirve una petición a la vez.

## Qué pasó

`TESSERAE_EXTRACT_CONCURRENCY` vale 4 por defecto. Ollama, llama.cpp y LM Studio
sirven una petición a la vez, así que tres peticiones quedaban encoladas detrás
de cada llamada, y una petición encolada que el servidor descartaba bloqueaba a
su worker durante todo el `TESSERAE_EXTRACT_TIMEOUT`. Desde fuera parece
exactamente un problema de memoria, y costó horas leerlo correctamente.

## Qué cambió

- **Sin definir, el valor sigue al endpoint.** Un `llm_base_url` loopback
  (`localhost`, `127.0.0.1`, `::1`) significa un documento a la vez, y una nota
  en stderr indica el endpoint y cómo sobrescribirlo.
- **El runner por lotes pregunta al extractor adónde van sus peticiones.**
  `LLMResearchExtractor` expone el `base_url` de su cliente y el router
  selectivo responde por su mitad LLM, así que no hubo que cablear nada por
  cuatro sitios de llamada. Un extractor determinista no tiene endpoint y
  conserva 4.
- **Un valor explícito siempre gana.** Un proxy loopback que reparte hacia una
  API en la nube (LiteLLM, vLLM con batching) admite más: defínelo.

`docs/tuning.md` documenta el nuevo valor por defecto.

## Actualización

Nada que migrar. Si una compilación con modelo local parecía atascada o sin
memoria, probablemente era esto. Un `TESSERAE_EXTRACT_CONCURRENCY=1` que hayas
añadido como solución temporal puede quedarse o irse; el resultado es el mismo.
