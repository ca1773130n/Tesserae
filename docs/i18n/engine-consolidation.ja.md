# 自動統合 — エンジンのスリープサイクル

脳は休息中に記憶を統合します。眠っている間、その日の生の経験は再編成され、圧縮され、統合されます——最近のうるさいものは永続的な構造に折り畳まれます。Tesseraeのエンジンも同じことをします。プロジェクトが**アイドル状態**になると、常にオンのデーモンは次の編集を待つことをやめ、静かな時間に既に知っていることを再編成します：**圧縮して忘れ**、誰も取得していない知識を**未使用で褪色させ**、**生き残ったもの間の新しい接続を発見**します。

これまで、そのパスはあなたが要求した場合にのみ実行されていました——メモリ圧力下で`tesserae refresh`、または明示的な`tesserae distill`。エンジンはすべてのファイルとセッションイベントで再コンパイルしましたが、自動的には統合されませんでした。**スリープサイクル**がこのギャップを埋めます：`tesserae engine`を実行し続けると、休息中に統合が発生し、覚えるコマンドはありません。

[階層化されたメモリ](agent-memory.ja.md)システンのすべてと同様に、これは**オプトインしない限りノーオペレーション**です——デーモンはアイドル状態で統合しますが、その下の蒸留は`TESSERAE_AGENT_DISTILL`が設定されている場合にのみ機能します。

## いつ発生するか

専用統合スレッドは固定**チェック間隔**（デフォルト30秒）で目覚め、単調アクティビティクロックに対して2つの独立したトリガーを評価します：

- **アイドルトリガー。** プロジェクトが少なくとも`--consolidate-idle`秒間トリガーイベントもパイプラインも実行されていません（デフォルト**300秒= 5分**）。これは「休止中の統合」です——エンジンが作業を停止したことに気づき、休止を使用しました。前回の統合以降の**フロア**はスラッシングを防ぐため、ちょうど静かになった忙しいプロジェクトは敏感なトリガーでは統合されません。
- **上限トリガー。** 前回の統合以降**アクティビティに関係なく**少なくとも`--consolidate-every`秒が経過しました（デフォルト**21600秒= 6時間**）。これにより、継続的に忙しいプロジェクトでも、静かな瞬間がないのではなく定期的に統合されることが保証されます。これを`0`に設定すると上限が無効になります——その場合、アイドルが唯一のトリガーです。

すべての編集、セッションターン、または再コンパイルはアクティビティクロックを増やすため、アイドルウィンドウは本当の休息中にのみ経過します。両方のクロックは**単調**で、ウォールクロックではなく、アーティファクトに永続化されません——統合タイミングはバイト決定論的グラフを乱すことはできません。

## 実行される内容 — 5つの操作

各発火は`.tesserae/graph.json`からコンパイルされたグラフをロードし（ファイルが存在しない場合はパスをスキップ）、順序で5つの統合操作を実行します。それらは一緒に、休んでいる脳がすることを反映しています：最近のうるさいものを圧縮し、再度訪問されないものを褪色させ、生き残ったもの間の新しい関連付けを配線し、そしてリハーサル——誰も待っていない今、読者が次に望む説明に少しの努力を費やします。

### 1. 圧縮/忘却 — 蒸留

`tesserae refresh`が各エージェントのメモリを再編成、圧縮、安全に忘れるために使用するのと同じ`maybe_distill_on_refresh`エントリポイントを呼び出します。その関数は内部的に**三重ゲート**され、エージェントごとの失敗で発生することはありません：

1. **オプトインゲート** ——`TESSERAE_AGENT_DISTILL=1`（または`config.json`の`{"agent_distill": {"enabled": true}}`）。デフォルトではオフ；設定するまで、周期全体は安全なノーオペレーションです。
2. **エージェントごとのウォーターマーク** ——前回の蒸留以来結論が変わっていないエージェントはスキップされます。
3. **エージェントごとのメモリ圧力** ——蒸留されていない結論がコンテキスト読み取りの半分に収まらなくなったエージェントのみが統合されます（MemGPTスタイルトリガー）。

したがって、統合がスケジュール上で**発火**する場合でも、オプトインして実際に十分な新しいメモリを蓄積したエージェントに対してのみ**機能**します。蒸留が生成するものについては、[階層化されたエージェントメモリ](agent-memory.ja.md)を参照してください。

### 2. 不使用による忘却 — 年齢だけではなく検索上のLRU減衰

蒸留の減衰は、もはや作成年齢だけによって駆動されません。すべての読み取り表面は、それが返す結果に対するアクセスを記録します——`last_accessed_at`と`access_count`——**`node_memory`サイドカー**に記録し、`graph.json`には記録されません。蒸留パスが減衰を計算する前に、そのライブアクセス状態を作業ビューにマージするため、作成以来取得されていない結論は減衰して吸収または降格の対象となり、最近読み取られた結論は年齢に関係なく新鮮に保たれます。これは**検索最近性**、メモリに適用されたLRU（最近最も使用されない）直感です：継続的に取得する知識は保持されます；誰も要求しない知識は最初に褪色します。空のサイドカーは古い年齢のみの動作を正確に再現するため、完全に後方互換です。

### 3. 関連付け — 新しい接続を発見

最終操作は、生き残ったもの間の*新しい*関係を探します。蒸留されたメモを埋め込み、意味が近いペアをリンクします——**埋め込みゲート**、実際の埋め込みバックエンドが構成されている場合にのみ実行されます（ハッシュスタブはスキップされ、ノイズリンクは生成されません）。発見はプロジェクト内および**エージェント間**で実行され、発見する接続は`federation_semantic`マーカーを持つ`shares_concept_with`エッジとして作成されます。

重要なことに、これらの発見されたエッジは、`.tesserae`の下の**サイドカーオーバーレイ**に書き込まれ、*絶対に*`graph.json`には書き込まれません。オーバーレイは**サイクル間で蓄積**されます——各関連付けパスは、以前のパスが発見したものに対して重複排除および拡張します。読み取り時（クエリ、PPR拡張、フェデレーションビュー）に、オーバーレイは**メモリ内のみで**グラフにマージされます。エージェントビューオーバーレイと同じように——バイト決定論的`graph.json`は絶対に触れられません。操作全体がラップされ、デーモンループに発生することはありません。

### 4. 要約 — エージェントが降下するコミュニティキャッシュを事前ウォーミング

`graph_map`はスコープごとにカードを提供します。要約キャッシュが冷たいスコープは、決定論的な*構造的な*カード——メンバー数とトップメンバーのリスト——を取得します。そこを訪問する最初のエージェントは散文を取得するために同期LLM呼び出しを支払います。この操作はそのコストを読み取りパスから移動します：ティック当たりの予算内（`--summarize-budget`、デフォルト25；`0`は無効化します）次に訪問される可能性が最も高いスコープの要約を具現化するため、訪問はウォームキャッシュを見つけます。

候補は**需要**によってランク付けされます——スコープ自身の`graph_map`トラバーサルからのアクセス増加とそのメンバーのアクセス回数の合計——その後サイズ、度、レベルによって、総順序で、同じ状態での2つのティックは同じスコープを選択します。既にウォームで依然としてダイジェスト有効なキャッシュはバジェットを消費しません；冷たい具現化のみがそうします。LLMクライアントがない場合、操作全体はノーオペレーションです。

### 5. ブリーフ — チャーターのドメインブリーフを事前ウォーミング

同じ形式ですが、1つの軸が異なります：候補は樹形図のコミュニティではなく[チャーター](../README.md)のライブドメインです。冷たいドメインは、それが出現する場所——`graph_map`、`charter_route`のスコアリングコーパス、リントの`CHARTER_FALLBACK`センサスで——構造的なカードとしてレンダリングされるため、このパスは認可された機関に散文を提供するものです。

予算は独自のノブ（`--brief-budget`、デフォルト8；`0`は無効化します）です。意図的に`--summarize-budget`から分離されているため、どちらの操作も他を飢えさせることはできず、意図的により小さいです：チャーターの**部門**は`graph_map`がそのルートカードセットとして提供するもので、その数はほんの一握りなため、8 は最初のアイドルティックでエントリポイントを温め、より深いティアはその後ろで 1 ティックあたり 8 件ずつ続きます。

順序は**幅優先**で、需要ランクではありません。ドメインのメンバーセットはその全体のサブツリーを含むため、親の需要は常に子の需要を支配し、祖先の前にどのドメインもウォームされません。それは意図的です：エージェントはルートから降下するため、粗いカードは最初に読まれるものであり、散文を持つ価値のあるものです。アクセス回数は、どちらも他を含まないドメインを順序付けし、ライブな**部門**——ライブな親がないドメイン、`graph_map`のルートが使用するのと同じルール、`tier == 1`ではない——は他のすべての前にソートされます。

いくつかのドメインはバジェットスロットにコストをかけることはありません。これはスロットがLLM呼び出しであることを意図しているためです：廃止されたドメイン、`intake`センサス（これは主題を持たないため、その数千のメンバーの25人から書かれたブリーフは確信を持って全体の 1 パーセントにも満たない部分の説明になります）、グラフを離れたメンバーを持つドメイン、および既にウォーム。そして具現化が**失敗した**ドメイン——最も多くは、その散文が子の何も引用しなかったため拒否されたため——は同じランクで再試行されるのではなく倍の数のティック間保持されるため、永続的にウォーム不可能なドメインはウォーム可能なドメインが使用できるスロットを保持することはできません。

### このコストは時間あたりいくら

両方の予算は**ティック**あたりで、ティックは`--consolidate-idle`ウィンドウあたり最多1回発火します。デフォルトで：

| | ティック当たり | `--consolidate-idle 300`での時間あたりティック | 上限 |
|---|---|---|---|
| 要約 | 25 | 12 | 時間あたり300 LLM呼び出し |
| ブリーフ | 8 | 12 | 時間あたり96 LLM呼び出し |
| **合計** | **33** | **12** | **時間あたり396 LLM呼び出し** |

これは**キャッシュが冷たい間にのみ到達される上限**であり、**ゼロに減衰**します：ウォーム、ダイジェスト有効なキャッシュは呼び出しもスロットもコストをかけないため、プロジェクトのスコープとドメインが要約されたら、スリープサイクルはグラフが変わるまで何も費やしません。いずれかの予算を`0`に設定してその操作をオフにするか、`--consolidate-idle`を上げてティックをまれにします。

**なぜコンパイル時ではなく、ここなのか。** ブリーフは1つのLLM呼び出しです。コンパイル中にそれを作成することは、すべてのコンパイルでドメインごとに1つの呼び出しを置くことになり、コンパイルはこのプロジェクトが決定論的で安いままにしておくパスです。読み取りに遅延して作成することは、`graph_map`呼び出しがモデル上でブロックできることを意味します。アイドルスリープサイクルは、誰も待っていない呼び出しを費やすことができる唯一の残りの場所です。

## 安全性と決定性

- **コンパイルゲートの下で実行します。** 統合は再コンパイルと同じロックを取得するため、コンパイルと**直列化**され、**決して重複しません**。保留中のコンパイルは進行中の統合を待ち、その逆も然り——グラフは書き込み中に読み込まれることはありません。
- **デーモンループに発生することはありません。** パス全体がラップされています；エラーはログに記録され、スレッドはループを続けます。失敗した統合はエンジンを停止させることはありません。
- **ゲートがオフの場合、ノーオペレーション。** `TESSERAE_AGENT_DISTILL`が未設定の場合、パスは高価なものをロードせず、すぐに返すため、スリープサイクルを開いたままにしておくことは本質的にコストがかかりません。
- **決定論的アーティファクト、変更なし。** 蒸留されたアーティファクトは入力が与えられれば決定論的のままです；スリープサイクルは蒸留が**いつ**実行されるかのみを変更し、**何**を生成するかは決して変更しません。アイドル時間は`graph.json`または蒸留層に漏洩することはありません。
- **`graph.json`はバイト冪等を保持します。** ここでの操作は何も書き込みません。アクセス状態は`node_memory`サイドカーに存在し、発見された接続は累積オーバーレイにあり、要約とドメインブリーフの両方は`community_summaries`キャッシュにあります——すべて`.tesserae`の下、読み取り時にメモリ内のみでマージされます。権威あるグラフバイトは検索履歴、発見されたリンク、または事前ウォームされた散文の影響を受けません。要約とブリーフは**知識ではなくキャッシュ**です：キャッシュディレクトリの削除は次の読み手に構造的なカードをコストし、他には何もコストしません。
- **クリーンシャットダウン。** 統合スレッドはデーモンの停止イベントを観察し、`Ctrl-C` /シャットダウン時に迅速に終了します。これはロング実行モード機能のみです：`tesserae engine ... --once`は決してそれを開始しません。

## CLIフラグ

| フラグ | デフォルト | 効果 |
|---|---|---|
| `--consolidate` / `--no-consolidate` | on | スリープサイクルを完全に有効または無効にします。デフォルトで有効（蒸留ゲートが設定されていない場合、ノーオペレーション）。 |
| `--consolidate-idle SECONDS` | `300` | 休止ウィンドウ：この多くの秒のアクティビティなし後に統合します。 |
| `--consolidate-every SECONDS` | `21600` | 上限：アクティビティに関係なく、最低限この頻度で統合します。`0`は上限を無効にします。 |
| `--consolidate-check SECONDS` | `30` | 統合スレッドがトリガーを再評価するために目覚める頻度。 |
| `--summarize-budget N` | `25` | コミュニティ要約を事前ウォーミング費やす最大ティック当たりLLM呼び出し。`0`はSUMMARIZE操作を無効化します。 |
| `--brief-budget N` | `8` | チャータードメインブリーフを事前ウォーミング費やす最大ティック当たりLLM呼び出し。`0`はBRIEF操作を無効化します。 |

## フリートの動作(`--all`)

`tesserae engine --all`は1つのプロセスですべての登録されたプロジェクトを最新に保ちます。各プロジェクトユニットは同じノブを持つ独自の統合スレッドを取得し、すべてのユニットは1つのフリート全体のコンパイルゲートを共有します——したがって、1つのプロジェクトの統合はフリート全体のコンパイルとシリアル化され、どれとも重複しません。

## 完成した例

蒸留をオンにしてから、より高速なスリープサイクルでエンジンを実行します——60秒のアイドル後に統合し、関係なく最低30分ごと：

```bash
export TESSERAE_AGENT_DISTILL=1
tesserae engine \
  --consolidate-idle 60 \
  --consolidate-every 1800 \
  --consolidate-check 15
```

いつものようにエディタとエージェントで作業してください；エンジンが観察し、デバウンスし、各変更を再コンパイルします。1分間停止するとアイドルトリガーが発火します：統合スレッドがコンパイルゲートを取得し、メモリ圧力下のエージェントを蒸留します——再編成、圧縮、安全に忘れて——その後、スリープに戻ります。30分のマークを過ぎて一度も停止せずに作業を続けると、上限も発火するため、容赦ないプロジェクトはまだ統合されます。

エンジンは実行を続けるが、統合を手動`tesserae distill`実行に任せるには、`--no-consolidate`を渡します。アイドル時に実行するが、固定スケジュールでは決して実行しないようにするには、`--consolidate-every 0`を渡します。
