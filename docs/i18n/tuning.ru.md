Все переменные, которые Tesserae читает из окружения, их значения по умолчанию и когда
их действительно стоит менять. Здесь ничего не требуется: значения по умолчанию
выбраны так, чтобы обычная команда `tesserae compile` работала корректно.

Конфигурация проекта и глобальная конфигурация (`.tesserae/config.json`, `~/.tesserae/config.json`)
имеют приоритет для параметров LLM-бэкэнда; переменные окружения ниже переопределяют
обе конфигурации в текущем запуске.

---

## Хуки, которые тратят деньги

Плагин Claude Code поставляется с хуками, которые могут запустить компиляцию в фоне. Всё, что
тратит деньги, **отключено по умолчанию**:

```sh
export TESSERAE_HOOK_AUTOCOMPILE=1   # явно согласиться на автоматические перекомпиляции
```

Ограничены: `posttooluse-edit.sh` (срабатывает на каждом Edit/Write) и `session-end.sh`.
Не ограничены, потому что стоят ничего: `session-start.sh` запускает `tesserae code
sync`, что детерминировано, и `pretooluse-compile.sh` только перехватывает
`tesserae compile`, который вы сами напечатали.

Это значение по умолчанию существует, потому что альтернатива была измерена. База знаний в
`~/.tesserae` делает `$HOME` похожей на корень проекта, и резолвер хука
шёл *вверх* от рабочей директории к первому найденному `.tesserae/` — поэтому
любой сеанс вне зарегистрированного проекта разрешался в `$HOME` и компилировал
всю домашнюю директорию: 15k файлов, граф 795 MB, **~10 часов расходов LLM**,
из отделённого процесса, пережившего сеанс, который его запустил.

`resolve_project_root()` теперь отказывает `$HOME` по обоим путям, и возвращает пусто
вместо отката к рабочей директории, поэтому вызывающие коды ничего не делают вместо угадывания. Хук, который запускает работу модели в фоне, должен быть включен явно,
не отключен после того, как придёт счёт.

## Извлечение

### `TESSERAE_EXTRACT_TIMEOUT`

**По умолчанию `1800` (секунды), за попытку.** Ограничивает каждый вызов
codex/claude-извлечения, чтобы зависший дочерний процесс не мог зависить compile.

Это реально случилось: compile наблюдался на 0% CPU в течение **5 h 43 m**
с `codex exec` дочерним процессом, простоявшим **4 h 6 m**, постоянно удерживающим
`.tesserae/compile.lock`. Он уже построил 32 краткие описания сообществ в памяти
и никогда не получилось их сохранить.

За попытку, не за документ — при timeout клиент переходит к следующей
директории `CODEX_HOME` / claude, поэтому в худшем случае для одного документа это
`timeout × количество настроенных профилей`.

```sh
export TESSERAE_EXTRACT_TIMEOUT=3600   # больше времени для очень больших документов
export TESSERAE_EXTRACT_TIMEOUT=0      # без ограничений — работать до завершения
```

Значение, которое задано но не валидно (`10m`, `600s`, отрицательное, `inf`), выведет
предупреждение в stderr и сохранит значение по умолчанию. Опечатка не должна
бесшумно отключать предохранитель безопасности.

### `TESSERAE_EXTRACT_CONCURRENCY`

**По умолчанию `4`.** Документы, извлекаемые параллельно. Каждый — это
блокирующий дочерний процесс CLI, требующий примерно минуту, поэтому
последовательный цикл делает реальное время ровно суммой всех времён моделей —
измерено как ~2 h 40 m для 161 документа.

Верхний предел — это limit скорости аккаунта провайдера, а не вашей машины, поэтому
значение по умолчанию консервативно. Установите `1` для строго последовательного поведения.

Параллелизм никогда не меняет результат: список работ зафиксирован в порядке пути,
результаты собираются по индексу, поэтому параллельный запуск идентичен
последовательному в каждом байте.

### `TESSERAE_LLM_CACHE`

**По умолчанию включено.** Кэш с адресацией по содержимому ответов CLI-провайдера
в `~/.tesserae/llm_cache`, индексированный по дайджесту фактически отправленного
промпта, а также по модели и уровню рассуждений — поэтому другой вопрос
переспросит, и при смене модели система переспросит вместо использования ответов
предыдущей модели. Сохраняются только распарсиваемые ответы, поэтому одна ошибка
генерации не может стать постоянной.

Старые записи недостижимы по замыслу: ключ использовался как метка,
поставляемая вызывающей стадией, а не как дайджест промпта, поэтому несвязанные
вопросы могли попадать в одну и ту же запись. Ничто их не переносит — каталог безопасно
удалить, и компиляция заполнит его заново.

```sh
export TESSERAE_LLM_CACHE=0   # всегда переспрашивать
```

### `TESSERAE_LLM_CHUNK_CHARS`

Количество символов на фрагмент, когда документ слишком большой для одного вызова.
Оставьте неустановленным, если вы не упираетесь в limit контекста.

## LLM бэкэнд

| Переменная | По умолчанию | Примечания |
|---|---|---|
| `TESSERAE_LLM_PROVIDER` | `claude` | `codex`, `claude`, `anthropic`, `custom` |
| `TESSERAE_LLM_MODEL` | зависит от провайдера | Ограничено провайдером, чтобы claude-совместимая модель никогда не попала на codex путь |
| `TESSERAE_CODEX_REASONING_EFFORT` | `medium` | Структурированное извлечение не требует `xhigh`, который вы можете установить для интерактивной работы — `xhigh` делает multi-document compile в несколько раз медленнее |
| `TESSERAE_CLAUDE_CONFIG_DIRS` | — | Разделённый `os.pathsep` список каталогов конфигурации Claude в порядке ротации — канал переменной окружения для повторяющегося `--claude-config-dir`. Авторитетен только *заданный* список; окружающий `CLAUDE_CONFIG_DIR` намеренно нет, потому что привязка к нему схлопывает ротацию нескольких аккаунтов до одного |

`tesserae config status` выводит полученный бэкэнд и проверяет его доступность.

## Проходы компиляции

| Переменная | По умолчанию | Что контролирует |
|---|---|---|
| `TESSERAE_COMMUNITY_SUMMARIES` | **включено** | Проход краткого описания в стиле GraphRAG. Один вызов LLM на кластер ≥ 5 членов, кэшировано по дайджесту членства. Отключается через `false`/`0`/`no`/`off` |
| `TESSERAE_ENABLE_LLM_PASSES` | выключено | Опциональные проходы обогащения LLM сверх извлечения |
| `TESSERAE_AGENT_DISTILL` | выключено | Артефакты L1 знаний на агента (`tesserae distill`) |
| `TESSERAE_RUNBOOK_DISTILLATION` | выключено | Узлы дистиллированной памяти Runbook/Gotcha |
| `TESSERAE_SESSION_EVENT_PASS` | **включено** | Узлы `Event` для каждого хода из стенограмм сессий. Без LLM и побайтово детерминировано, но по одному узлу на каждый значимый ход — заметный объём на длинном корпусе. Отключается через `false`/`0`/`no`/`off` |
| `TESSERAE_INSIGHT_SYMBOL_LINK` | включено | Связывает insights сеанса с символами кода |
| `TESSERAE_SUPERSEDE_PASS` | включено | Рёбра `superseded_by` между исправленными утверждениями |
| `TESSERAE_PROMPT_SIGNATURES` | выключено | Записывает подписи промптов для обнаружения дрейфа |
| `TESSERAE_COMPILE_LOCK_WAIT` | — | Секунды ожидания `.tesserae/compile.lock` перед отказом |

**О резюме сообществ:** проход компиляции нетерпеливо охватывает самый грубый уровень;
`graph_map` дополнительно лениво материализует резюме при первом спуске
в холодную область, кэшируемое за уровень. Отключение прохода — это законная
стратегия экономии — вы платите только за ветви, которые действительно посещаете — но
есть одно предостережение: **федеративный спуск никогда не материализует лениво.**
Карточки соседнего проекта могут быть названы только из его резюме в графе
или уже горячих кэшей, поэтому проект, по которому вы навигируете кросс-проектно,
хочет включённый нетерпеливый проход.

## Запрос и синтез

| Переменная | По умолчанию | Примечания |
|---|---|---|
| `TESSERAE_QUERY_LLM` | выключено | LLM-планировщик для `tesserae query` |
| `TESSERAE_QUERY_DRY_RUN` | выключено | План без вызова модели |
| `TESSERAE_SYNTHESIS_LLM` | выключено | Синтез текста в `tesserae ask` |
| `TESSERAE_SYNTHESIS_MODEL` | — | Переопределяет модель синтеза |
| `TESSERAE_SYNTHESIS_WORKERS` | — | Рабочие потоки параллельного синтеза |
| `TESSERAE_SYNTHESIS_DRY_RUN` | выключено | Пропустить модель, выполнить конвейер |
| `TESSERAE_VERIFY_BAND` | выключено | Пересудить моделью неуверенные пометки проверки в `ask`. `on` берёт измеренную полосу 0.30–0.70, `lo-hi` её переопределяет. Выключено — пометки не стоят ни токенов, ни сети |

### `TESSERAE_VERIFY_BAND`

Каждый ответ `ask` несёт пометки проверки по предложениям, которые ничего не стоят.
Они менее точны, чем вопрос к модели — 0.870 против 0.926 на 755 отложенных
предложениях, — и почти вся разница приходится на ложные тревоги о точных
пересказах: такие предложения делят с источником мало слов.

Эти два способа ошибаются на разных предложениях, поэтому платить модели только там,
где бесплатная проверка не уверена, возвращает точность за долю цены. Передача
покрытия 0.30–0.70 дала 0.932 на 42% вызовов: неотличимо от вопроса про каждое
предложение (McNemar p=0.52) при 42% расходов.

```bash
export TESSERAE_VERIFY_BAND=on          # измеренная полоса 0.30-0.70
export TESSERAE_VERIFY_BAND=0.40-0.60   # уже: 22% вызовов, 0.914
```

По умолчанию выключено: пометки документированы как не стоящие ни токенов, ни сети, а
каскад, включающий себя сам, нарушил бы это обещание для каждого вызывающего.
Конверт сообщает `adjudicated`: `null`, если каскад не запускался, и число, если
запускался. Модель, которая не смогла ответить, оставляет бесплатный вердикт на месте —
неудавшийся вызов никогда не сделает помеченное предложение чистым.

## Кто читал граф

| Переменная | По умолчанию | Заметки |
|---|---|---|
| `TESSERAE_READ_AUDIT` | **выключено** | Записывает чтения, которые перемещают счётчики доступа — `{tool, actor, node_ids, at, tesserae_version}` — в таблицу `read_audit` в `.tesserae/sqlite.db`, читаемую обратно через инструмент `read_audit` с per-actor-суммой. Строка пишется везде, где возрастает счётчик доступа, поэтому число строк следует поверхности, а не вызову: инструмент, который выдаёт список узлов (`search_nodes`, `node_context`, `compile_context`, `graph_map`, `graph_ppr`, `ask` / `query`, `drill_down`, `find_session_findings`), пишет **одну строку на вызов**, называя каждый узел, который он посчитал, тогда как `fresh_insights` увеличивает счётчик внутри собственного цикла и потому пишет **одну строку на узел**, который он выдал. Вызов, не выдавший ничего, не пишет ни строки, а инструмент, не читающий ни одного узла — `schema`, `graph_summary` — до аудита вообще не доходит, потому что строка, не называющая ни одного узла, не объясняет ни одного счётчика доступа. Выключено по умолчанию, потому что всегда включённый аудит по каждой поверхности чтения превращает любое чтение в запись; проверка флага стоит до открытия хранилища, поскольку создание таблицы само по себе является записью. Ничто из этого никогда не попадает в `graph.json` |
| `TESSERAE_ACTOR` | — | Кому приписать чтение, когда вызов не несёт представления агента. Актор — это аргумент `agent`, если вызов его разрешил, иначе это значение; если оно не задано, чтение записывается как анонимное, а не с выдуманным именем |

Отключение `TESSERAE_READ_AUDIT` прекращает запись, но не стирает того, что уже было записано, и вступает в силу без перезапуска сервера. Аудит нужен *для* [забывания по неиспользованию](agent-memory.ru.md#забвение--никогда-не-удаление): счётчики доступа определяют, что будет поглощено или понижено, и без актора болтливый агент, опрашивающий узел, и человек, прочитавший его один раз, — это один и тот же вход.

## Запуск нескольких машин на одном проекте

Ситуация, под которую это написано: несколько серверов, на каждом свой кодовый
агент со своими локальными транскриптами сеансов, и общий диск — то есть они
видят один и тот же каталог проекта и один и тот же `.tesserae/`.

**Отдайте компиляцию одному хосту, остальным оставьте только сбор.**

```bash
# on the compiling host
tesserae engine

# on every other host
tesserae engine --harvest-only
```

`--harvest-only` вливает локальные транскрипты своей машины в общее хранилище
сеансов и никогда не берёт блокировку компиляции проекта. Это убирает
конкуренцию, а не разруливает её, — потому и работает лучше, чем подкрутка
таймаутов.

**Когда вы всё же хотите встать в очередь, а не упасть**, передайте `--wait`:

```bash
tesserae compile --wait          # up to 30 min, reporting every 5s
tesserae compile --wait 120      # or name your own bound
```

Без него компиляция, наткнувшаяся на удерживаемую блокировку, выходит с кодом 2 —
правильно для хука, невыносимо для человека. `--wait` сделан флагом, а не
выводится из того, терминал ли stdout, потому что одна и та же команда не должна
менять поведение под `tee`, в захвате tmux или в CI. То же самое для целого
дерева процессов делает `TESSERAE_COMPILE_LOCK_WAIT=<seconds>`.

**Поддержание свежести всех проектов** одним вызовом:

```bash
tesserae refresh --all               # every registered project, sequentially
tesserae refresh --all --jobs 3      # three at a time
tesserae compile --all --name alpha --name beta
```

Падение одного проекта не останавливает остальные. Код выхода `2`, если что-то
упало, `1`, если что-то было заблокировано другим запуском, `0`, если отработало
всё. `--jobs` по умолчанию равен 1, потому что компиляция тяжела по LLM, и
повышение значения тратит квоту параллельно.

### Что делает это безопасным

Состояние, специфичное для машины, раньше хранилось под одним общим именем и
читалось каждым хостом. Каждый из этих пунктов теперь разделён по
идентификатору хоста:

| Состояние | Где | Почему оно обязано быть у каждого хоста своим |
|---|---|---|
| Записи сеансов | `.tesserae/harness_sessions/` | Хост удаляет только то, что собрал сам. Иначе хост B удаляет сеансы хоста A и рапортует об успехе — сканирование каждого хоста ставит одного и того же производителя, а их пути `~/.claude` разрешаются одинаково, так что различить их больше нечем |
| Pid-файл движка | `.tesserae/daemon.<host>.pid` | Живость — это `os.kill(pid, 0)` против **локальной** таблицы процессов; pid, записанный другой машиной, проверяется против постороннего локального процесса |
| Нижняя граница сканирования Codex | `.tesserae/harness_sessions.db` | Один общий watermark означал, что хост, отработавший последним, сдвигал его за транскрипты, которые другой ещё не прочитал, — и те не импортировались вообще никогда |

Идентификатор хоста генерируется один раз в `~/.tesserae/host_id` (свой на
каждой машине, **не** в общем каталоге проекта) и может быть зафиксирован через
`TESSERAE_HOST_ID`. Это сохранённый id, а не hostname, потому что парк,
собранный из одного образа, переиспользует hostname'ы, а их совпадение отдало бы
записи одной машины другой.

### Допущение, которое стоит проверить

Всё вышеописанное предполагает, что `flock(2)` **соблюдается** файловой
системой, на которой лежит `.tesserae/`. На NFS и SMB это зависит от
конфигурации, и без работающего lock-демона `flock` может молча выродиться в
no-op — и тогда два хоста компилируют один и тот же проект одновременно, каждый
в уверенности, что держит эксклюзивную блокировку.

`tesserae doctor` предупреждает, когда проект лежит на сетевой файловой системе,
но один хост **не может** доказать межхостовое соблюдение блокировок. Проверьте
это напрямую на реальном железе: возьмите блокировку на хосте A и убедитесь, что
хосту B отказано.

## Восстановление деградировавшего корпуса

Когда извлечение документа не удаётся, он обслуживается детерминированным
исходным вариантом и **помечается** в `.tesserae/manifest.json`.
Без пометки его невозможно отличить от чистого извлечения, поэтому
`--changed-only` будет его пропускать вечно и деградация будет
постоянной, пока содержимое файла не изменится.

```sh
tesserae compile --changed-only --retry-fallbacks
```

Повторно обрабатывает только помеченные документы; чистые остаются пропущены.

## Проверка иерархии

```sh
tesserae graph-map                          # корневая карта
tesserae graph-map --scope <scope_id>       # спуск
tesserae graph-map --scope '<alias>::'      # соседний зарегистрированный проект
```

Каждая карточка сообщает `size` и `leaf_member_count` из служебного файла
иерархии, плюс `live_member_count` — сколько членов *текущий* граф действительно
содержит. Если там `0`, это означает, что область мертва (рассинхрон служебного
файла/графа): пропустите её вместо спуска.

## Агенты пишут в граф

`graph_write` (MCP) принимает проверенные по схеме типизированные узлы и рёбра с обязательной провенансой, поэтому агент записывает находку как *структуру*, а не как прозу, которую экстрактор должен угадывать типы.

Отказывает, а не принуждает: нетипизированные рёбра, типы узлов или рёбер вне контролируемого словаря, свободные концы и записи без провенанса отклоняются. Дублированные записи идемпотентны. Узлы, написанные агентом, выживают при полной перекомпиляции, удалённом `graph.json`, `--limit` и полном удалении корпуса.

## Проверка утверждения относительно графа

`verify_claim` (MCP) отвечает, лицензирует ли граф тройку. Принимает `(subject, predicate, object)` — **нет параметра на естественном языке**, по замыслу, потому что парсер заставил предыдущую версию ответить SUPPORTED на отрицание утверждения, которое она поддерживала.

Вердикт — чистая функция графовых байтов: нет LLM, нет встраивания, нет нечёткого совпадения где-либо на пути принятия решения.

| Вердикт | Значение |
|---|---|
| `SUPPORTED` | рёбро существует, содержит собственные доказательства, и этот текст переоснован на исходный файл |
| `PRESENT_UNEVIDENCED` | рёбро существует, но ничего на основе документа не поддерживает его |
| `CONTRADICTED` | подтверждённое документом `contradicts_claim` между теми же двумя концами |
| `DISPUTED_UNEVIDENCED` | утверждаемое несогласие, ничего не подтверждено |
| `CONFLICTING` | обе полярности подтверждены документом — инструмент отказывается решать |
| `ABSENT` | этот граф не утверждает тройку. Не опровержение |
| `NOT_RESOLVABLE` | конечная точка или предикат не может быть точно разрешена |

Есть две вещи, которые он намеренно не делает. Он никогда не рассматривает `supersedes` как опровержение — эта связь говорит, что *узел* был заменён, а не что тройка ложна. И запись агента может только *ослабить* класс провенанса, никогда не обновить, поэтому ничто, что агент утверждает, не может представляться как документно-обоснованное.

Стоит знать при чтении результатов: на реальном графе с 15 284 рёбрами около 40% вердиктов `SUPPORTED` тавтологичны — рёбра `evidenced_by`, цитируемый диапазон которых является собственной целью ребра. Верно, но не информативно.

## Маршрутизация вопроса

`tesserae ask` выбирает путь извлечения по форме вопроса: простые поиски по одной сущности идут на дешевый бэкенд, мульти-хоп / "что изменилось" / "почему" / вопросы по корпусу идут на граф. Это разделение кодирует **гипотезу, а не измерение**: мы ожидаем, что обход окупится на мульти-хоп, временных и синтетических вопросах и окажется расточительным на простом поиске фактов. Ничто в этом репозитории этого не проверяет — здесь нет бенчмарка извлечения и нет опубликованных чисел за таблицей маршрутизации, поэтому считайте её значением по умолчанию, которое стоит переопределить, а не результатом.

Решение появляется в возвращённом конверте, поэтому дешёвый ответ проверяем. Переопределите его с `--route` на CLI или параметром `route` на инструменте MCP.
